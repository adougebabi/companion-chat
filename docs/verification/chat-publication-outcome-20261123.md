# 聊天媒体校验误判与业务状态修复

## 根因与范围

对原失败回合的只读诊断确认：候选正文表达图片介绍、分享意愿，校验模型却提取为
已经交付图片的声明。交付列表为空，连续拒绝后以 `direct_media_delivery_unresolved`
结束。较早的一次图片内容介绍也被误提取。原始私人对话及请求仅保留在仓库外，
本报告和回归使用缩减的合成文本，不包含人物资料。

Core 原有规则存在三个问题：未识别紧邻分享动作的意愿限定；提取跨逗号原文时
只取首分句而丢掉限定词；将明确发送当前文字消息的括号描写视为图片交付。
另一路状态问题是终态失败的 inbox 重放返回 `status=failed` 和 nil error，旧工作流
会成功结束，任务列表因此显示完成，而聊天正确地保留失败状态。

## 实现

- 仅在校验视图识别明确的意愿、否认、内容介绍及文字消息描写，保留候选和用户
  原文。即便提取模型错误，Core 仍检查其原句限定。肯定完成声明仍必须绑定同会话
  实际附件、主体和交付记录，并在发布事务重查。
- 一次主体核验只消费一个交付分句；不能用黑猫图片的真实记录放行另一个白狗
  图片声明。描述性前缀不能覆盖递交、投递等交付动作。
- 校验诊断关联真实父回合，记录候选、原提取、排除项、拒绝片段和原因。纠正反馈
  携带具体片段和拒绝原因。模型返回内容与正式聊天发布分别记录。
- 新失败保留闭集具体错误码，不一律折叠成 `adk_run_failed`。聊天提示明确说明
  “回复未发送”、失败环节和原消息保留情况，详情关联原回合。
- 任务详情、诊断任务列表、原请求关联任务和待处理来源共享 durable inbox 业务
  状态投影。保留外层 `workflow_status`、回合状态以及真实 assistant 消息是否存在，
  不把正常静默处理说成已发送回复，也不把已发送后的后续失败说成完全未回复。
- 新工作流以非重试终态报告 durable 业务失败，版本标记保留旧历史回放。调度器
  核对精确 workflow/inbox，并以 workflow、attempt 和 payload 条件防止旧运行覆盖
  后续重试。历史矛盾行通过只读投影显示，无批量修改业务库。

## 验证

- 修改前使用 Go overlay 驱动实际规则，分享意愿与文字消息描写均复现失败。
- 任务专用、仅 loopback 暴露的 PostgreSQL 执行正式 `HandleTurn`：意愿、介绍、
  文字动作、匹配交付可以发布；无依据完成、主体不符、跨句借用证据继续阻断。
- 实际数据库核对历史 `workflow=completed / inbox=failed` 的任务详情、诊断列表、
  待处理统计一致；pending/processed 后续状态不继续显示旧失败。
- 受控 Temporal 可见性配合真实调度器/数据库，验证 completed 执行不覆盖 failed
  业务状态；工作流测试覆盖历史版本与新版本的不同终态。
- 真实模型校验器配合受控主候选、正式原生工具链和隔离数据库：普通分享意愿最终
  唯一写入一条 assistant 消息；虚构已发图三次被拒且零消息。真实模型本身仍可能
  误提取，因此不把提示词修改当作唯一修复。这不是完整真实模型对话生成验收。
- 受影响后端包回归、前端类型检查与生产构建通过；前端针对聊天反馈、任务详情、
  诊断卡片、原消息重试身份及既有消息交付的 79 项测试通过。
- 使用真实 React 组件和合成数据检查桌面/移动聊天反馈、消息结果、失败环节及
  任务业务失败说明。截图保留在仓库外，生产包检查确认无 QA 页或样例存储。

## 交付边界

本次交付源码与回归，不自动部署、不修改生产数据库、不清除旧失败记录、不代替
用户重新发送消息。现有终态回合不会因更新代码自动变成一条已经发送的回复；
部署后仍应从原回应的恢复入口发起新尝试并核对真实消息。
