# M2-05 渲染提交歧义证据

2026-11-12 使用 Context7 查询 `/comfy-org/comfyui` 的公开源码索引：
[ComfyUI server.py](https://github.com/comfy-org/comfyui/blob/master/server.py)。该索引
所示当前上游 `/prompt` 允许调用方提供 UUID `prompt_id`，验证通过后执行
`prompt_queue.put(...)` 并返回 ID；`/queue`、`/history` 可查询任务。所检索内容没有
证明以同一 `prompt_id` 重复 POST 一定去重；队列和历史也可能因服务重启或清理而
不再保留记录。上游 master 不能代表用户当前部署的 ComfyUI 版本及其扩展实现。

本地复现使用一次性 PostgreSQL、两个独立测试进程、受控模型和受控 HTTP renderer。
服务器先记录接受第一次请求，随后断开连接，不返回 Job ID；第二进程在同一任务上
重新执行时再次调用 `/prompt`。`m2-05-red.log` 记录了两次提交和测试退出 1；没有
连接真实 ComfyUI，不代表真实图片被生成。当前后端无法从保存的状态确定第一次
请求是否被对端接受，因此不能把无 Job ID 等同于未提交。

可能的处理边界：提前持久化客户端任务标识并在响应丢失后尝试查询队列/历史，
查到原任务才恢复；查询不到时不能据此证明对端未接单，仍需保留不确定状态。
直接暂停等待核对也能避免自动重提，但会使某些实际上未送达的任务停住。这两者
会改变现有的自动重试行为；旧任务没有提前保存标识时也需要明确兼容策略。

用户随后明确选择直接暂停并等待人工核对，不自动查询或重提。实现采用发送前
持久化标记和不确定状态；只将已识别的 ComfyUI 结构化校验拒绝视为明确未接单。
普通媒体的人工恢复需要明确勾选核对并记录理由。Studio 与视觉身份均会停止自动
提交并显示待核对，但视觉身份、Studio 在核对后接回原任务的领域内操作尚未补齐。

新增 `0117_media_submission_guard` 是向前的可加字段迁移：旧记录保守标记不确定，
新记录默认未提交。新旧 Worker 同时运行时旧版本不会遵守这个标记；升级到本版本
前需要停止旧写入进程。上述迁移仅在一次性隔离库测试，尚未应用于用户业务库。
