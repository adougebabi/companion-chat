# AEL 通用 Agent 工程流程规范 v1.0

> 用途：定义 Codex 或其他 Coding Agent 在任何已接入项目中如何处理工作、持续执行、交接、回退和结束。AEL 的 Skill、CLI、执行器与看板都应落实本规范，而不是各自解释一套流程。
> 本文是供实现和验收使用的新规范，不表示现有 AEL 已具备这些能力。不使用任何具体业务项目、分支或历史任务作为通用流程模板。
> 本规范优先修正原 V1 的流程与产品验收口径；原有非破坏迁移、权限、证据真实性和并发保护要求继续有效。已有实现符合本规范的部分应复用。
> 并发行为更新：不同任务不再通过工作区锁互斥；相同任务的领取、恢复和证据校验仍有效。共享可写文件与外部资源的冲突由执行者协调或隔离。

## 1. 核心约定

**AEL 的主产品是一套可执行的工程流程协议。Agent 做实际工作；程序维护记录、检查可机械判断的条件并提供衔接；看板展示同一份真实工程事实。**

- “必须”是符合本规范的必要条件；“按需”必须由任务范围和项目政策判断，不能由执行者为了过关随意省略。
- 流程适用于单 Agent、多 Agent 和人机协作。角色数量不改变流程含义，也不要求每个逻辑步骤启动新 Agent。
- 正常工作在已有授权内连续执行。审批是处理真正决策边界的例外，不是每个步骤的默认动作。
- 已有有效输入可以复用；小任务可以合并处理若干逻辑步骤，但不能省略目标、适用规范、实际工作及完成依据。
- 不将“进程结束”“提交了状态”“写了总结”“生成了报告”等同于任务达标。
- 不把流程规范全量塞入每轮上下文。入口保持短小，执行时按节点读取相关规则与项目资料。
- 本规范不高于宿主系统安全规则和用户授权；普通任务不得悄悄覆盖既有关键项目契约。冲突应明确处理。
- 不要求提供模型的内部思考过程，只记录必要的工程结论、取舍依据、执行事实和证据。

## 2. 先区分五类资料

| 资料 | 回答的问题 | 权威边界 |
|---|---|---|
| 流程规范 | Agent 应该怎样处理工作？ | 本规范及项目已批准的流程配置 |
| 项目规范 Spec | 这个项目必须遵守哪些边界、接口和行为约定？ | 有来源、有范围、有生效状态的现行契约 |
| 决策 Decision | 为什么选择此方案，为什么没选其他方案？ | 决策记录及其接受、否决、替代关系 |
| 工作项 Task | 本轮做什么、做到哪里算结束、下一步是什么？ | 原始请求、任务定义与有效计划 |
| 执行结果与证据 | 实际做过什么、检查结果怎样、交付到哪里？ | 实际执行、检查和交付回执 |

Spec 不等于代码实现说明：代码违反现行契约时，应记录偏差，不应为了让文档吻合而把错误写成新规范。
Decision 不取代 Spec，任务历史不自动变成现行规范，历史计划不自动变成已实现事实。

一个任务可以只有一份紧凑定义与少量执行记录。不要为每个步骤强制生成 PRD、设计稿、验收稿、交接稿等重复文档。

## 3. 通用流程及真正的 Loop

项目接入属于前置准备，不是每个任务都重做的步骤。处理每次用户请求前，先按 W0 判断是否需要工程流程。

```text
项目接入：识别现有资料 → 建立可追溯的规范基线 → 确认可用能力与边界

用户请求 → W0 意图分流 ── 普通讨论/查询/审阅 ──→ 直接处理并沟通
                     └── 工程变更 ──→ 界定工作 → 依据规范分析/选择路径 → 执行实际工作 → 验证结果 → 收敛与交付

验证发现实现问题 → 返回实际工作修复
发现需求/方案/约束问题 → 返回界定或分析

完成后的反馈 → 归属与分类 → 关联的新工作项 → 下一轮
```

以上是逻辑责任，不是固定六次调用。发布只在交付目标需要时执行；反馈是下一轮入口，不让旧任务无限等待。

### W0：按请求目的分流

在运行 doctor、查询任务或知识索引、创建任务及加载工程工作流之前，先判断用户的目标是否是修改项目实际内容以进行项目迭代、修复或其他工程变更。不能把为了运行 AEL 而产生的文件或状态当成进入工作流的理由。

普通讨论、查询、定位功能、调研、分析、审阅，以及仅供审核的材料，即使保存为文件，也直接处理并与用户沟通；不运行 AEL 命令或创建任务，也不进入实施、验收或来源索引流程。可以按需直接读取项目资料，材料保存到用户指定位置本身不意味着要改进项目。

已授权的项目迭代、修复和其他工程变更，例如修改业务代码、配置或项目正式文档，进入 W1—W5。用户明确要求执行 AEL 命令、操作或继续某个 AEL 任务时，按该请求处理；单独查询不自动创建任务。只验收或调研的 AEL 工作项须是用户明确要求的 AEL 工作项，不能因为一般的审阅或讨论而创建。

请求在进行中变为已授权的工程变更时，首次实际修改前重新判断并进入工程流程。发现问题本身不扩大原授权；目的不明确时先完成可做的只读工作，仅在确有必要时澄清。

## 4. INIT：项目接入与规范基线

### INIT-1 识别和继承，不从空目录开始假装已就绪

初始化读取用户指定项目范围内已有的入口、Spec、ADR/Notes、任务及参考资料。可以兼容 Trellis，但不能只兼容 Trellis。先只读盘点，不执行旧脚本，不扫描用户其他项目和全量会话。

必须对每项来源给出处理结论：已接入、保留为历史、待核实冲突、明确忽略、读取失败。计数与原始来源应可对账。读取失败不能伪装成“项目没有规范”。

已有明确的项目规范可按其原有身份继承，并标注“继承基线、来源、版本”；不要求用户逐篇重新批准。继承规范不等于声称已验证代码完全遵守它。来源矛盾、规则失效或正文混杂的部分单独标记，只影响相关任务范围。

无历史规范的项目建立最小流程边界和资料索引；从源码推导的规则标记为候选，不编造产品目标或将推测称为现行契约。允许先做只读调研来补齐。

### INIT-2 能用、能看、能追溯

接入完成后必须同时满足：看板能打开规范正文；任务能引用它；Agent 能获取同一来源及版本。不能出现只复制文件、只写数据库计数、只生成空页面中的任意一种“半接入”。

在已激活范围中明确唯一规范来源；索引和看板是投影，不建立另一套可任意修改的规范副本。旧目录保留只读历史或暂时作为明确配置的来源，切换后不长期双写。

项目就绪状态至少区分：资料可浏览、任务可执行、某项能力缺失、迁移冲突待处理。CLI 连接正常不等于工程流程全部就绪。

### INIT-3 安装入口而不是安装空壳

安装提供：短宿主入口、工作流程 Skill、节点所需规则引用、实际可运行的命令说明和恢复方式。重装不覆盖用户修改，不重复注入。

通过新会话测试宿主能发现入口、读取任务相关规范并提交真实结果。只把 SKILL.md 放进目录不是接入验收。

## 5. W1：界定工作

**输入：** 用户要求、已分配工作项或已授权队列中的下一项；也可以是已登记的反馈。

**Agent 必须：**
1. 核对 W0 的分流结论；普通讨论、查询和审阅材料直接处理，不因为产物落盘或工作持续时间而自动创建任务。
2. 优先关联已有工作项，保留用户原始目标；明确范围、非目标、交付对象、验收条件和可执行权限。
3. 明确交付目标：分析结论、验证报告、验证通过的改动、合并或指定环境发布。目标不能在结束时偷偷降低。
4. 读取已有输入，能够自行核实的先核实；只对确实影响正确性或权限的未知事项请求确认，不重复问已回答的问题。
5. 判断是否有前置依赖、已有执行者或不安全的共享写工作区。

**最低产物：** 可引用的任务目标、完成条件、范围与下一动作。
**退出：** 目标明确则继续 W2；需要实质决定则待确认；依赖缺失则待处理并标明恢复条件。

## 6. W2：依据规范分析并确定路径

**输入：** 工作定义、相关代码/资料、项目规范与历史决策。

**Agent 必须：**
1. 获取项目级关键约束，再按影响模块、路径和问题检索相关 Spec、决策、被否方案；需要时展开原文。
2. 为本次工作保留“适用规范清单”：来源、版本、适用理由。不能仅写“已阅读规范”。提供了上下文不代表已证明遵守。
3. 核实当前实现/事实，区分现状、计划、假设和历史。发现冲突必须记录，不擅自以代码、最新文件时间或模型判断替代现行规则。
4. 形成最小充分方案、工作分解与检查计划。为每条验收条件确定检查方式、所需能力和证据；不能把所有条件复制给每个检查器。
5. 判断是否需要新决策：关键架构、跨模块契约、重要行为或非显然取舍需要记录；局部明确修复不强制立新 Note。
6. 选择实际步骤，说明复用和不适用的部分。已有充分分析直接复用，不为了模板重述一次。

**最低产物：** 适用规范、执行计划、验收覆盖关系、必要的决策记录。
**退出：** 方案在授权内则继续 W3；改变关键边界或权限时才进入准确版本的确认。

常见裁剪方式：

| 工作 | 必需工作 | 不默认要求 |
|---|---|---|
| 小型后端 Bug | 界定故障、相关规范、定位修复、回归、交付总结 | 独立需求 Agent、UI/UX、长篇方案 |
| 一般功能 | 范围分析、实施、相关检查、文档同步 | 所有检查类型和生产发布 |
| UI/交互修改 | 设计依据、实际页面、相关视觉/交互及功能检查 | 与改动无关的全套验收 |
| 明确要求使用 AEL 只验收现有成果 | 确认受检对象、执行检查、报告与缺陷登记 | 修改业务代码、发布 |
| 明确要求使用 AEL 的调研/根因分析 | 证据收集、结论复核、限制说明 | 代码修改、部署 |
| 架构/数据变更 | 方案取舍、兼容与迁移风险、必要授权、充分检查 | 无依据的自动放行 |

Fast/Standard/Strict/Research 可保留为计划预设，但真实任务范围和风险决定所需责任，不由模板名称代替判断。

对只验收任务，W3 就是执行检查，W4 负责复核覆盖、证据与汇总结论，不为凑流程重新运行同一套检查。对调研任务，W4 复核结论依据与限制，不强制另外启动审查 Agent。

## 7. W3：执行实际工作并持续留下进展

**Agent 必须：**
1. 在已明确的工作区、任务和执行单元内工作，完成当前负责内容；一个逻辑步骤可包含多次工具使用，不为每个命令创建新 Agent。
2. 读取适用规范再修改，新增影响范围时补读相关规范。不能先做完再给结果补挂几篇 Spec 冒充受规范约束。
3. 按实际完成的工作更新进展：做了什么、产物在哪里、产生什么发现、接下来是什么。不记录无依据的百分比。
4. 新问题先分类：本范围内可修复问题继续处理；范围外问题登记关联反馈；影响方案或边界的返回 W2。
5. 完成当前单元时提交产物、结果、剩余问题和下一动作。提交日志/证据不是修改任务目标。
6. 单次完成的代码任务，在实现和必要的提交前检查完成后，直接创建只包含本任务改动的 Git commit。保留无关和其他执行者的改动，遵守项目提交钩子；不能安全区分改动或提交失败时如实报告原因。提交不意味着推送、合并或发布。

Git commit 会改变 HEAD，也会改变 AEL 的候选指纹。单次代码任务应先完成上述 commit，再提交实施结果生成候选，并对提交后的候选执行正式验收；验收后若修正代码并产生新提交，须重新生成候选，并对新候选重新执行全部必要检查。

**最低产物：** 实际代码、文档、设计、调研或验证操作结果，以及简短的事实摘要和引用。
**退出：** 获得可检验产物则进入 W4；真正阻塞时保存现场。单角色交接仅结束本执行者职责，不宣告父任务完成。

## 8. W4：验证结果并决定回路

验证必须同时考虑“实现是否工作”和“是否符合任务及相关项目约束”，但不能把模型判断包装成绝对证明。

每个检查至少关联：验收条件、受检版本/输入、检查方式、实际执行者、结果、证据、失败或阻塞原因。

| 方式 | 合法依据 |
|---|---|
| 自动化命令 | 实际执行、结果、日志及受检对象；退出码 0 不独立证明覆盖完整 |
| 浏览器/场景操作 | 实际页面和步骤、结果、必要截图或记录 |
| Agent 语义审查 | 读过的具体输入、发现与理由、判断来源；明确它是模型审查 |
| 人工裁定/授权 | 指定人员对具体问题和版本的明确决定 |

需要判断不等于必须人工。UI/UX/功能验收可由具备能力的 Agent 执行；无能力时是缺少执行条件，不是偷偷变成人工填表。

检查状态至少明确区分通过、失败、未执行、环境阻塞、不适用、经授权豁免。后两者须说明适用范围和理由，不能用于掩盖失败。

### W4-LOOP 结果路由

| 结果 | 必须采取的动作 |
|---|---|
| 范围内实现问题，且任务允许修改 | 生成具体失败反馈 → 返回 W3 修复 → 对有效候选重新验证 |
| 需求、方案或契约冲突 | 返回 W1/W2 修订相应部分，按影响失效计划/证据；必要时确认 |
| 缺环境、依赖或执行能力 | 保存证据与恢复条件，待处理；不能算通过，也不笼统要求用户批准 |
| 只验收任务发现缺陷 | 记录失败及证据，按授权建立关联缺陷；不越权修改业务 |
| 检查全部满足交付要求 | 进入 W5，不只返回“提交成功” |
| 重复失败或预算耗尽 | 保存已尝试措施、最新证据与具体阻塞，停止当前自动重试 |

默认同一类失败最多连续尝试三轮，项目可修改预算。重试必须基于新增操作或证据；不得重复生成相同报告来延长 Loop。

“检查全部执行完”与“候选全部验收通过”必须独立表示。交付目标为验证报告时，可交付明确的不通过报告；交付目标为 verified 改动时，失败检查不能被报告完成抵消。

## 9. W5：收敛、交付、知识回写

**Agent 必须：**
1. 核对验收条件覆盖、最终候选和有效结果；没有证据的部分保持未验证，不用自述补齐。
2. 同步受影响的 Spec 与 Decision：有变动就更新，没有就记录无需变更的简短理由。重要否决或踩坑结论关联到相应知识；常规过程留在任务中，不大量制造永久规范。
3. 关键契约变更先按授权达成决定，再将实现与契约放在同一候选中验证。收尾修改若影响受检输入，需要重验；运行日志等明确排除项不应使代码证据无故失效。
4. 按约定完成交付；只有要求合并/发布的任务才执行对应动作。实际发布必须有目标环境、版本/制品和真实结果，触发流水线不等于发布成功。
5. 形成结果摘要：交付内容、验收结果、限制、关联规范/决策变化、后续反馈。保留失败历史，不重写成从未出错。

**退出：** 满足原定交付目标才能完成；纯交付故障留在交付处理，代码故障回 W3，授权缺失则准确待确认。

完成后只继续用户已经授权的后续任务或队列。没有下一项授权工作就停止/空闲，不为保持“持续进化”发明新产品需求。

## 10. FEEDBACK：下一轮输入

反馈记录来源、对应交付/版本、现象或建议。先去重并判断归属：执行中的同范围问题回到原任务；已结束任务的新缺陷/需求通常创建关联新任务，保留原历史。

明确违反既有契约的 Bug 可复用有效分析走短路径；目标或设计变更进入 W2。反馈收集不意味着自动获准开发或发布，是否自动进入队列遵守项目授权。

本规范不建立独立“项目自治规划 Agent”，项目演进通过每轮真实工作、规范变化、决策与反馈持续积累。

## 11. 单 Agent、多 Agent 与恢复遵守同一协议

- 单 Agent：在预算与权限内连续完成当前授权任务，不在每个逻辑步骤询问是否继续，不强制切会话。
- 多 Agent：领取当前单元 → 获取输入/规范 → 工作 → 提交结果/证据 → 结束当前职责。后续由已有运行器、下一执行者领取或当前宿主继续承接。
- 可并行的是无冲突的执行单元；共享可写工作区、测试账号或业务状态时需隔离或串行。只隔离 Git worktree 不代表业务数据已隔离。
- 每次提交必须得到明确下一动作：继续、交接、等待环境/依赖、等待确认、回退、完成或取消。待接手项必须可发现、可领取。
- 没有执行者时如实显示等待接手。没有存活进程或调度器时不宣称后台持续执行。
- 恢复读取任务定义、适用规范、最后有效结果、受检版本和下一动作；不全量重读历史，更不重做已满足的步骤。
- 同一任务保留必要的领取保护、幂等、过期提交拒绝及旧执行者恢复检查；不同任务不会因共享工作区而被 AEL 排他阻挡。

## 12. 修订与审批的精确边界

| 变化 | 流程响应 |
|---|---|
| 标题、排版、非语义链接补充 | 更新展示，不无故使实现/检查失效 |
| 新执行摘要、证据、状态结果 | 记录执行结果，不改任务定义版本 |
| 扩展受检范围、改变验收条件、实施方案 | 评估受影响步骤和证据，产生必要修订；不一律重跑所有阶段 |
| 降低必要门禁、扩大权限、改变关键契约 | 按项目政策请求准确问题和版本的批准 |
| 无法证明旧可写进程已停止 | 展示具体执行与风险，暂停该任务的接管；其他任务并行时自行协调共享文件和资源 |

不确定影响时可以保守重验，但应说明原因。审批有效性绑定其语义范围和版本；无关显示变化不应导致反复批准。

普通测试失败不是审批问题；普通任务结束也不默认需要用户手工确认。

## 13. 过程、进度、卡点的记录协议

在开始工作、完成工作单元、得到检查结果、发现阻塞、调整计划、交接和结束时更新记录。不要求逐 token 或每条工具调用记账。

每条重要进展至少能还原：时间、执行者、步骤、已经发生的事实、对应产物/证据、对计划的影响、下一动作。自动程序可生成确定性摘要；Agent 的描述只能来自实际操作。

进度分开显示“工作项完成情况”与“验收项结果”。如 3/5 项检查通过是检查覆盖信息，不冒充总研发进度 60%。不得以耗时、事件数、文档行数推算完成度。

卡点必须给出：类别、具体原因、受影响范围、已尝试措施、谁或什么条件能解除、解除后恢复位置。多 Agent 的纯交接等待与技术故障、人工决策分别展示。

## 14. 看板是流程可见性的一部分

本轮不调整配色、字体、装饰和动效，但必须把真实流程呈现出来。

### 14.1 五个工作台板块

| 板块 | 判定 |
|---|---|
| 正在推进 | 存在有效执行；显示实际工作、执行者、最新结果和进度 |
| 待处理 | 待整理、已就绪、待接手、依赖/环境阻塞或主动暂缓；显示下一步与恢复条件 |
| 待确认 | 存在阻断继续的真实决策；显示具体问题、影响、选项、确认对象与版本 |
| 最近完成 | 达到原定交付目标；区分报告交付、验证通过、合并、发布及历史导入 |
| 已取消 | 保留取消原因、已有成果与替代关系；运行中的取消需安全结束执行 |

同一任务只属于一个主板块，内部检查可以有不同状态。子执行者完成不能直接把整个任务移到完成。

### 14.2 任务详情必须回答六个问题

1. 做什么，按哪些规范和参考依据做？
2. 计划如何走，哪些步骤复用或不适用，为什么？
3. 谁正在处理什么，已实际完成什么？
4. 哪些验收条件通过、失败或未运行，证据是什么？
5. 卡在哪里，需要谁做什么，之后回到哪里？
6. 最终交付了什么，改了哪些规范/决策，后续反馈在哪里？

默认展示真实业务进展；claimed/process_started/submitted 等原始事件折叠进技术详情。不能用漂亮文字掩盖没有执行产物。

### 14.3 工程知识与演进

必须展示现行规范、决策、否决理由与历史关系，支持原文、来源、版本、适用范围、关联任务和关联结果。规范页面为空时明确区分未配置、确实为空、未索引、冲突和读取失败，不能只给空白列表。

任务可跳到所用规范；规范可回看哪些任务引用和改变它；决策可追到方案、修改及检查结果。时间线展示真实的这些变化，而不是单纯收集底层状态事件。

看板与 Agent 使用同一权威数据，不独立维护第二套状态。数据库/索引/界面不一致必须可诊断，不能回退样例数据。

## 15. 程序和 Skill 的分工

| 部分 | 必须承担 |
|---|---|
| 短宿主入口 | 识别当前项目、说明何时启动工作协议、提供真实 Skill/命令入口 |
| 工作 Skill | 按 W1—W5 执行；按需读规范；消费下一动作；保持循环或准确交接 |
| 程序 | 持久化、引用检查、同任务领取保护、版本与证据校验、下一动作判定、可查询结果 |
| 看板 | 同步展示上述事实与必要决策入口，不让用户手工扮演状态机 |

只写 Skill 不能保证结果真实；只有机械门禁又不能代替理解需求。两者必须贯通。

规范中涉及的能力应映射到现有真实 API/CLI。未实现能力明确报错，不能让 Agent 直接改数据库、伪造事件或靠猜测命令绕过。具体命令名由实现统一维护，流程正文不复制多套会漂移的指令。

## 16. 独立合规验收，不使用业务项目反推规则

在专用测试工程中验证下列场景；可针对现有数据做只读核查，但不以某个历史任务是否能“点完”作为通过标准。

| 编号 | 场景 | 必须证明 |
|---|---|---|
| T01 | 有既有规范和历史决策的项目接入 | 来源对账；规范可读、可引用、可加载；历史不冒充现行 |
| T02 | 单 Agent 修复一个有回归用例的后端 Bug | 按规范工作；真实失败与修复；不引入 UI/UX；结果与看板同步 |
| T03 | 普通功能任务 | 分析、方案、实现、验收、必要规范更新形成证据链；无需每步人工批准 |
| T04 | 只验收任务发现问题 | 报告真实失败、建立关联缺陷；业务源码未被越权修改 |
| T05 | 关键契约变更 | 真实问题及差异可审批；旧决定保留；批准后继续正确步骤 |
| T06 | 多执行者交接及独立任务并行 | 前一执行者提交即可结束职责；下一项可领取；结果不串任务/版本 |
| T07 | 环境缺失、进程中断与恢复 | 卡点具体；不伪装通过；恢复不重做仍有效步骤或重复有副作用动作 |
| T08 | 普通结果记录与真正定义修订 | 提交进展不退回 define；实质变更影响正确检查；无关编辑不反复审批 |
| T09 | 场景/语义审查 | 实际能力与证据；不是统一人工按钮；无能力时如实阻塞 |
| T10 | 按需交付及后续反馈 | 非发布任务不强迫发布；发布有回执；反馈进入关联新轮次，历史不篡改 |
| T11 | 无规范、索引损坏与加载失败 | 各情况可区分；缺关键依据不能静默继续；不制造虚假规范 |
| T12 | 新会话入口与卸载/回滚边界 | 能恢复到正确工作；旧资料和用户配置保留；不影响无关业务代码与服务 |
| T13 | 普通讨论、功能定位、只读分析或仅供审核的材料 | 新会话先判断目的并直接处理；无论材料是否保存为文件，都不自动运行 AEL 命令、创建任务或进入验收；不受过期来源索引阻断 |
| T14 | 项目迭代、修复及明确请求的 AEL 操作 | 工程变更在首次修改前进入流程；明确的单项 AEL 操作只执行所请求操作；已有任务按明确要求恢复 |

状态机单测可以用明确标注的模拟执行器；完整 Agent 兼容验收必须有真实宿主运行。没有可用宿主/环境时标记未验证，不用模拟通过代替。

## 17. 完成定义与参考

符合本规范的完成标准：**新会话中的 Agent 能接到工作、读到适用规范、持续处理并按结果回退或交接；人不翻原始日志即可看懂依据、过程、结果、卡点和下一步。**
