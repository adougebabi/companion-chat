## 4. New task dispatch/version/worker composition options (no selected design)

- Old `Dispatcher.DispatchOnce` at workflow.go:2006 queries **all** platform_workflow_intents pending/retry (2029), no supported-type allowlist or task queue filter. New queue alone does not isolate rows from old dispatcher. It decodes old `Input` before route switch (2065); malformed/non-object JSON can be failed at 2069 even for unknown type. Unknown *well-formed* type ends in default **2182–2185**, leaving pending but consuming query/fairness slots. It does not claim or ExecuteWorkflow unknown types, but repeatedly sees them.
- Old `ReconcileOnce` query constant workflow.go:**48** also includes all pending/retry/started/cancel_requested, so sharing platform table with new queue is not a durable isolation boundary. Separate continuation task table + its own dispatcher is a available seam: old SQL cannot see it; queue separates pollers. Alternatively broad platform table requires upgraded dispatch/reconcile allowlists and rollout accounting; cannot rely on unknown-route logging.
- `workflow/workflow.go:1170` `StartWorkers`: fixed queues at 1174; **1196–1204** every worker UseVersioning true with deployment `fluctlight`, build ID `WorkerDeploymentBuildID()` (133; environment TEMPORAL_WORKER_BUILD_ID, default platform-v1) and **AutoUpgrade** behavior. New continuation queue/register functions can be added here; actual current-version bootstrap is `cmd/worker/main.go:116–126`. AutoUpgrade/versioned worker does not by itself ensure a new task is pinned to only compatible workflow implementation.
- Interaction registration at **1257–1263** owns CognitionProcessingWorkflow/ProcessCognitionActivity; media registration 1254–1256 owns MediaWorkflow/ProcessMediaActivity. New dedicated queue and workflow/activity names are available composition options without changing old workflow history.
- `workflow/workflow.go:87` `ApplicationService` narrow activity interface; runtime Configure at 122 uses it; `ProcessCognitionActivity` at 858 / media activity 887 show domain call wrappers. New resume method can be injected through this seam and corresponding App method rather than opening HTTP/user turn.
- `cmd/worker/main.go:55` Configure(application), **80** SetWorkflowRuntime, 116 StartWorkers, **135** Dispatcher construction, **241/247** bounded dispatch/reconcile ticks are real running composition entry points. A separate continuation dispatcher can be composed on same main tick or own timer; startup repair needs its own durable rows.
- `core/workflow_runtime.go:11` WorkflowRuntime is management interface (List/Status/History/Signal/Cancel/Terminate/Reset/**Restart**); no generic typed Start. WorkflowStart at 41 has WorkflowID/TaskQueue/IntentType/Payload.
- `workflow/runtime.go:233` TemporalRuntime.Restart validates queue/identity, resolves `workflowFunction` at 269, decodes legacy Input, starts with ALLOW_DUPLICATE and 30-min timeout. workflowFunction only supports existing enum, unknown continuation errors (306). Reusing Restart requires explicit registration/type shape semantics; it is a management restart API, not existing durable continuation outbox.
- `workflow/workflow.go:1997` workflowStartOptions uses reuse policy function (1965+), ExecuteWorkflow at 2188; new intent falls to REJECT_DUPLICATE (1994). New continuation task identity should independently account for dependency revision/retries rather than borrowing original user idempotency or ALLOW_DUPLICATE management behavior without durable deduplication.
