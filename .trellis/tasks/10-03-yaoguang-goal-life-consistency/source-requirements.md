# 摇光：目标驱动生活与事实一致性修复实施任务

## 执行要求

请在当前仓库中实际完成代码、必要的数据迁移、测试和诊断修复，不要只输出设计建议或盘点报告。先定位真实入口与现有实现，再按下列任务实施；既有能力已经存在时修复接线和语义，不要重复建设。

本轮的业务主线明确为：

> 摇光发现缺少某件服装或物品 → 通过 Tool 建立购买需求/目标 → 根据目标安排未来日程，或合法调整当前/下一时间段 → 日程实际执行、进入购物情境 → 调用购买入库 Tool，提交获取事件并产生库存物品 ID → 后续通过独立的穿着/使用操作使用该物品。

购买前没有库存 ID 是正常情况。禁止“必须先有库存 ID 才能购买”，也禁止“找不到库存 ID，就直接把物品写进当前着装或生图提示词”。

这里的购买按项目已有角色生活世界内的业务行为实现，不默认接入真实电商、真实支付或物流。本轮不是建设商城、商品供应链或通用世界模拟引擎。

### 必须保持的边界

- 复用现有 Eino/ADK 原生 Agent Loop、正式 Agent/Task、插件化 Tool、Prompt/Slot、领域服务和持久化机制。不得另建 Agent Loop、工具调度平台或通用工作流引擎。
- 每个 Tool 仍然能脱离 Agent 独立执行；独立执行也必须经过同一套领域校验、权限检查和真实持久化。不得把关键校验仅放在 Main、某个 Agent 或提示词中。
- 保留现有事务、幂等、事件和发布机制；仅补齐本轮操作所需的原子性与恢复，不做全局事务框架重构。
- 最终仅保留一条正式生效路径。删除被替代的旧注入、旧兜底、重复状态写入和兼容分支；一次性历史迁移不等于保留双轨运行。
- 禁止解析自然语言正文或 reasoning 来伪造 Tool 执行；`accepted`、`completed`、`failed` 等必须表达真实业务状态。
- 不得以“加强提示词”替代事实有效性、库存、时间、睡眠、幂等或状态写入的程序校验。
- 下文的字段和工具名称表达契约语义，不要求机械照搬名称、另建表或增加同名工具。先映射现有代码，只有确实缺失才做最小新增。
- 修复应同时覆盖聊天、Wake-up、反思、日程执行、购买、换装、图片生成和后台诊断的相关正式入口，不得只修一条演示路径。

## 已观察到的问题与证据边界

用户测试观察：目标写入人格后缺少真实推进；用户在国外的纠正后续失效；Wake-up 提示词接近两万字符，其中大量为聊天原文；睡眠期定时检查不断产生“醒了”的发言；工作地点与聊天叙述不一致；诊断中心旧错误排在新运行前；不存在于库存和当前着装的服装最终进入了生图。

提示词样本还显示：错误的“同楼等待”推断与“用户在国外”的纠正同时召回；大量相似“夜间自然醒来”的 developing_self；重复喝水、开灯、光线和毛衣颜色的主动消息；定时输入却标记 `current_speaker=actor_user`；部分摘要正文与元数据时间相差八小时。

这些是需要复现的症状，不是已经确定的代码根因。尤其用户没有提供购买 Tool 的完整返回，必须沿真实 trace 检查，不能直接断言购买、入库、换装或渲染中的某一层已经成功或失败。

## T01：统一时间格式、时区与时间语义

### 1. 统一表示，不统一双方的本地钟点

所有表达“某个确定时刻”的系统输出统一使用 RFC 3339 兼容的带数字偏移格式，固定输出毫秒：

```text
2026-10-03T11:26:18.000+00:00
2026-10-03T19:26:18.000+08:00
```

上面是同一时刻的两种时区投影，不是两个事件。项目规范输出统一使用数字偏移，不混用空格日期、CST、裸时间和 Z；标准输入中的 Z 可以正常解析，但在边界处统一输出为 +00:00。Z 本身表示 UTC 零偏移，并不表示缺失时区。[R1]

- [ ] 系统 API、Tool 结果和结构化运行日志中的瞬时时间统一序列化为 UTC 的上述格式。
- [ ] LLM 运行视图中的事件时间统一投影到本次明确指定的参考时区，默认 actor_self 的时区，保持相同格式。不要同一段聊天历史一条 UTC、一条本地裸时间。
- [ ] 在运行视图顶部明确 `reference_timezone`、`actor_self` 的当前本地时间，以及在已确认时的 `actor_user` 当前本地时间。历史消息按参考时区显示时，要明确“时间显示时区不代表发送者所在地”。
- [ ] 只统一机器字段、系统生成的元数据和格式化入口；不要改写用户原话，也不要强迫自然语言聊天每句话都带时间戳。
- [ ] 纯日期、重复日程的本地钟点、持续时长是不同类型，不强行把生日或“每天 08:00”伪造为某个 UTC 瞬时。日程实例落地时再得到带时区的起止时刻。

### 2. 时区与存储

- [ ] Actor 的时区使用明确的 IANA 名称，例如 `Asia/Shanghai`；用户时区未确认时保持 unknown/null，不从“在国外”、浏览器、服务器或另一 Actor 的时区自动猜测。
- [ ] 用户以后明确提供所在地/时区后，更新带生效时间的事实；“在国外”本身不提供具体时差。
- [ ] 偏移量由时区与日期计算，不能把某地永久写死为 -08:00。重复日程需保留本地钟点和时区，并定义夏令时缺失/重复钟点的处理策略及测试。[R2]
- [ ] 检查现有数据库瞬时时间类型。使用 PostgreSQL 时，瞬时优先复用/迁移为 `timestamptz`；原始时区名仍需单独保存，因为该类型内部保存 UTC，不保留输入时区名。不要为了统一展示而把时间列改成字符串。[R2]
- [ ] 数据库已有更高精度时不必丢失；排序和分页游标使用真实字段精度及唯一键，不依赖截为毫秒的展示字符串。

### 3. 统一“现在”与历史迁移

- [ ] 业务时间通过可注入 Clock 获取，用于日程生效、睡眠、购买执行和目标复盘；测试可以推进虚拟时间，不等待真实数小时。
- [ ] 真实运行审计时间与模拟业务发生时间分开。不能把回放的业务时间当成诊断列表的新运行时间。
- [ ] 一次上下文投影标记明确 `as_of`；耗时工具实际提交前重新校验必要的当前时间、状态版本和权限，避免跨日程边界后继续用旧状态执行。
- [ ] 区分 `occurred_at`、`created_at`、`effective_at`、`expires_at`、日程起止。不得用模型总结生成时间代替事件发生时间。
- [ ] 旧数据只在来源时区明确时转换；有八小时偏差不代表可以全库统一加减八小时。来源不明的裸时间保留原值并标记待核查，不伪造精确时间。

### 验收

同一时刻经数据库、API、Tool、Prompt、前端往返不漂移；异地双方不被强行同步；跨午夜与夏令时测试通过；不能继续在系统生成的同类时间字段中混用裸时间、CST 与不同格式。

## T02：Actor 背景、事实纠错与记忆有效性

### 1. 小背景常驻，细节按需查询

- [ ] 复用现有 Actor 数据，提供轻量背景投影；关键事实少量常驻，详细信息使用现有或最小新增的 Actor 查询 Tool。
- [ ] 本次回归夹具的常驻信息至少能够表达：双方异地；用户明确说过在国外；具体所在地/时区未知；没有已确认的线下见面安排。
- [ ] 显式初始化设定和用户自己的明确陈述保留来源；当前所在地带有效时间，不固化成不可变人格。
- [ ] 人物事实按 `actor_id` 隔离。群聊、其他 Fluctlight、引用消息和工具回传不能都混入 actor_user。

### 2. 纠正必须使错误断言退出当前事实

- [ ] 实现或补齐事实粒度的修正：主体、属性/断言、值、来源、有效时间、状态、被替代/纠正关系。优先复用已有结构，不建设通用知识图谱。
- [ ] 区分“之前就是误判”与“之前真实、后来状态改变”。不能简单以最后写入时间覆盖所有历史。
- [ ] “用户说想见你”可以保留；从中推出“用户就在同楼”不能继续作为事实。“用户在国外”这条纠正生效后，同时间范围内的同楼/送豆浆/已约出门等无证据断言应失效。
- [ ] 修正后同步影响运行背景、召回、常驻记忆、摘要、developing_self 和相关缓存；无需整库扫描时，利用已有来源引用定位派生内容。
- [ ] 保留原始聊天和审计。对失效记忆，正常召回不得作为事实返回；必要的历史查询应明确返回“当时的误解及其纠正”。

### 3. 证据与主体归属

- [ ] `verified` 若只表示来源可追溯，必须与“内容已证实”明确区分，不能用高置信度将 inference 升格为事实。
- [ ] 摘要/反思反复引用同一次模型自述，不构成多份独立证据；引用应能回到原始消息、初始化来源或真实成功事件。
- [ ] Tool 失败、购物计划、未提交动作、图片结果和角色单方面叙述，不能被抽取为已完成生活事件。
- [ ] 计划、推断和创作细节允许作为这些类别存在，但不得污染用户位置、库存、当前穿着、实际行程或关系确认。
- [ ] 权威字段按领域解析：人格约束行为风格；已生效领域状态决定当前地点/穿着；用户明确纠正决定其自述事实。去掉对所有字段一刀切的 `core_persona > developing_self > current_state` 规则。

### 验收

用户纠正后，经过多轮聊天、增量总结、反思、重启和记忆召回，旧错误仍不可重新成为当前事实。可追溯地保留正确互动，不通过删除整段历史掩盖错误。

## T03：周期检查不等于角色醒来，日程不等于已执行

### 1. 区分系统触发与用户消息

- [ ] 定时触发以系统事件表达，区分 `trigger_source`、`target_actor`、真正发送者和实际新入站消息。目标是 actor_user，不代表 actor_user 刚说了话。
- [ ] 对没有真人新消息的周期，不伪造 `current_speaker=actor_user` 或新的人类交互。
- [ ] 为 Wake-up 提供简短的最近入站时间、最近主动发送、连续未获回应次数、已表达主题和当前是否有新事件。

### 2. 睡眠与行为权限

- [ ] 周期开始先处理合法到期日程/事件，再计算当前有效生活状态。
- [ ] 当前仍在睡眠且没有获准打断事件时，跳过自主社交/外出决策，记录正常的静默原因；不生成“醒了一下又睡回去”的生活事件。
- [ ] 后台摘要或记忆维护可以运行，但不改变角色睡眠状态，不记为生理觉醒。
- [ ] 发送消息、购物/外出等相关 Tool 在领域层复核当前权限和状态；不要另建一套 Main 工具名分支或通用门禁引擎。
- [ ] 用户真实来消息的处理沿用项目既有打扰策略；不能把“永远不回”或“任何消息都强制起床”作为隐含新规则。

### 3. 日程与有效状态

- [ ] 区分日程获准、尚未开始、正在执行、完成、中断/改期。获准不能直接表述成已到达、已买到、已穿上。
- [ ] 明确唯一当前状态来源，场景与活动变化通过现有合法执行事件更新。聊天/摘要只读取，不能靠叙述覆盖。
- [ ] 支持根据目标修改当前剩余时间或下一个时间段；校验已有任务、不可打断活动、必要耗时和安排冲突。冲突时返回可理解结果供 Agent 改期，不能静默吞掉原计划。
- [ ] 只有合法执行到该阶段才能切换到购物状态。计划安排在明天，不能在同一轮里直接声称明天已经执行完。
- [ ] 已在商店且条件满足时，允许当前合法时间段内继续购买，不必机械增加等待周期。
- [ ] 工作状态允许符合既有规则的聊天/休息，但不能仅因一句“我在书房”变成已回家。

### 4. 主动表达去重复

- [ ] 自己发出的“灯变了、喝水了吗、不用回”不作为下一次联系的新用户事件。
- [ ] 无新事实、无新目的时允许静默；对重复主题和连续未回复的主动消息实行可配置的冷却/抑制。
- [ ] 不将静默等同于失去主动性：真实新事件、到期承诺或合适的目标机会仍可触发联系；不以固定“每日消息数量”代表关系推进。

### 验收

睡眠期间多次周期检查不会改变角色为清醒，不形成自然醒习惯；合法起床仍正常执行。日程修改、到达、购物和状态变化可在事件与持久化中逐项追溯。

## T04：目标进入运行状态，并形成行动—结果—复盘闭环

### 1. 共享目标状态

- [ ] 目标不仅存在于人格长文：初始化可提取/登记，后续可通过正式 Tool 创建、更新、暂停和完成；已有目标模型优先复用。
- [ ] 至少能表达目标意图、当前阶段、最近实际尝试、结果证据、下一步、阻碍、复盘时机及生命周期状态。避免只有一个没有含义的进度百分比。
- [ ] 聊天、Wake-up、反思和日程消费同一份持久目标；重启/摘要不丢失，不能各自维护一份互相不同的推进状态。
- [ ] 运行时只投影当前相关的少量活跃目标和下一步，完整历史按需查阅；不能再把所有目标日志常驻。

### 2. 主动推进而非僵硬剧本

- [ ] 角色可创造低压力机会，不必等待用户主动发话；人格克制约束表达方式，不等于无限等待。
- [ ] 将“发动态 → 挑款 → 深夜倾诉 → 明确托底 → 告白”从强制前置流程改为可能策略，不把它写成唯一状态机。
- [ ] 恋爱目标用作回归案例而非写死业务分支：用户谈到想找女朋友时，应在上下文允许时考虑自身关系意愿，不总退回无关的生活指导。
- [ ] 目标不能因情绪平静或驱动压力为零就自动停止；同样不能每一轮强制推进、告白或发消息。
- [ ] 购买目标接入同一目标机制，但有独立领域完成条件；不得为购物再建第二套独立目标系统。

### 3. 复盘与负反馈

- [ ] 反思基于原始机会/行动/结果，区分真实推进、做出尝试待回应、合理等待、错失机会、受阻、完成或放弃。
- [ ] 发送成功只能证明表达已送达，不证明关系已推进；对方的意愿只能来自对方回应。
- [ ] 多次无效策略或错失合适机会，应形成有证据的调整和新的可行下一步，而不是再次写“以后更主动”。
- [ ] 不另建惩罚/痛苦系统，不惩罚睡眠、工作约束、明确拒绝或正常等待；不靠提高焦虑驱动行动。
- [ ] 严格禁止把刷消息、自我评价或总结“我进步了”计为成果；明确拒绝不得作为需要惩罚或突破的阻碍。

### 验收

至少用“关系探索”和“购买物品”两类目标验证：目标能创建、进入下一次运行、产生行动、消费真实结果并复盘。关系目标评价行为语义，不固定台词，也不要求每次测试都立刻表白。

## T05：缺少物品 → 购买目标 → 日程 → 购买入库

### 1. 购买前无需库存 ID

- [ ] 库存查询准确区分未持有、查询失败、权限失败和模糊匹配；不能把查询服务失败当作确定没有。
- [ ] 确认缺少物品后，Agent 可以用描述性需求创建购买目标，例如“黑色短靴、低跟、适合通勤”；此时不要求 `inventory_item_id`。
- [ ] 商店候选/商品规格、购买需求、库存实例是不同对象。有商品目录时复用其标识，但不能拿商品 ID 冒充自己持有的库存 ID；没有商品目录不为本轮新增完整目录平台。
- [ ] 想要不等于必须购买。Agent 可选择购买、延期或放弃；一旦选择购买，应持久化目标并进入后续安排，而不是停留于台词。
- [ ] 重复周期针对同一尚未完成需求应复用/更新目标，避免每轮新增购买目标和购物日程。补购、不同规格和数量变化按现有业务语义区分，不能一律按名称去重。

### 2. 目标确实驱动日程

- [ ] 正式工具能力必须覆盖“建立购买需求/目标”和“安排/调整日程”；可以复用通用目标及日程 Tool，不强制拆出多个新工具。
- [ ] 目标与日程建立可追踪关联，日程中保留购买意图及所需条件，不提前附加虚构库存 ID。
- [ ] 支持未来空闲时间安排，也支持在权限和条件允许时修改当前剩余/下一时段，不能只有次日计划一种路径。
- [ ] 日程提交失败时目标仍保留为待安排/受阻；日程取消或改期要反映到目标，不能产生“目标已完成但购物从未执行”。
- [ ] 重启和重复触发后仍可在合法时间继续，且不会重新安排多个同义购物任务。

### 3. 购买入库的真实提交

- [ ] 到达已生效购物阶段且相关前置条件满足后，由正式购买入库 Tool 完成角色世界内的获取操作。
- [ ] 该 Tool 接受合法购买需求/规格及由运行上下文提供的目标、执行实例等依据。不能信任 LLM 自填的 `purchased=true`、伪造回执或自由文本“我已经到了”。
- [ ] 商店/获取事件可以在项目角色世界中被合法创建，不要求真实线下小票；但“角色世界内的成功”必须由领域服务验证并持久提交，不能等同于模型说成功。
- [ ] 购买事件与库存新增尽量在现有同一事务中提交：生成获取事件、真实库存 ID、物品属性与来源，并关联目标。不得先返回 completed 再后台尝试写库存。
- [ ] 若现有实现确实将购买与入库拆开，必须显式表达中间状态和恢复；尚未入库时不能可用，不能假装原子成功。
- [ ] 返回的成功结果包含真实获取事件引用、库存 ID、已提交状态及必要的版本/时间；Agent 在原生 Loop 中消费真实结果，而不是自行补 ID。
- [ ] 单件和套装均支持。套装使用已有模型表示成员/部件；默认整体事务成功，已有合法部分成功语义则明确逐项返回，禁止部分成功被说成整套已拥有。
- [ ] 幂等键由目标/执行尝试等稳定业务标识支撑；同一次请求重试、网络超时后重试、重启恢复，不重复入库。不能只依赖每次会变的模型调用 ID。
- [ ] 需要写入库存的权限放在获取领域入口；不得给普通对话一个不校验来源、随意补物品的绕过路径。初始物品/管理员导入走明确受控来源。

### 4. 完成与失败边界

- [ ] 购买目标完成条件是相应物品获取入库成功，不是创建日程、到达商店、尝试调用、说已经买了或生成图片。
- [ ] 购买失败保留目标，允许重新安排、调整规格或停止；不能为了顺畅对话给出假的完成状态。
- [ ] 原生 Agent Loop 收到失败后仍可合理继续：查询、改期、说明受阻或静默，但不能照常穿上不存在物品。
- [ ] 未到未来安排时间不得在单次 Loop 中虚构时间推进，把整条生活链瞬间执行完。

### 验收主线

```text
库存没有黑色短靴
→ 查询确认未持有
→ 创建购买目标，只有需求描述，没有库存 ID
→ 安排/合法调整购物日程
→ 提前触发时仍未持有、不可穿着
→ 可控业务时钟到达购物执行阶段
→ 真实执行到可购买状态
→ 购买入库 Tool 成功，产生真实 item_id
→ 购买目标完成
→ 当前穿着仍保持购买前状态
→ 独立换装成功后，当前穿着才引用该 item_id
→ 此后“当前自拍”生图使用已提交的穿着
```

同一主线也应至少覆盖一件非服装物品，例如画笔或杯子，证明实现不是仅对服装名称打补丁。

## T06：持有、穿着/使用与图片生成分开

### 1. 持有不自动等于正在使用

- [ ] 购买入库不能顺带自动修改当前着装。换装/使用必须是独立、有条件校验和持久结果的领域操作；条件允许时可在同一 Agent Loop 中顺序调用，但仍是不同操作。
- [ ] 换装验证物品属于该 Actor、真实存在、可用、穿着槽位/组合合法以及当前场景权限。不存在、已失效或不属于该 Actor 的 ID 必须返回真实失败。
- [ ] 日常偏好、搭配模板、拥有物品、当前穿着分别存储/投影。设置常用搭配不自动等于此刻已换装。
- [ ] 使用非服装物品复用相同获取真实性约束，但不把所有物品硬塞成穿着槽位。
- [ ] 人格切换和重启不重置共享身体的实际衣着/外观；已生效变化覆盖初始化初值，不覆盖核心行为人格。

### 2. 当前实拍类生图只能使用权威快照

- [ ] 追踪真实图片入口、Prompt 组装和最终 ComfyUI/模型请求；在最后可信边界校验，不只在上游增加一句“不要幻觉”。
- [ ] “当前自拍/我现在的照片”由服务端读取一致的 Actor 状态版本、当前着装和真实库存条目；服装及所使用物品来自该快照。
- [ ] LLM 可组织动作、构图、表达等允许内容，但不能通过自由文本服装段覆盖权威着装、伪造库存 ID 或把愿望/搭配方案当成现在。
- [ ] 当前服装数据不完整时返回结构化缺失/冲突，要求补查或合法换装；禁止按想要的服装自由兜底，也不能把缺失数据当成默认无衣物。
- [ ] 未拥有/未穿上的物品不能出现在“当前实际穿着”的最终服装输入中。保护不仅覆盖 item_id，也覆盖自由文本描述和参考图选择中的绕过。
- [ ] 锁定拍摄请求的状态快照与版本；状态并发变化时按明确策略重新校验或保留拍摄时快照，禁止将不同版本拼接。
- [ ] 图片生成、发布成功不能反向写入“已购买”“已穿上”或实际身体变化，也不能用图片补造缺失库存。
- [ ] 项目若已有设计预览/虚拟试穿模式，保持显式非当前实拍语义且不修改持有和穿着；不要为绕过本轮校验新增无约束预览入口。

### 3. 初始物品与视觉边界

- [ ] 初始化明确拥有/穿着的衣服可以通过受控初始化流程登记库存和当前穿着，不要求角色先购买自己的全部初始衣服。
- [ ] 旧描述无 ID 时，只能依据明确初始化来源或合法事件补链；不能从历史生图、聊天臆想或无来源描述批量补库存。
- [ ] 必须验收最终工作流入参，而不是只看界面显示。若已有视觉验图能力则复用；没有则明确像素级服装还原不在程序校验可保证范围，不宣称已消除生成模型所有视觉偏差。
- [ ] 本轮不强制引入额外大视觉模型、训练或昂贵的生图循环。

### 验收

购买失败、不存在 ID、已持有但未穿上、状态冲突四类情况均不能绕过当前实拍服装约束。成功链路中可追踪“获取事件 → 库存 → 换装事件 → 拍摄快照 → 最终图片请求”。

## T07：5—10 分钟增量总结与有界上下文

### 1. 有新增才总结，摘要替换被覆盖历史

- [ ] 使用可配置的 5—10 分钟检查周期；仅有待处理新消息且满足时间条件，或未压缩输入已达到阈值时总结。突发大量消息不必等满时间；没有新内容不重复总结。
- [ ] 总结可用当前已支持的非思考模式，作为现有 Task 运行；不为总结新增长期驻留模型或独立 Agent 框架。实际模型不支持关闭思考时需明确诊断，不能声称已关闭。
- [ ] 每个会话/Actor 范围维护有界运行摘要、版本和明确覆盖游标。优先会话内有序序号；不得假设任意 UUID 的大小就是消息先后。
- [ ] 模型输入使用“当前运行摘要 + 尚未覆盖的完整消息”，不是“多条历史摘要 + 全量旧聊天”。已覆盖消息原文仍完整保存在数据库，按需查询。
- [ ] 保留最近必要的完整对话尾部；若有明确的受控重叠，必须有界并标记，不能将一天的原文反复注入。未闭合的工具调用与结果不能从中间切断。

### 2. 游标与并发正确性

```text
读取旧摘要版本与已覆盖位置
→ 固定本次待处理范围，不包含之后到来的新消息
→ 生成并校验新摘要及来源
→ 原子提交新摘要与新覆盖位置
→ 后续只读取成功覆盖范围之后的消息
```

- [ ] 生成失败、验证失败、写库失败时不推进游标、不标记消息已总结。
- [ ] 使用版本比较/锁等现有手段避免并发摘要互相覆盖；重试不遗漏、不重复永久记录。
- [ ] 编辑、撤回或事实纠正影响已覆盖内容时，显式修订/失效对应摘要范围，并保留版本依据。
- [ ] 总结任务本身也要分批受预算约束，不能将整段已超限历史原样交给另一个模型再次 OOM。

### 3. 摘要内容标准

- [ ] 优先保留明确事实及纠正、双方意图、真实承诺、重要结果与依据、仍未完成事项；人物归属、否定和不确定性不能丢。
- [ ] 用户背景、目标和权威状态有独立持久来源，不靠运行摘要充当唯一事实数据库。
- [ ] “不用回”“喝水了吗”“灯变了”不默认生成永久 open_thread；无新信息的重复主动播报归并成一条交互状态即可。
- [ ] 光线、毛衣颜色和环境细节仅在当前讨论确实需要时保留，不能每条都写成摘要主干。
- [ ] 摘要自身有固定可配置预算；合并时替换旧运行摘要，不按时间不断追加摘要块。跨天真实未完成事项继续保留。
- [ ] 推断仍标为推断，计划仍标为计划，失败仍是失败；不能在压缩时把“打算买”变成“买了”。

### 4. 最终模型请求预算

- [ ] 将应用层一刀切字符截断改成可配置的 token 预算；允许配置更大的应用预算，但不取消模型与部署的安全边界，也不自动把 ctx-size 拉满。
- [ ] 每次实际模型调用前统计：系统协议、Working Persona、运行状态、Actor 背景、目标、摘要、消息、Tool schema、结果和结构化输出契约。Agent 循环的后续调用也必须检查。
- [ ] 优先实际 tokenizer/服务端 usage；只能估算时明确标记估算与安全余量，不把字符数当成精确 token 数。
- [ ] 为输出和工具续接留出空间。压缩顺序优先去重复、低价值历史和冗余字段，不能静默删除当前用户请求、关键纠正、真实 Tool 结果或当前有效状态。
- [ ] 运行时刷新采用同一 Slot 替换，而不是每轮追加完整状态快照；完整 trace 留在诊断存储，不全部带入下一次模型输入。
- [ ] 最小必要上下文仍超限时返回明确诊断，不静默截坏 JSON、工具协议或事实，也不无限重试 OOM。

### 验收

用跨天长会话、连续自主播报及多轮 Tool Loop 压测：原始历史增长，但运行摘要与常驻投影保持有界；消息不丢、纠正不丢；展示完整最终请求的分项 token 对比，而不只比较 runtime 字符数。

## T08：历史污染清理与旧路径下线

### 实施任务

- [ ] 提供可重复执行、支持 dry-run 的迁移/清理脚本；按明确范围执行，保留原始消息、旧值、原因和回滚信息。不得直接清空整库。
- [ ] 撤销仅由定时检查推导出的自然醒经历及其习惯/常驻记忆派生项；不能简单合并成一条更权威的“稳定自然醒习惯”。真实有依据的起床事件要保留。
- [ ] 将已被纠正的同楼、约出门、送物等错误断言从有效事实层移除，保留真实说过的话和纠正历史。
- [ ] 隔离无法追溯的购买/持有/穿着断言，不为让当前页面看起来完整而批量补造库存。
- [ ] 清理重复 developing_self 和模板化摘要；先审事实资格，再去重，不能只按相似文本压缩。
- [ ] 更新来源关联、失效标记、检索过滤、常驻投影和摘要版本；同步处理相关缓存/索引，防止旧错误从另一入口重新回来。
- [ ] 历史恢复未完成的目标与日程时，使用已有真实记录关联，不凭模型猜测填充已完成阶段。
- [ ] 下线已替代的时间格式化、旧全量上下文注入、失败自由文本兜底、图片反写状态及重复目标/状态写入口。

### 验收

迁移重复执行结果稳定；可审计可回滚；修复后重启和召回不能把已失效数据复活。先在隔离测试库验证，交付正式执行命令和范围，不擅自对未知生产数据运行破坏性操作。

## T09：诊断中心 Agent / 模型运行按时间倒序

### 实施任务

- [ ] 两个列表统一默认按“本次运行发起/记录创建的固定时间”倒序，时间相同再按唯一键稳定排序。先核对哪个现有字段符合此语义，不按错误更新时间、结束时间或历史业务发生时间排序。
- [ ] 默认列表不暗含错误优先；错误筛选和特殊置顶作为显式选择，而非默认排序的一部分。
- [ ] 在后端完成全局排序之后再分页；多个来源合并时先统一排序语义，不能先各自分页再在前端拼接反转。
- [ ] 明确空值处理。PostgreSQL 的 DESC 默认是 NULLS FIRST，需要显式排除空时间置顶的问题；旧缺失时间优先用可靠创建时间，否则 NULLS LAST。[R3]
- [ ] 稳定分页使用真实时间精度和唯一键；刷新、筛选、追加页和实时新记录不得造成重复或漏页。必要时复用/补齐游标或固定查询快照。
- [ ] 前端统一时间展示组件，按明确选择的时区呈现带偏移的相同格式，不用不同偏移的展示字符串做全局排序。
- [ ] 单次运行详情内部的模型—工具—结果步骤保持执行正序，列表倒序不意味着内部步骤也倒序。
- [ ] 正常睡眠跳过、没有主动意图等 no-op 与真实错误区分；失败前已执行的 Tool、预算分项和状态版本保留可查。

### 验收

新成功、新失败、旧失败、空时间、相同时间、多页、筛选及实时刷新都符合统一排序契约；有后端断言及前端验证，不只改页面当前数组顺序。

## T10：测试、回归与证据交付

### 1. 两类执行测试必须保留

**Tool 独立运行测试：** 从正式工具入口直接调用，在隔离数据库中准备必要领域状态，验证权限、时间、失败、幂等、持久结果和可重入恢复。不能只 Mock 仓储返回一个成功对象。

**Agent Loop 测试：** 经过真实 Eino 原生运行路径，验证模型请求 Tool → 真执行 → 真实结果回填 → 继续决策。确定性故障注入可以使用脚本模型，但工具与持久化不能全被替换；另外使用实际部署模型做行为回归，并明确两者的区别。

新增/修改 Tool 应全部有执行测试；所有受影响正式 Agent/Task 与其本轮新增/修改的调用关系都要覆盖。已有全量测试清单不得缩减。

### 2. 必测矩阵

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| A01 | 初始化包含关系目标 | 目标进入持久状态和后续运行投影，不仅存在人格文本 |
| A02 | 存在关系目标，用户表达想找伴侣 | 允许符合人设的探索，不能固定退回无关建议；按语义评估，不锁定台词 |
| A03 | 用户未回复、明确拒绝、睡眠或工作受限 | 不刷消息、不伪造进展；合理等待/暂停不被当作惩罚对象 |
| A04 | 反思发现有证据的错失机会 | 形成不同于空泛承诺的可行下一步，并被后续运行读取 |
| B01 | 用户纠正此前同楼误判，说明在国外 | 正确信息常驻，旧相冲突断言失效，不再当事实召回 |
| B02 | 纠正后总结、反思、跨天、重启 | 纠正仍有效；不恢复旧同城约见/送物情节 |
| B03 | 用户后来明确回国 | 正确处理当前状态变化，不抹掉历史真实状态 |

### 3. 交付物

在项目已有文档目录内交付一份可供复核的 Markdown 报告，至少包含：

1. 每项用户问题的实际根因、代码位置、修改点和正式入口接线证据；未复现或证据不足的地方明确写出。
2. Agent/Task/Tool 变更清单，以及哪些既有能力被复用、哪些旧路径已删除。
3. 数据结构/格式变更、时间契约、配置默认值与调节方式、迁移 dry-run 输出、执行与回滚命令。
4. 测试命令、用例对应表、通过/失败/跳过数量和真实日志；漏测、跳过关键项或失败不能被 CI 当作通过。
5. 一条“无物品 → 目标 → 日程 → 购买入库 → 换装 → 图片请求”的完整证据，附关键数据库状态、真实 Tool 结果、run_id 和最终渲染入参。
6. 一条失败购买及重试幂等的证据，证明既不假装拥有，也不阻断后续合法重试。
7. 用户异地纠正经摘要/反思/重启仍有效的证据；睡眠多周期无自然醒污染的证据。
8. 修复前后同一数据集的完整模型输入分项 token、摘要长度与覆盖范围，不能只报告字符变化。
9. 两个诊断列表的后端排序结果及前端验证结果。
10. 仍未验证的真实模型行为、外部图片服务或像素级还原问题。不得将脚本模型、Mock 图片或仅通过单测描述成真实端到端通过。

## 实施顺序与最终完成定义

推荐先 T00，再完成 T01/T02/T03 的基础约束；T04 接入目标，T05/T06 打通购买与使用；T07 同步收口上下文；T08 在隔离数据中验证迁移；T09 可独立推进；最后统一执行 T10。

不要因为任务跨多个模块就停在方案，也不要把它扩大为整体架构替换。完成定义是：正式运行入口使用了修复后的唯一实现，历史错误不会重新污染，完整成功与失败链路都有真实状态证据，相关回归可重复执行。

**本轮最重要的判断标准：角色可以因为没有某物而主动计划并合法获得它；但计划、台词、失败调用和图片，绝不能提前把它变成已经拥有或正在使用的事实。**
