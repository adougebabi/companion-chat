# Notification badge/read synchronization — source audit

Read-only investigation; no browser validation, no test runs, no source edits.

## Confirmed lifecycle and defects

- **Initial authenticated boot never fetches notification unread count.** `App.tsx:126` calls `workspace.bootstrap`; `state/workspace.mjs:256` uses `refreshProduct({initialOnly:true})`; `v3/read-product.mjs:11` returns before the global `unreadNotificationCount` read at line 26. `workspace.mjs:186` initializes notifications to `[]`, and `replaceDirectory` (lines 217–252) does not hydrate notifications or `meta.unreadCount`. Thus the sidebar is empty/zero on a direct authenticated visit until entering Inbox. Login/setup can launch an unrelated full background product refresh (`v3/providers/real.ts:43–48`), but even its mapped `meta.unreadCount` (`contract-map.mjs:440`) is not consumed by workspace sidebar state.
- **Entering Inbox starts two separate notification reads.** App route effect includes Inbox in `workspace.load(page)` (`App.tsx:157–160`); `workspace.mjs:1030` delegates to `loadBrowse`, whose Inbox branch (`604–612`) loads notices/pending and copies only the first 30 notification rows into `state.notifications`. Native Inbox independently loads the same page in `pages/InboxPage.jsx:39` via `useWorkspaceRead`; the hook holds its own cloned JSON state (`shared/useWorkspaceRead.js:69–84`) and does not populate workspace notifications. Neither path invokes `notificationCount()`.
- **Sidebar badge is a page-length count, not the global unread count.** `App.tsx:239` computes unread from `state.notifications`. Provider `operations.ts:17` caps that list at 30. A first page containing 30 read rows with older unread rows yields no badge; >30 unread yields at most 30. Sidebar only renders badge if >0 (`shared/WorkspaceNavigation.tsx:34`). API count is available at `operations.ts:18` and browser client `v3-contract.ts:364–365`.
- **Mark one updates sidebar only if the separate workspace cache already contains the row.** `InboxPage.jsx:46` confirms write then updates local `readIds`, finds cached row and mutates `read_at`. If cache is populated, Valtio update propagates; if absent/stale, only native list count changes. An older concurrent `workspace.loadBrowse` response can overwrite that cache with unread data. Local Inbox `readIds` masks this for native list only.
- **Mark all leaves sidebar stale.** `InboxPage.jsx:49` confirms command, updates local readIds and reloads native notices; it never updates `w.state.notifications` or refreshes a global count. Provider command (`operations.ts:7–12,19–20`) does no projection refresh. Therefore sidebar continues showing pre-command unread rows until a later workspace Inbox route reload. Native Inbox unread tab/count changes locally, but it counts loaded rows only (`InboxPage.jsx:45,51`).
- Topbar bell at `App.tsx:244` currently has no unread badge at all. This is distinct from stale sidebar behavior; header bell does not read either count.

## Minimal ownership and races

Own one global notification count/read synchronization API in `state/workspace.mjs`, exposed to App/Inbox. Add count state with unknown/loading/failure rather than interpreting an unread read failure as zero. Schedule an independent count refresh after initial directory bootstrap, without making first paint wait on optional modules; App should consume that count instead of counting loaded rows. Native list can retain its pagination hook. Both successful single/all commands should refresh authoritative count and synchronize any cached rows with the server acknowledgement. Avoid refreshing all product modules for this.

Count is owner scoped, not selected-character scoped. Existing workspace `read()` (`workspace.mjs:266–283`) captures both owner and selected fid and invalidates on selection via generation (`1036`), so blindly reusing it for a global count discards valid reads on character change. Use owner/session generation plus count request epoch. Invalidate pre-write count requests when a mark command commits so an old count cannot restore the badge. Retain active/dispose protection and reject prior-owner responses, including A→B→A owner cycles. Inbox `live()` (`InboxPage.jsx:35–38`) checks owner equality/active only, with no owner generation; this equality-only guard alone does not handle same-owner return cycles. Native list read hook already has scope/epoch protection for its own requests (`useWorkspaceRead.js:32–69,104–120`).

## API semantics / constraints

- Character directory `unread_count` is **chat unread**, based on conversation message sequence/read positions (`core/repository.go:107`), not owner notification unread. Do not reuse it for Inbox badge.
- Notification count includes all unread personal owner notifications; `alert_count` excludes quiet notifications (`core/notification_center.go:181–187`). Choose explicitly whether UI means total unread (`count`, current semantics) or alerts.
- `listNotifications` is cursor/snapshot scoped with server `as_of`; scope includes owner/fid/unread and rows are bounded by snapshot (`notification_center.go:147–177`). A loaded page cannot establish total count.
- Single mark returns authoritative `{id,read_at}` and is idempotent through COALESCE (`notification_center.go:190–209`; client `v3-contract.ts:358–359`). Use returned read_at, not client clock.
- Mark all is global for owner, **not just visible rows or selected fid**; uses `created_at <= before`, requires observed timestamp and idempotency key (`notification_center.go:212–227`). Preserve `notices.extra.as_of`; notifications arriving after snapshot remain unread. Refresh count after command rather than setting zero or subtracting page length. Write commit must remain successful if subsequent readback fails (`operations.ts:10–12`).
