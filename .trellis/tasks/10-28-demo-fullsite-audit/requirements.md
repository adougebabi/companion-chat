# 任务：以现有 Demo 为基准，对正式项目进行全站 UI/UX 比对、缺陷修复与业务接入核查

请直接执行这项任务，完成代码修复和验证。范围是 **Demo 的全部页面、子页面、详情、表单、弹窗、交互状态和跨页流程**，不能缩减为公共外壳与聊天页，也不能只提交分析报告或后续计划。

## 一、目标与依据

正式项目已经参考 Demo 做过一轮实现，但目前存在“整体看着像，细节与交互没有完整保留”的问题。本次需要系统性地找出差异并修复，而不是重新设计一套界面。

使用以下依据：

- **正式项目基线**：当前工作区的最新代码，包括未提交改动。先检查 Git 状态，避免误用旧提交，也不要覆盖或撤销已有工作。
- **视觉与交互基准**：已提供的 `fluctlight-workspace-demo` 完整源码及其实际运行效果。
- **业务与数据基准**：正式项目已有的领域模型、接口契约、权限、持久化和任务机制。
- **辅助资料**：Demo 中的 `README.md`、`docs/REPLICA.md`、`docs/SOURCE_MAP.md`、截图及其他相关说明。精确展示效果以 Demo 实际组件和生效样式为准。

先自行定位正式项目和 Demo。只有确实找不到必要文件时，才询问缺失路径。

阅读并遵守仓库现有 `AGENTS.md` 和适用开发约定。常规检查、修复与验证直接推进；真正受权限或环境阻塞的事项，明确记录原因。

本次同时核查三个独立维度：

1. **视觉一致性**：布局、间距、字号、字重、颜色、边框、图标、图片、组件尺寸和滚动行为。
2. **交互完整性**：按钮、菜单、表单、详情、编辑、取消、保存、返回、加载、失败与恢复。
3. **业务正确性**：页面是否真正接入现有业务，操作是否形成实际请求、处理、持久化和回读闭环。

不要预设后端已经处理完成，也不要预设所有问题都在后端。通过实际调用链和证据判断。

## 三、建立真正可比较的视觉基准

### 1. 对照必须使用同一内容与状态

不要再拿稀疏的“验收样本”、缺失头像、无附件消息或失败状态，去对比 Demo 的完整正常页面。

为各类页面建立可重复的固定验收场景，按页面实际需要覆盖：

- 正常且内容完整。
- 空数据。
- 加载或执行中。
- 编辑及存在未保存修改。
- 保存成功。
- 失败、未知、冲突或待审阅等实际支持的状态。
- 长文本、多字段、多条目以及窄屏。

对照时统一：

- 浏览器、视口、缩放、设备像素比和字体环境。
- 人物名称、头像、图片与其他展示资源。
- 文案、数据数量、字段长度、消息内容和附件。
- 选中项、筛选项、展开项与交互状态。
- 页面滚动位置和内部滚动位置。

不同状态分别与各自基准比较。不要通过缩短文案、减少字段、删掉图片、隐藏异常或截断内容来降低差异。

### 2. 固定数据只服务于验收

可以增加测试 fixture 或开发验收入口，但必须运行**正式项目实际使用的展示组件与数据映射路径**。

不能另做一套验收专用的漂亮页面，也不能把 Demo 直接嵌入后当作正式项目已完成还原。

测试数据不能泄漏到正式业务。正式环境缺失头像、穿着、日程或任务结果时，应展示真实缺失状态，不能偷偷填入 Demo 数据。

### 3. 保持参考基准稳定

Demo 作为只读参考。不要修改 Demo、改写参考截图或重新生成“以当前实现为标准”的基准来消除差异。

正式产品可以移除 Demo 专用的模拟开关等工具，但要登记为明确允许的差异，并在对照中使用一致的显隐配置。

## 四、按实际展示代码修复，避免继续产生近似实现

优先复用 Demo 中可以复用的展示结构、组件、样式和资源。需要接入正式业务时，抽出明确的数据输入和操作回调，通过适配层连接现有 controller/client。

避免在移植过程中自行重新组织布局、替换成另一套默认组件外观，或重新猜测尺寸。

重点检查：

- 容器尺寸、最大宽度、网格比例、对齐、内外边距。
- 字体及实际回退字体、字号、字重、行高、字距和文字颜色。
- 按钮、输入框、选择框、徽标、弹窗、抽屉的实际尺寸。
- 头像和图片来源、宽高比、裁切方式及加载失败回退。
- 图标尺寸、描边粗细、基线与文字间距。
- hover、focus、selected、disabled、loading、error 等状态。
- 页面与内部容器的滚动、sticky/fixed、遮挡、裁切和溢出。
- 侧栏每一行与每个分组的高度，避免小偏差逐行累积。
- 长文本、扩展字段、列表密度变化后的真实排版。

检查 **实际加载的 CSS 与浏览器有效样式**。查清规则来源、继承、CSS layer、组件默认类和覆盖顺序。不要仅因为旧样式文件存在，就认定它正在污染页面。

不要通过连续追加高优先级覆盖或大量 `!important` 掩盖根因。能在共享组件或原始规则中修正的，优先在那里修正，并复验受影响页面。

特别核查：

- 同一角色在侧栏、卡片、会话头部和消息列表中的头像来源是否完整、一致。
- 是否存在依赖 `id === 'linwan'` 等示例 ID 才能出现完整展示的隐式条件。
- 空输入、纯空格输入及等待中，发送按钮的行为和禁用外观是否一致。
- 正文、元信息、状态提示和恢复操作是否保持正确的视觉层级。
- 右侧卡片变高究竟来自内容变化还是样式偏差，不要用固定高度掩盖内容问题。

## 五、同时核查真实业务与后端接入

对每项有业务效果的操作，追踪并验证：

**用户操作 → 前端处理与参数映射 → 实际请求 → 后端处理或任务 → 持久化或产物 → 重新读取 → 当前页面及关联页面更新。**

具体要求：

1. 核查字段是否遗漏、映射错误、提交范围错误，是否丢失嵌套结构、未知扩展字段、来源或版本。
2. 核查按钮是否只改本地状态、只弹成功提示，或者实际请求与界面表达不一致。
3. 区分“请求已受理”“执行中”“执行完成”“结果可读”，不能统一显示成功。
4. 保存后应按现有契约读取结果；适用操作在刷新或重新进入后仍应成立。
5. 保留权限校验、版本冲突处理、幂等、原请求恢复和后端允许操作。
6. 核查切换角色、切换世界、切页及迟到响应，避免旧请求污染当前对象或覆盖新输入。
7. 不允许把正式能力替换为 `setTimeout`、硬编码成功结果、固定回复或仅写 `localStorage`。
8. 后端不可用、接口缺失或环境不足时，记录具体阻塞和已验证范围，继续完成不受阻的工作。
9. 后端只修复已经定位、与本次页面或流程直接相关的缺陷，不进行无关协议重写、数据库清空或大范围重构。

尤其保持以下业务区分：

- 保存资源草稿、发布具体版本、应用到角色是不同操作。
- 世界配置复用应遵循正式契约，不能误复制其他角色的历史或运行状态。
- 空白初始化与非空白分析流程分开；激活前可编辑，激活后围绕原任务恢复。
- 初始化结果未知时核对原请求，避免重复创建。
- 初始化进度来自真实阶段状态，不能用前端计时模拟后端完成。
- 保存穿搭方案与请求换装分开；当前穿着以确认后的结果为准。
- 日程建议与实际安排分开；目标进展以实际证据或正式结果为准。
- 记忆纠正保留来源和历史。
- 用户自填资料与角色已经形成的认识分开。
- 视觉设定、候选图、规范参考、角色设定图、显示头像分开。
- 通知已读与业务待处理完成分开。
- 模型服务连接与各用途绑定分开。
- 暂停、取消、重试和恢复遵循接口能力与 `allowed_actions`，不制造无效操作。

同时验证跨页一致性，例如换装后聊天与此刻同步、资源发布后初始化读取正确版本、通知操作后关联页面状态更新。

## 六、实施顺序与执行方式

按以下顺序推进，但必须最终覆盖完整清单：

1. 确认工作区基线，建立全站对应矩阵。
2. 运行 Demo 与正式项目，建立同场景验收条件。
3. 修复影响多页的公共组件、主题、字体、资源和布局问题。
4. 按模块逐页比对、修复并验证全部适用状态与业务操作。
5. 验证跨页流程、角色作用域、刷新恢复和响应式行为。
6. 汇总剩余差异、阻塞及最终验证结果。

可以分批实施，也可以并行分析互不冲突的模块，但共享组件和全局样式必须统一协调。

每完成一批就更新覆盖矩阵。不要只完成第一批、公共外壳或聊天页就结束。长任务跨上下文继续时，应根据已记录状态接着执行，不重复推倒重做。

保留现有有效业务逻辑。修改共享样式后，检查相关页面，避免修好一页又破坏其他页。

## 七、验证与完成标准

### 视觉验证

- 在相同场景与环境下生成参考图、实现图及差异证据。
- 先检查结构、尺寸和排版，再检查颜色、图标及状态细节。
- 合理的字体抗锯齿差异可以说明，但不能用它解释明显的字号、字重、行高或位置变化。
- 不得通过扩大容差、遮罩主要区域或替换参考图来制造通过。
- 桌面与窄屏分别实际检查；没有实测就明确标记未验证。

### 交互验证

根据页面适用性，验证：

- 搜索、筛选、分页或加载更多。
- 打开详情、编辑、取消、保存、返回。
- 草稿保留、确认操作和关闭行为。
- 加载、失败、重试、未知、冲突与恢复。
- 键盘操作、焦点恢复和窄屏可用性。
- 切换页面或对象后不会丢失不应丢失的上下文。

### 业务验证

- 写操作具有真实调用和结果回读证据。
- 异步任务展示实际阶段与允许操作。
- 刷新、重新进入以及相关页面读取后的结果一致。
- 对模拟环境验证与真实后端验证分别标注，不能混为一谈。
- 运行与修改相关的现有测试、类型检查和构建；新增检查应覆盖具体风险，避免只重复实现本身。

**构建通过、测试通过、页面能打开，均不能单独代表视觉或全站验收完成。**

## 八、最终交付

完成后提供：

1. **完整覆盖矩阵**：每个页面、子页面和关键状态的视觉、交互、业务接入结果。
2. **实际修复清单**：问题现象、根因、修改文件、修复方式与验证证据。
3. **视觉对照证据**：按模块组织的同场景截图，附已解决和仍存在的差异。
4. **业务接入结论**：哪些已经确认真实闭环，哪些修复了调用或后端问题，哪些只在受控环境验证。
5. **验证记录**：执行过的检查、结果和明确边界。
6. **剩余问题与阻塞**：具体到页面、操作、依赖及所缺条件，不能写成笼统的“后续优化”。

不要使用“基本还原”“整体完成”“大约 90%”代替逐项结果，也不要将未验证项标为完成。

现在开始执行：先检查当前工作区和 Demo 的实际版本，建立全站覆盖清单，然后持续完成比对、修复和验证。除确实需要用户提供的信息或权限外，不要在分析或计划阶段停止。
