# 跨子任务设计

## 边界

父任务只保存七项源要求、子任务映射和最终联合验收。每个子任务拥有自己的代码、设计、验证与可回滚边界。`09-27-life-event-timezone` 是语义变化最大的子任务；其他子任务不应把旧的活动/场景割裂当作前提。

## 数据流约束

- 权威数据仍在 Go Core。Provider 可见投影、Tool schema、Owner 诊断及浏览器 DTO 是不同边界，不把内部数据库 ID、完整认知 trace 或未脱敏内容直接放进公开聊天。
- `active_memory:ctx_*` 与 `memory:ctx_*` 的更新目标用途保留；普通对话可减少无独立目标消费的细粒度来源 ref。Tool 参数精简需与投影修改互相核对。
- 当前事件状态应由同一有时效边界的事实驱动。事件/场景/活动可明确延期；到期且无延期就不再是当前。业务效果只由已确认结果写入。
- 时间来源要区分作者：摇光的生效 IANA 时区 = 显式设定优先、初始化识别其次；用户消息需保留发送时捕获的 IANA 时区或有界 offset。存储 UTC instant，显示时按消息作者与当时的时区转换，不使用宿主进程时区推断历史发送地。
- 对话摘要与 raw history 以最终 Prompt 真正入选的 Summary source refs 去重；原文先形成最多 200 条候选，并作为 Working Memory 的 fallback 保留到总预算决策。异步未完成或任一预算落选的 Summary 不得提前剔除原文；预算裁剪和固定窗口错位要分开诊断。
- Owner 诊断每个物理 Provider 请求保留独立 Prompt/Response；UI 按逻辑 correlation 组织，不修改公开聊天消息协议。

## 顺序与兼容

建议先完成时区与事件生命周期，再完成 Context/Tool 契约；通用 Tool 参数错误分类完成后，再修 Visual Identity 的观察输入与有界修正调用，最后完成诊断展示。Tool 与 Context 的目标引用调整要在同一联合检查中确认。现有数据库状态及历史诊断须保持可读；如新增活动终态或持久 timer，使用向后兼容迁移与明确的旧 run 收敛策略。

## 联合风险

- 现有工作区有进入本任务前的未提交改动，尤其衣橱、浏览器边界、前端详情与两个 spec 文件；实施时逐文件比对，不回滚或夹带这些改动。
- 事件到期时 Provider/Worker 不可用，不得让过期 run 继续冒充“当前”；也不得在无结果时凭空生成购入物。
- 对话历史可能因预算仍被裁剪；验收目标是消除固定窗口制造的空档，并让裁剪可诊断，不是无限上下文。
