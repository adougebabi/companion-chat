# 任务：Agent / Tool 插件化收敛与双 E2E 验证闭环

你正在当前项目仓库中执行一次定向架构修正。请读取实际代码并完成实施，不要只输出方案、审计报告或演示代码。

本任务允许修改较多文件，但不是整体重构。修改必须围绕：Agent 独立运行、Tool 独立执行、正式调用方迁移，以及对应的真实测试。

## 一、必须实现的最终架构

项目应当具备两类独立插件：

### Agent：完整任务的决策与循环单元

每套承担完整任务的提示词对应一个正式 Agent，例如认知、视觉身份，以及仓库中其他承担完整任务的提示词。

一个 Agent 包含自己的任务提示词、输入与上下文装配、模型配置、工具装配和输出契约。它能够通过自己的正式入口独立运行，使用 Eino 原生 Agent loop 完成：

输入 → 模型决策 → 调用 Tool → 消费实际工具结果 → 继续决策 → 完成任务。

不同 Agent 共享 Eino 的循环实现和必要基础设施，但不共用一个包含所有业务分支的大 Main 流程，也不各自复制一份循环代码。

公共提示词片段、Slot 和普通辅助函数不需要机械地变成 Agent。无需调用工具的任务允许一次模型调用后正常结束，但不能因为旧实现被命名为 Task，就保留一条无法使用正式 Agent 运行能力的旁路。

### Tool：完整业务能力的独立执行单元

每个业务 Tool 必须能够脱离 Agent、Main、认知轮次和特定流程阶段独立调用。

给定必要业务参数和实际依赖，Tool 必须执行自己的业务逻辑，返回真实成功结果、业务失败结果或运行错误。

必须存在两种调用方式，并共享同一个执行实现：

直接调用 → 正式 Tool → 真实业务依赖 → 真实结果。

Agent 调用 → Eino → 同一个正式 Tool → 同样的业务依赖 → 结果回到 Agent。

插件化不要求动态加载、热插拔或新增插件平台。优先使用清晰接口、显式注册和依赖注入完成。

最终应当做到：新增普通 Tool 不需要修改 Agent loop；新增 Agent 不需要修改通用工具执行逻辑；修复某个 Tool 不需要在认知核心中增加该工具的特殊分支。

## 二、修改范围与旧约定处理

允许修改现有 Agent 定义与装配、Prompt/Slot 接线、Tool 实现与适配、直接相关的业务服务和局部事务、正式调用入口、测试及相关 Trellis 规范。

不替换前端/BFF/Go 服务架构，不迁移 Temporal、数据库和基础设施，不新增第二套 Agent Runtime、通用工作流平台或平行测试平台，不为目录美观进行无关拆包。

当前正确使用 Eino 的实现应当保留。以当前锁定的依赖版本及对应源码确认 API，不顺手升级依赖，不复制或修改框架源码。

以下旧约定若与本任务冲突，必须替换，不能继续作为兼容要求：

- 普通认知只能单次调用模型，或者只有 QUERY 才能续接。
- 根据工具类型固定限制模型生成次数，或者写工具执行后强制结束。
- Tool 只生成候选动作，必须等待 Main、冻结或后续结算才能完成实际执行。
- Tool 必须具备某种人格、surface、Agent 来源或流程阶段才能运行。
- 为旧执行方式服务的自研续接、重复 Dispatcher 和协议兜底。

这里的“不做限制”，指不得施加隐藏的运行场景限制。必要参数、真实资源归属和业务条件仍应正常检查，并返回明确结果；不能把旧的场景门禁换个名称藏进去。

独立调用不意味着新增对外无鉴权接口，也不意味着测试可以操作真实用户或生产资源。

保留用户已经拥有的产品能力。可以删除旧实现，但不能通过关闭功能、减少场景、删掉困难工具或弱化断言实现“稳定”。

涉及提交位置和执行时机的必要变化，应明确记录并测试；不能为了声称“行为完全不变”，继续保留与独立执行相冲突的旧机制。

## 四、Agent 实施要求

### 使用唯一的原生循环

正式路径收敛为：

业务入口 → 对应正式 Agent → Eino 原生 Runner/Agent loop → 正式 Tool → 后续模型决策 → 任务结果。

外部调用方只负责提供输入、启动任务和接收结果，不再代为解析动作清单、执行工具、拼装工具结果或决定是否续接。

工具执行以正式原生 ToolCall 为依据。不得从正文、reasoning 或另一份结构化 JSON 中再建立第二套执行协议。

最终结构化输出可以保留，但应在任务完成时按 Agent 输出契约处理，不能把中间工具调用消息误当作最终结果校验，也不能失败后偷偷使用前一轮文本兜底。

### 完整保留循环语义

普通工具返回后，Agent 必须能够消费结果并继续判断，包括业务失败结果。

不得将所有写工具配置为直接结束。确实属于任务终结动作的工具可以采用对应的原生结束机制，但必须逐项说明其任务契约并测试。

保留明确的超时、取消和最大迭代次数。这些是运行保护，不是正常完成条件；不得将超限、取消或错误转换成成功。

不得保留“查询后只允许一次 continuation”“第二次生成必须结束”等隐藏限制。

同轮多个 ToolCall 必须正确关联执行结果。不能漏掉调用、串用结果、重复执行，或者抹掉已经发生的执行事实。

### 独立运行与正式接线

每个正式 Agent 都能通过自身入口运行，不需要伪造一次聊天、启动 Main 或依赖另一个 Agent 完成剩下半段。

每次运行的输入、工具结果、任务状态必须隔离。必要的持久化上下文通过明确业务接口获取，而非复用其他运行的可变状态。

视觉任务需要将真实图片按正式模型适配路径送入后续判断，不能只返回一个路径字符串就声称已经完成视觉评估。

现有 API、对话和后台任务入口必须迁移到这些正式 Agent。不能独立测试通过，生产入口仍走旧路径。

后台测试可以主动触发真实任务入口，不必等待定时时刻，但不能绕过正式装配和执行逻辑。

## 五、Tool 实施要求

### 正式实现可直接调用

工具的独立入口必须复用生产实现、参数解析、结果序列化和业务服务，不能新增测试专用简化版本。

允许提取可复用的最小生产装配，但不能要求调用一个简单工具时必须启动整套 Main 和后台流程。

Tool 需要的用户、资源、参数和依赖必须显式提供。不得要求调用者伪造人格状态、认知结果、冻结动作或特定轮次。

直接调用没有 Eino ToolCall ID 也应能运行；需要追踪或业务幂等标识时，采用明确的执行标识。Agent 调用必须保留真实 ToolCall 关联，不能伪造模型调用事实。

### 真正完成承诺的业务

查询工具必须实际查询，写入工具必须实际写入，发布工具必须完成其契约定义的实际发布动作。

如果当前工具只做 Prepare，再由 Main 提交，应将真正的执行能力收敛为独立业务服务，由 Tool 调用。保留必要事务，不让事务只能寄生在认知主流程中。

回复发布、人格切换、记忆写入、视觉身份保存等能力若存在，也必须纳入迁移，不能把最难处理的工具留到下一阶段。

复用既有有效的正式发布通道，不另开旁路，不将中间事件或候选结果自动发布，不造成工具发布与外层发布重复。

异步工具可以返回真实受理结果和任务标识，但必须区分受理与完成。不得把原本承诺完成操作的工具批量改成“提交任务”，借此回避独立执行。

### 真实失败与副作用一致性

可处理的业务失败应当作为明确结果返回，使 Agent 能够消费失败原因并继续决策。

代码错误、取消和依赖异常必须保留准确原因，按明确的错误契约处理；不得统一吞掉后返回空结果或 success。

重点覆盖：Tool 已成功提交，但后续模型调用失败、取消或最终输出非法。

此时必须准确保留已发生的事实，不伪称回滚，也不能通过重跑整轮 Agent 重复写入、重复发布。

有副作用的工具必须定义重复调用语义。需要幂等时使用稳定的业务操作标识，不能只依赖每次可能变化的模型 ToolCall ID。

不新增跨模型、数据库和所有外部服务的全局事务；保证各工具的实际结果、局部事务和副作用一致。

## 六、必须完成两套独立测试

### A. 全部业务 Tool 的独立 E2E

测试从正式生产 Tool 边界进入，使用真实依赖，不启动 Main，不伪造 Agent 状态，不只调用内部辅助函数。

每个正式业务 Tool 必须有独立测试，覆盖：

| 场景 | 必须证明的事实 |
|---|---|
| 有效调用 | 没有 Agent 运行上下文也能完成实际工作 |
| 业务失败 | 返回真实失败结果，不只测试参数格式错误 |
| 实际结果 | 返回值与数据库、任务、消息或文件产物一致 |
| 依赖异常 | 不吞错、不将未完成操作伪装为成功 |
| 重复执行 | 按工具契约验证幂等或明确的重复操作行为 |
| 正式适配 | Agent 适配调用与直接调用使用同一实现 |

测试可以准备和清理数据，但不能代替被测工具完成业务。

查询使用真实测试数据；写入检查真实持久化；生图检查真实任务与产物；异步提交检查实际受理，最终完成能力另检查真实完成状态。

难以稳定制造的依赖异常可以使用隔离故障注入补充，但不能用它替代真实成功链路。

框架纯运行时控制动作与业务工具分列，不要求将 exit/transfer 等机械改成业务插件；但不能把业务工具改名为内部动作来逃避独立测试。

### B. 全部正式 Agent 的循环 E2E

使用正式提示词、正式上下文装配、正式模型适配、正式工具注册和真实 Provider，验证真实任务闭环。

每个正式 Agent 都必须有自身运行证据。只写一个简单示例 Agent 证明 Eino 能运行，不算项目通过。

根据 Agent 的真实职责覆盖：

| 场景 | 必须证明的事实 |
|---|---|
| 不需要工具 | 能正常直接完成，不强制制造调用 |
| 一次工具调用 | 工具实际执行，结果进入下一次模型输入并被使用 |
| 连续多轮 | 至少有两轮工具执行、三次模型决策的有效链路，不被旧机制截断 |
| 业务失败后继续 | 真实失败结果回填，后续决策能调整、换动作或说明失败 |
| 写入后查询 | 后续查询能观察到前面的真实提交 |
| 同轮多个调用 | 调用和结果正确关联，无遗漏、串线或重复 |
| 工具成功后模型失败 | 不丢失执行事实，不重放副作用 |
| 异常结束 | 超时、取消、超限、非法最终输出不被算作成功 |
| 运行隔离 | 不同用户、Agent 和运行之间不混用状态 |

不强迫所有 Agent 制造无意义多轮，但不能所有 Agent 都只测一次返回。

至少设计一条无法靠提示词猜答案的真实链路：在记忆库写入本次随机生成的信息，当前对话不提供答案，由正式认知 Agent 通过实际记忆 Tool 获取并使用。

证据必须能关联实际模型请求、原生 ToolCall、工具执行、实际结果、下一次模型输入和最终结果。不能只检查出现过工具名称、调用次数或最终文本非空。

生产采用流式调用的路径必须覆盖流式行为，不能只证明非流式测试通过。

受控模型可稳定验证罕见协议错误、多调用和恢复分支，但必须单列为受控回归，不能替代真实 Agent E2E。

不得更换正式系统提示词、提前塞入答案、Mock 最终业务结果，或不断重跑后只保留偶然成功的一次。测试任务输入可以设计，但不能改造被测 Agent 来迎合测试。

### 完整性与测试有效性

先依据已有产品能力建立期望清单，再对照实际注册结果。不能只从当前注册表生成预期集合，导致删掉工具后测试仍自动“全覆盖”。

所有业务 Tool 必须有独立证据和正式适配执行证据，所有 Agent 必须有自身闭环证据。不要求无意义地穷举所有 Agent × Tool 组合。

在隔离环境验证至少两个破坏性场景：

- 断开工具结果回填，相关 Agent 测试必须失败。
- 跳过真实写入但仍返回成功，相关 Tool 测试必须失败。

如果仍通过，先修正测试。不得把故障开关留在生产路径，最终验收必须针对恢复后的最终代码重新运行。

复用现有测试脚本，提供单独运行指定 Tool、指定 Agent，以及运行两套完整套件的命令。

必要用例缺失、零匹配、SKIP、BLOCKED 或执行失败时，完整验收不得返回整体成功。普通开发测试可以独立运行，但不能被包装为双 E2E 验收结果。

## 七、实施顺序、清理与交付

按以下顺序持续完成本任务：

实际清单与环境预检 → 打通一条真实 Agent/Tool 链路验证结构 → 迁移全部业务 Tool → 接入全部正式 Agent 和调用方 → 清理旧路径 → 双 E2E 与有效历史回归。

第一条链路只是验证方法，不是最终交付范围。不要拆成“本次只搭框架，剩余工具以后迁移”。

删除被替换的旧循环、重复 Dispatcher、延后代执行、冲突门禁、协议兜底、兼容分支和只保护旧实现细节的测试。

保留有效产品契约测试；需要改写时，说明原契约如何迁移，不能降低要求。

同步修改已有 Trellis 规范，明确旧约定已被替换，不保留两份互相冲突的有效规范，也不另造一套庞大文档体系。

保留用户当前工作树中的既有修改，不擅自回滚；不执行生产迁移、生产写入、远程发布或强制推送。实际验证使用隔离环境和测试账号。

最终交付：

1. 实际代码与测试改动。
2. 简短架构说明：正式 Agent 路径、Tool 独立路径、删除的旧机制、必要的行为变化。
3. 完整验收矩阵：全部 Agent、全部业务 Tool、用例、测试类型、结果和证据位置。
4. 可复核的实际命令、退出码和运行记录，注明受测代码版本与必要配置，不包含密钥。
5. 尚未完成或受阻的事项，准确区分代码实现完成与真实验收通过。

只有在全部业务 Tool 真正可独立执行、全部正式 Agent 真正完成其循环、生产调用方使用同一套已验证路径，并且两套 E2E 完成验证后，才能报告任务完成。

不能以“接入了 Eino”“增加了很多测试”“编译通过”“部分路径可用”代替完成。

现在开始读取仓库并实施。过程中简短同步已确认问题、实际修改和验证结果，不要只回复一份计划后停止。
