### 0.1 最终业务行为

人格说明“她是什么样的人”；Actor 档案和关系说明“她面对谁、当前背景是什么”；Goal 说明“她现在想达成什么”；日程说明“获准的具体行动何时执行”。四者有各自权威，不互相充当永久指令。

系统维护最多五个活动的独立 Goal。GoalPlanner 先复核已有目标，再根据真实结果、稳定人格、相关 Actor、关系状态、当前生活和资源形成新候选，复用、去重、排序并按权限激活。有效候选不足时可以少于五个，甚至暂时为零，并留下原因及复核条件。

新目标继续使用已经跑通的阶段推进、执行、证据评估和完成链。旧目标保持其真实终态，不因为人格原文、重启、反思或新目标生成而复活。

### 0.2 不可突破的实施边界

保持现有 Eino 原生 Agent loop、模型适配、Prompt／Slot、插件化 Tool、日程、Worker／Temporal、领域命令、版本校验和幂等机制。GoalPlanner 是独立业务 Agent，不能塞成主认知里的另一个巨大分支，也不能另造模型—工具循环。

只新增本轮缺少的领域能力与调用接线，不替换 BFF、整体工作流、人格切换、记忆或关系系统。查询 Tool 无隐藏写入，写入 Tool 可独立运行；模型必须消费真实提交结果，不能以自然语言声称创建成功。

保留作用域、人格私有／共享边界、Actor 身份、Owner 权限、睡眠／地点／时间约束，以及现有副作用授权。目标规划不等于获准发送消息、出门、购买或更新关系。购物仍指现有虚拟生活获取链，不增加现实支付权限。

不通过降低成功标准、重置进度、增加亲密度、修改情绪、编造物品或对方回应来达成目标。不把用户拒绝解释成应该增加追求频率。

所有自动生成、初始化导入、Owner 创建／恢复等入口必须使用同一 Goal 权威和容量规则。迁移可以分步骤实施，但交付时不得保留长期运行的新旧双通道。

## 1. 本轮明确采用的产品语义

以下是实施目标，不是对当前源码现状的断言。没有必要再向用户追问这些已确定事项。

### 1.1 活动目标的容量

| 项目 | 本轮规则 |
|---|---|
| 计数范围 | 同一摇光实例拥有的所有活动独立 Goal；不是每个目标 Actor 或每个人格分别五个 |
| 上限 | 本轮最多五个，集中策略配置默认 `max_active_goals=5`；可收紧，不提供模型扩大上限的能力 |
| 占用名额 | `active` 及项目等价活动状态，包括执行中、等待机会、等待外部结果和受阻 |
| 不占名额 | 未激活候选、暂停、完成、取消、放弃；Stage／Commitment／Intention 不额外计数 |
| 补充原则 | 有空位时尝试补充，不为凑数造目标，不要求每天新增五个 |
| 候选管理 | 候选不占活动名额，但必须有数量边界、去重和退出原因，不能无限堆积 |
| 暂停恢复 | 恢复／重新激活重新检查容量、授权、依赖和当前事实，不抢占名额或默默挤走别的目标 |
| 人工保留 | Owner 明确暂停、取消或锁定的目标，Planner 不得自行复活、改名重建或解除限制 |

人格不可见的活动目标仍由服务端计入实例容量，但不能为解释剩余名额而把私有人格目标内容泄露给当前 Agent。依赖与规划也不能突破这个边界。

### 1.2 自动规划开关与人工操作

新增或复用独立的 `auto_planning_enabled` 策略。默认遵循实例现有自治开关与授权；只有已允许自主规划的实例才自动补充。现有自治被关闭、权限待批准或实例停用时，不因本轮部署扩大权限。

关闭自动规划表示不自动补充、激活或重新编排目标；它不等于取消已有目标、停止既有执行或清空日程。Owner 手动创建、排序和治理仍走正式权限。前端必须把“暂停自动规划”和“暂停某个目标／实例”区分清楚。

自动规划关闭期间出现的新愿望，仅可按既有权限记为非活动候选或待处理事件，不自动执行。重新启用后读取当前事实与目标集合再规划，不机械重放关闭期间的旧建议。手动“立即规划”在关闭状态下默认生成建议，不隐式恢复自动激活；需要应用时使用明确的受控命令。

### 1.3 目标排序与依赖

默认自动排序：同等条件优先已有、未结束且仍有效的目标；新目标默认放在已有目标之后。真实截止、已作承诺、前置需求、重大情境变化等可以构成插队或调整理由，但必须留下依据。

本轮采用可明确解释的 `automatic / manual` 排序模式或项目等价实现。Owner 确认手动排序后，Planner 只能建议调整；新增目标默认追加，不能悄悄覆盖人工顺序。Owner 可明确恢复自动排序。

优先顺序不等于执行资格。排第一但在等待回应的目标可以保留第一，执行器应选择下一个合法可执行目标，不得绕过等待、依赖或授权。

依赖先实现同一实例内独立 Goal 的“前置目标完成后才可开始新的关联行动”，多个前置默认全部满足。`derived_from` 等后续来源关系只用于追溯，不等于执行依赖。已有阶段内部依赖继续复用，不把每个准备动作都升格为独立 Goal。

### 1.4 时间与事实边界

沿用统一时间契约：时刻持久化 UTC，跨服务使用带时区的 RFC 3339；日历日期另带所属 Actor 的 IANA 时区。不得混入无时区时间，不能用 Owner／服务器时区覆盖目标主体的本地日程。

Owner 设置、初始化背景、实际互动事件、模型推测必须保留不同来源。修改关系配置不等于对方刚刚做出回应，也不自动完成要求真实表达／互动证据的目标。已发生的直接拒绝不能被旧初始化好感覆盖。

## GP01｜目标与人格解耦、一次性初始目标导入

**目的：** Goal 不再是固定人格里永久重复执行的愿望，完成后不会重新出现。

建立／复用独立 `initial_goals` 初始化输入及相应 UI／DTO。人格保留稳定性格、偏好、价值和长期动机，初始关系配置写入对应 Actor 关系来源，具体可完成愿望写入 Goal。不能创建一个新的“人格 goal 列表”作为并行运行时权威。

对混合内容进行语义区分，例如“性格克制，暗恋 A，等待机会表白”拆成稳定性格、对 A 的初始单向好感、一次性表达目标。不能用删除“目标／希望／想要”等关键词的正则清理，把稳定动机和爱好一起删掉。无法确定的历史内容标记待复核，不伪造关系事实。

初始化导入记录实例、来源项稳定 ID、输入版本、目标映射和结果。相同来源重试、重启、重新编译 Working Persona、切换人格不能重复导入。已有等价完成／暂停／取消目标时复用历史关联，不新建；来源内容真的变更也不能自动复活原目标，须显式确认新增意图或产生候选。

初始目标同样受五目标上限和自治授权约束。多于五个的初始输入保留超额候选及原因，不丢数据、不让数据库瞬间激活全部。

更新运行时装配：当前 Goal 只从 Goal 权威投影读取；当前关系只从有效关系状态读取。完整人格查询 Tool 默认返回结构化的稳定人格信息，不把已迁移的行动愿望作为当前指令。确需读取原始设定时按历史来源返回，并明确其版本与非当前效力；后续认知仍使用权威动态目标。

保留原始人格文件／文本作为可追溯来源，不覆盖用户原文、不要求重建实例。清理旧编译器、缓存、Prompt 和初始化重放路径；不能仅在提示词最后加一句“以动态为准”，却继续把旧愿望重复注入所有槽位。

**完成标准：** “表达心意”完成后，重启、重新编译人格、完整人格查询、WakeUp、Reflection 均不重建该目标。仍保留“克制、摄影兴趣、重视关系”等稳定特征。普通对话能够不借助已完成愿望维持人格。

## GP02｜Actor 背景与关系权威、编辑接口及变更传播

**目的：** Planner 使用的 Actor 配置可管理、可追溯，修改后真正影响运行。

优先扩展现有 Actor 模型，至少能表达：显示身份、简要背景、稳定兴趣／偏好、适用的时区及粗粒度所在地背景；不把生日、详细住址等非本轮必需信息变成必填字段。位置和时区可未知，不能从系统默认值推断 Actor 的现实所在地。

关系单独绑定主体 Actor 与对象 Actor，区分单向感受、当前已确认关系、互动边界和适用背景；保留人格作用域及私有／共享规则。不能把 `actor_user` 的关系默认为所有用户 Actor，也不能把对 A 的感受用于 B。

受控编辑与读取至少记录来源类型、修改者、版本、变更时间；时间性信息保留有效期或项目等价时效字段。沿用已有事实优先级，明确稳定配置、当前可变事实和旧初始化的冲突处理。不能强制以一段自由文本覆盖全部关系状态，也不能让规划 Agent自行修改对方意愿来满足新目标。

补齐正式 API：读取背景／关系、带版本编辑、查询修订，必要时区分背景编辑与关系配置修正。校验 Owner、实例、Actor 可见性和字段权限，防止跨实例／跨租户改写。前端对应 GP10，不能只增加后端结构。

配置写入成功后，可靠发布 `actor_context_changed` 或项目等价事件；记录受影响 Actor、配置版本和变更字段范围，刷新／失效派生上下文。只复核相关目标与未开始行动，不为编辑 A 唤醒全部 Actor。

Planner 提交时复核读取的关键 Actor／关系版本。配置变更后，涉及该变更的旧目标或日程行动在复核前不能用陈旧背景启动新的副作用；复用既有执行资格／待复核机制，不另建全局事务框架。无关行动不被阻塞，已发生的副作用不回滚。

编辑“对方在国外”应使不成立的近期线下行动进入调整／受阻，并从下一轮上下文消除错误同城假设。编辑关系配置应保留人工配置来源，不伪造一条对方接受、表白或同意的 ConversationEvent，不凭配置按钮完成要求实际事件的 Goal。

**完成标准：** API、页面保存、版本冲突、运行上下文、相关目标复核和执行门禁形成实际链路；Planner 对不同 Actor 使用不同事实；用户明确拒绝不被旧初始化覆盖。

## GP03｜实例级活动目标集合与统一容量提交

**目的：** 五个上限是服务端领域不变量，不是 Prompt 建议。

建立活动集合策略和版本，逻辑上至少承载实例、自动规划开关、上限、排序模式、集合版本和最近规划状态。优先复用现有 profile／policy／revision 存储，不要求新增固定表数，不复制 Goal 生命周期。

明确按实际生命周期枚举计数，不能只查询当前可见的人格或最近分页。等待、受阻仍属活动；暂停是正式生命周期命令，不能以改一个展示字段绕过计数。

统一处理所有创建即激活、候选激活、暂停恢复、重开、初始化导入、Owner 操作和 Planner 提交。超过容量返回可解释的领域错误；不能先插入第六条活动目标再异步补救。保存候选与激活的接口语义须明确，不得请求“激活”却偷偷只保存候选并返回成功。

对一次规划提供受控批量提交语义：期望集合／策略版本、各目标版本、必要的 Actor／关系版本、创建／激活／暂停建议、依赖与排序变更、来源及幂等键。模型不能写 progress、完成证据或目标终态来腾名额。

在短事务或项目等价并发机制内完成校验与持久化；激活、必要的合法暂停和排序按同一最终集合校验，不能部分成功后假报全部应用。新候选之间需要引用时使用批内稳定引用并在事务内映射真实 ID，防止依赖挂错目标。

容量、集合版本、依赖图修改、Goal 激活／暂停和并发 Owner 操作必须有统一串行化边界。禁止“先 count 后无锁 insert”；不要跨模型调用持有数据库锁。事务失败不发送执行事件，事件通过现有可靠机制在提交后产生。

同一幂等请求重复提交返回原结果，包括已创建 ID 和实际应用顺序；读取快照过期时返回明确冲突，Agent 重新查询再作有限次调整。跨实例操作互不阻塞，不以进程内互斥当作分布式保证。

所有影响活动集合的创建、激活、暂停、结束、顺序和依赖修改，都由正式命令更新集合版本；候选和相关事实更新也必须有纳入快照校验的版本或水位。不能只给 Planner 自己的写入增加版本，其他入口变了却仍接受陈旧计划。

候选采用有界队列或项目已有状态存储：建议自动候选保留上限默认 20，作为运维参数明确记录；超额时去重、拒绝新候选或淘汰低价值自动候选并审计，不删除 Owner 明确保留的内容。候选被拒绝／淘汰不会删除其历史记录，不能靠候选数量无限扩张绕过五目标设计。

**完成标准：** 活动数为四时，完成事件规划、Review、Owner 新增／恢复等并发操作最终不超过五；失败、超时重试不多建；关闭自动规划不能被旧队列任务绕过。

## GP04｜独立 GoalPlanner Agent 与插件化 Tool 契约

**目的：** 由一个独立任务维护整个活动目标集合，日程和 Reflection 不再各自补目标。

按现有 Eino 机制注册 GoalPlanner：独立 Prompt／Slot、输入契约、运行记录、工具集合、停止条件与测试入口。它可以独立启动，按需查询、消费真实结果后继续，并使用正式领域命令提交；不能用一个不执行工具的文本生成函数冒充 Agent。

首轮输入只包含实例策略、触发原因、作用域、精简人格／稳定动机、活动目标概览及必要的事实版本。通过插件化查询读取相关 Actor 背景、关系、当前生活约束、近期 Resolution、候选和相似历史目标；不得默认载入所有聊天、全部历史目标和全部 Actor 档案。

规划顺序固定为：复核已有目标 → 检查空位和实际承接能力 → 复用有意义候选／延续未满足动机 → 提出新候选 → 去重及事实检查 → 排序与依赖建议 → 正式提交 → 读取真实结果。先考虑继续已有目标，不每次生成一套新列表替换原列表。

输出结构至少说明：保留的目标；新增或复用的候选；每个候选的可观察成功标准、动机、相关 Actor、来源引用、与历史的区别、当前必要条件；排序和依赖调整；未应用建议及原因；本轮未补满原因；下次复核条件或时间。字段可复用现有 Goal 和修订结构，不存另一份独立目标实体。

候选必须有可结束的结果定义。稳定长期动机可以常驻人格摘要，但不能为了占住名额生成没有结束语义的“永远让用户开心”。“维持联系”等宏观愿望需要形成适当、可评估的当前目标，不要求全部变成当日任务或每次聊天的指标。

Tool 至少覆盖规划所需查询、候选与集合受控提交、目标／历史详情读取。优先扩展现有命名空间，仅向 Planner 注册需要的能力。Actor 配置编辑、无证据完成、任意情绪／关系更新、直接外部行动不属于 Planner 的工具权限。

运行契约区分“仅建议”和“获准应用”模式，由服务端依据触发来源、明确的 Owner 命令及自治策略确定。调用者身份、实例权限、Owner 确认和运行模式由可信执行上下文提供，不能信任模型参数中自称的 owner／approved 标记。仅建议模式不得通过调用提交 Tool 绕过关闭状态。

所有 Tool 有独立参数校验、权限、幂等与失败测试。提交工具返回实际 Goal ID、状态、集合版本、已应用顺序和拒绝原因。模型提出五条建议但服务端未激活时，Agent 不能宣称已经有五个活动目标。

区分运行状态和业务决定：调用失败不是“没有合适目标”；容量满了、等待关系事实、自治关闭、没有合理候选、保留原集合不变，都是不同的可解释结果。结果记录可采用 `applied / no_change / no_viable_candidate / awaiting_facts / blocked_by_policy` 及独立执行状态，名称以现有规范为准。

复用已有超时、最大工具轮数、输入预算和错误诊断；冲突后允许有限重读重提。持续失败进入有退避的可恢复状态，不能通过无限 Agent loop 或马上重新触发自己解决。

**完成标准：** 正式脚本 Provider 测试证明“查询工具 → 真实结果回填 → 继续决策 → 提交 → 真实结果回读”；Agent 和全部新增／变更 Tool 可分别独立运行，失败不会假报创建。

## GP05｜新目标来源、历史去重与后续目标收敛

**目的：** 有合理的新目标，也能不重复、不硬凑、不依据陈旧关系编造后续。

生成候选时综合使用稳定人格／偏好、当前活动与候选目标、完成结果、取消／放弃／拒绝历史、相关 Actor 及关系、近期事件、物品和资源、现有承诺与日程可行性。资料不足时明确未知，必要时查询；稳定兴趣本身可以支持自主形成目标，但不能用兴趣伪造已经存在的活动、作品或物品。

不用固定“关系一个、购物一个、学习一个、摄影一个”模板填满名额，不把每个普通生活活动目标化，不强制所有目标围绕用户。目标组合可以体现兴趣和生活，但不硬凑类别数量。

完成结果同时承担两个作用：证明什么需求已满足，避免重建；提供仍未解决的动机和实际后果，支持真正的新目标。完成某事并不必然意味着还要做一件类似的事。

把旧 Resolution 后直接生成后续目标的生产路径收敛到本轮规划入口。旧链保留结算、证据、关系／物品事实更新及可靠事件，只提供候选线索或请求重新规划，不再独立激活新 Goal。普通认知和 Reflection 发现的独立新愿望也按统一规则进入候选与规划，不能各自实现一套“少于五个就补齐”。

需要依赖终结结果和关系变更时，确认相关权威事实已持久化且可读，再规划后续。完成事件已到但关系更新未完成，应记录等待事实及恢复条件；不能将“表达完成”推断成“关系成立”，也不能读取仍然单向暗恋的旧状态规划相反目标。

去重至少分两层：服务端保证相同来源事件／来源项／幂等键不重复落库；语义层比较期望结果、对象 Actor、时间窗口、适用条件、成功标准和已有状态。文本 hash 或 embedding 相似度只可作候选召回，不能单独证明语义完全相同或完全不同。

比对范围包括活动、暂停、候选、已完成、取消和放弃，不只查最新五条。使用按需检索／索引与有界上下文；不要每次全量喂给模型。相同语义的活动／候选优先复用 ID，已完成的需求不改名重建，Owner 暂停／取消的意图不能通过新 ID 绕过。

允许有依据的重复周期或新需求，但必须明确新的适用窗口、条件或真正变化的结果需求。例如新的摄影专题可与已完成专题不同；“再买同一双短靴”不能只因昨天的目标结束就成立。周期推进不能通过每天重置 Goal 状态伪造进展。

关系类目标遵守对方拒绝和已确认边界。对一般恋爱愿望不能推断已选择摇光；结束表达目标后不得改名成另一种反复施压的追求任务。新目标必须符合当前真实语境，不用提升频率和亲密度补偿停滞。

为每个新目标记录生成来源、Planner run、触发事件、关联 Actor、可选前序 Goal／Resolution、简短生成理由和去重判断。理由是决策摘要，不要求保存模型私有思维过程。新目标已经被当前事实完全满足时不创建，避免“创建即完成 → 再补充”的无限循环。

**完成标准：** 已完成表达／已获得物品不会换措辞重建；相关新需求可形成独立目标；缺少依据可以保留空位，失败与无候选有区别；终结事件乱序和重复不会重复派生。

## GP06｜稳定排序、旧目标延续与人工优先级

**目的：** 旧目标默认优先，新情况可以合理调整，人工排序可持久保留。

复用现有重要性、紧迫性和期限字段，增加或明确活动集合的有效顺序及排序来源。避免另造一套与原 priority 同时生效但无法解释的分数。顺序需要持久化，分页／重启后稳定，以稳定 ID 等作为最终并列排序键。

自动模式下保留现有目标的相对连续性，新目标默认追加。截止窗口、真实机会、已作承诺、前置需求等要求调整时，记录改变前后的顺序、依据和适用条件。目标创建时间只是连续性依据之一，不是让旧目标永久压住所有新目标的唯一规则。

人工模式下，完整顺序通过带集合版本的 API 提交；Planner 返回建议，不直接覆盖。候选激活／新目标加入／目标恢复后放到合法的默认位置并保持其他人工相对顺序。实际边界在后端校验，不依赖前端拖拽状态。

Owner 明确保留／锁定的目标不能因模型判断“低收益”被自动暂停或取消。其他自动调整仍遵循现有自治授权与生命周期规则，不为腾空位随意丢弃已有承诺。无权限调整时记录建议和阻碍。

执行选择先过滤授权、生命周期、依赖、日程、事实版本与等待条件，再按有效顺序选择。排第一但不可执行要显示阻碍，不阻止后续合法目标；不能用不断失败的最高优先目标形成热循环。

排序变化不清空证据、Stage、Commitment 或已排日程，不主动打断不可撤销的执行。需要改动未开始承诺时通过现有正式命令，并保留原因。连续无进展先 Review 策略，不通过改大 priority／情绪模拟推进。

**完成标准：** 同等条件旧目标优先；有理由的新目标可调整顺序；人工顺序经过规划和重启仍保留；高优先但受阻时能够合法推进其他目标。

## GP07｜轻量 Goal 依赖、来源链与执行门禁

**目的：** 依赖可查询、可校验、真正限制执行，但不引入新的通用 DAG 工作流引擎。

在现有 Goal 关系能力上实现最小前置依赖：有向边表达“B 的新关联行动要求 A 已完成”。只允许同实例、合法作用域和当前调用者可关联的目标，不允许自依赖与环。多个前置默认 AND；本轮不新增任意表达式、跨实例编排或复杂 OR 规则。

`derived_from_goal_id / resolution_id` 或等价来源关系单独保存，不影响执行资格。UI 和 API 不得混淆“从旧目标得到灵感”与“必须先完成旧目标”。阶段内部准备继续优先用已有 Stage／Intention 表达，避免人为拆满五个名额。

依赖修改与目标集合使用一致的版本和并发控制。并发插入 A→B 与 B→A 必须至少拒绝一个，不能两次独立无锁检查都通过。批内新目标引用先解析为真实 ID，再对最终图校验；按可达范围检查而非只查前端展示的五个节点。

候选、暂停或未完成的前置目标不能满足依赖。前置取消／放弃／失效后，下游保留受阻原因，触发调整建议；不能自动改成完成或无理由删除依赖。前置满足后可靠触发下游资格复核，但仍检查授权、当前窗口和日程。

将依赖资格接入已有 Intention 创建／提升、到期触发、Worker 恢复及动作启动前校验。不能只在 Planner 生成时检查一次。已开始的动作按现有副作用契约处理，不以新依赖强行回滚。

历史目标完成只证明其当时完成条件。需要“现在仍有画笔／对方仍在同城”时还要检查当前领域事实，不能认为前置购买目标曾完成就永远拥有物品。前置被显式重开或其完成结论需复核时，下游新动作重新评估，不能继续拿失效结论启动。

识别容量占满但前置未激活的组合。Planner 优先提出释放合法名额、激活前置、将长期等待目标暂停或保留候选等方案；如存在 Owner 锁定／权限约束则返回 `capacity_dependency_blocked` 等明确原因，不突破五个、不自动暂停受保护目标。

**完成标准：** 循环和越界依赖被拒绝；未满足前置时旧触发／Worker 也不能启动；前置完成后下游可恢复；来源关联不会误阻塞执行；依赖与容量冲突可解释、可治理。

## GP08｜事件触发、周期补偿与规划恢复

**目的：** 目标全部结束后能够自动规划，平时不在每轮聊天／WakeUp 重复调用。

复用现有持久事件、任务队列或 workflow，至少接入：初始化完成后的规划请求；Goal Resolution；目标正式暂停／取消释放容量；相关 Actor／关系／生活事实重要变更；Review 请求调整；自动规划重新启用；Owner 手动请求；启动恢复和日常周期补偿。

日程只提供时间与承接约束，不成为唯一目标来源。活动目标满额时，重要背景变更仍可触发复核和排序，但不是额外生成第六个目标。普通聊天、无关配置编辑、每一次物品查询或每次 WakeUp 不无条件触发。

每实例同一时刻只应用一份有效自主规划。使用已有任务认领、租约／fencing 或等价机制，配合集合版本拒绝失效 Worker 提交；不能只靠进程内锁。模型运行期间不持有数据库长事务。

合并同一实例短时间内的多个结束事件和调整请求，记录明确事件集合与处理水位。运行期间到来的新事件保留为未处理或 dirty 状态，后续合并处理，不能因一轮结束清空全部标记而丢事件。迟到事件按入库／事件序列处理，不单靠发生时间过滤。

触发落库与业务更新之间使用已有可靠投递或可证明不会漏读的游标／对账机制。进程退出、Provider 失败、提交冲突、提交成功但响应丢失分别可恢复；幂等保证不会重复创建、重复调整和重复发启动事件。

设置可配置合并窗口、失败退避、最大重试／人工处理阈值和同一无新信息快照的冷却。可复用项目参数；新增时给出明确默认值及测试，不新增高频独立 cron。无合理候选记录复核时间，不能把空位本身当作无限重试理由。

Planner 自己产生的目标创建、排序和 run 完成事件不作为无条件再次规划触发。新目标激活转交目标推进链，只有新的实际结果／重要信息才再次请求规划，避免自激循环。

提交前重新验证自动开关、实例状态、作用域和事实版本。Owner 在规划中途关闭自动规划时旧计划不得继续激活；恢复后重新读快照。睡眠期间是否允许后台内部规划沿用现有策略，但绝不因此直接叫醒、发送消息或安排不合法当前行动。

**完成标准：** 所有目标完成后有可靠规划请求；重复事件合并、进程重启恢复、提交超时不多建；关闭开关后旧任务不越权；普通闲聊和重复无信息唤醒不会新增无意义模型调用。

## GP09｜主认知、Reflection、日程与运行上下文统一接线

**目的：** 新目标能沿现有执行链跑起来，旧模块不再维护第二套目标集合。

逐一迁移 GP00 找到的自主新目标生成入口：普通认知、Reflection、后续目标任务负责提出新愿望／来源或发起统一规划，不自行按数量补齐。初始化与 Owner 可直接使用统一受控命令，仍受容量和权限限制。原有目标推进能力继续负责 Stage／Commitment／Intention，而不是被 Planner 重写。

若现有 Tool 允许“创建 Goal 后立刻创建 Intention”，迁移时同步修改返回状态和所有调用方。保存为 candidate／等待激活时不能按 active 继续执行；需要尽快激活时进入正式即时规划／审批路径，不把购物等链路拖到夜间反思，也不绕过容量。

目标激活后用可靠事件或现有编排触发既有推进能力，生成下一步、等待条件或待规划状态。Planner 不直接写日程表，日程根据合法 Intention、承诺、依赖和有效顺序安排；依赖解除、排序调整和 Actor 变更通过正式领域事件反映。

运行时提供独立精简 Goal slot：实例活动数与上限、当前可见目标、有效顺序、阶段／下一步、依赖阻碍、等待条件、是否待复核及必要 ID。当前相关 Actor 背景与关系来自单独的上下文投影，不混回人格。

普通认知仅携带相关目标和有限必要状态；详细历史、生成依据、全部候选、依赖链与 Planner run 按需查询。可以保留有界的近期结束摘要防止认知误读，但不能把历史目标全部复制成另一个持续膨胀的 runtime memory。

完成目标从活动列表移出后，当前关系和已生效领域事实仍应可读。用户提到旧目标时能够查询其终态和依据，而不是因为 slot 不再展示就默认它没有完成。

配置变更、生命周期、排序和依赖更新后，失效对应缓存／派生投影。普通认知、WakeUp、Reflection、GoalPlanner 和 UI 对同一作用域读取相同权威版本；投影不能独立维护另一个生命周期。

保持请求预算与共享推理资源控制。普通聊天默认不多出一轮 Planner 模型调用；Planner 按需取详细信息、限制工具返回和续轮增长，不要求加载完整历史。报告提供同类场景改造前后的 token／字符数、调用数和峰值输入，避免仅缩短首轮却让工具续轮膨胀。

**完成标准：** 新目标完成激活后能进入原阶段／执行／完成链；没有待激活目标越权执行；所有运行入口读到同一状态；日常聊天不会因本轮明显增加固定模型开销。

## GP10｜目标独立管理、Actor 编辑与规划可观测性

**目的：** 用户能够独立管理目标与背景，并看懂“为什么这些目标、为什么只有三个”。

在现有 Vue／BFF／API 上实现，不要求为了本轮重建整套后台。目标管理从人格编辑中独立出来，可以复用实例详情的独立页签；初始化向导中的“初始目标”必须与人格字段分开。

目标页至少显示活动数量 `n/5`、自动规划开关、排序模式、活动目标顺序和当前执行资格；候选、暂停及终态目标可分页查看。支持正式创建／编辑、候选激活、暂停／恢复／取消、人工排序／恢复自动、依赖编辑及请求重新规划，复用已有生命周期能力。

目标详情补充生成来源、对应 Actor、前序来源 Goal／Resolution、依赖及满足情况、排序变更原因、人工保护来源、最近 Planner run。保留上一轮的标准、证据、结果与历史，不以新页面替换掉它们。

Actor 编辑页实际接通 GP02 API，分别编辑 Actor 背景与双方关系配置，展示来源和必要的版本／时效。保存后明确说明已生效或相关目标待复核；冲突要显示并支持重新加载，不能前端覆盖最新数据。UI 不允许编辑隐藏 Actor 或越过后端字段授权。

Planner 运行记录至少包括触发来源、输入范围及版本、实际决策摘要、新建／复用／保留／未激活目标、剩余空位与原因、排序／依赖调整、等待事实、实际 Tool 结果、失败分类和下一次恢复安排。不保存或展示无必要的完整私聊／模型私有思维。

区分“无合理候选”“候选被权限拦截”“等待关系事实”“容量满”“模型失败”“人工关闭自动规划”。不能把全部情况显示成空列表或永久 loading。记录与错误按真实时间倒序并有稳定次级排序。

所有页面动作调用正式服务端命令，带期望版本并处理幂等／容量错误。人工拖拽不只是更改本地数组；点击关闭自动规划后，后台在途任务也必须遵守新策略。

**完成标准：** 用户能独立编辑人格、初始目标、当前目标、Actor 背景和关系；顺序与依赖在刷新后保留；能追到一个新目标为何产生，也能解释为什么没有补满。

## GP11｜存量迁移、超额治理与旧路径清理

**目的：** 已有实例无需重建，完成历史不丢失，也不会部署后突然开始大量新目标。

设计版本化 schema 与数据迁移，覆盖策略、来源映射、Actor 配置版本、有效顺序、依赖、Planner run／请求及必要索引约束。按现有持久化风格实现，不以表数作为完成指标。

保留所有 Goal ID、状态、标准、证据、修订、Intention／Stage／Commitment 和日程关联。存量排序可用现有显式优先级加稳定创建顺序形成初值；不能把所有目标 progress 清零或统一变成 candidate。

存量人格中的初始愿望按 GP01 建立导入映射：能对应已有目标则引用已有 ID；有终态记录则不重建；语义不明确的进入可见待复核候选。回填支持 dry-run、分批、进度水位和重复执行。数据库迁移 SQL 不调用模型，必要语义回填用单独受控任务，不能在服务启动时无界同步执行。

存量 Actor 配置不确定时保持未知，不批量填入同一时区、所在地或关系状态。人工配置与历史证据保留来源，不能为通过测试伪造对方接受关系的记录。

若存量活动 Goal 已超过五个，不得静默删除、取消或任意暂停真实目标。标记容量违规并阻止新的激活／恢复；提供明确的受控治理入口，将用户确认的目标暂停或调整至不超过五个。旧事实和已在执行动作按现有规则保留，不用批量强制回滚掩盖超额。该实例在治理前明确显示未达到新容量门禁，不能宣称所有存量都已合规。

新增部署默认遵循现有自治权限；为有权限的空目标实例分批触发补规划，控制并发和调用预算，不一次性给所有历史实例发模型请求。已人工关闭自治或规划的实例保持关闭。

删除或停止调用旧人格目标注入、重复初始化、各模块独立的自动补目标逻辑、重复后继激活路径和过时测试。保留历史读取与数据兼容，不保留长期新旧双写。列出清理的生产入口和所有迁移调用方，不能只改新 Agent。

破坏性操作只在明确隔离测试环境执行。不得读取／清空生产库或删除用户容器、卷来完成验收。提供备份、部署顺序、回滚／前向修复方案；涉及旧程序回滚后可能恢复旧目标注入／绕过容量的情况必须标为风险，不能只写“回滚二进制即可”。

**完成标准：** 老实例的目标、关联和历史保持可追溯；回填可重入；超额可见且新增被拦截；部署不扩大自治权限；运行时只有一个 Goal 权威与一套自主集合规划规则。

### GP12.3 八条业务端到端验收脚本

每条脚本都记录实例、初始数据、触发方式、Goal／Actor／run ID、关键数据库或 API 断言、真实工具结果和最终状态。脚本 Provider 先用于确定性链路，真实 Provider 再评估语义质量；不要直接改目标状态代替本应验证的完成过程。

#### E2E-01｜全部目标完成后，进入新的合理目标集合

建立有明确稳定兴趣、相关 Actor 背景与合法自主权限的实例，准备三至五个可以通过测试工具或真实对话事件完成的目标。逐个经过原正式完成链结束，不直接 SQL 改 completed。

预期：结束事件触发合并规划，Planner 读取完成结果及最新 Actor 状态，生成至少一个有依据的新目标且活动总数不超过五。每个新目标有标准、来源、对象和顺序；旧目标仍在终态历史。再让其中一个新目标沿原链执行并完成，证明不是只会“补出五行数据”。

真实模型测试使用确实有多个合理新方向的输入。若模型返回无候选，审查其理由，不能把明显漏规划自动判通过。

#### E2E-02｜表达完成不复活，也不等于建立关系

初始人格文本含“性格克制，暗恋 A，等待机会表白”，经解耦形成独立目标。通过实际发送的明确表达完成该目标；先让 A 未回应或明确拒绝，验证不生成“再说一次”等重复推进，也不标记关系成立。

重启、重新编译 Working Persona、查询原始人格并继续 WakeUp，旧表达目标仍不得复活。另一个隔离子场景中，A 在对应语境明确接受，关系权威更新后才允许据此产生符合新关系的后续目标。它是关系变化后的新目标，不是重新执行表达。

#### E2E-03｜Actor 编辑改变目标可行性，而不伪造事实

目标计划近期与 A 同城线下活动，尚未启动。通过真实编辑页面将 A 的背景改为在国外，并设置适用的时区／有效背景。

预期：保存到正式 API，版本与事件更新；相关目标和未开始行动复核，原同城前提不能继续启动。Planner 依据新背景选择等待、调整或适当远程方向。对 B 的背景和目标不串改。后续单独修改关系配置，不产生虚假的对话接受事件或事件型目标完成。

#### E2E-04｜五目标容量在并发下成立

准备四个活动目标。并发触发一次自动规划、一次 Owner 创建／恢复和一次 Review／重复结束事件，并覆盖不同 Worker。

预期：最终最多五个活动目标；未获名额的操作得到明确结果。重复提交、提交成功后模拟响应丢失并恢复，不新增重复目标。界面数量、领域查询和真实数据库一致。

#### E2E-05｜旧目标优先，人工排序不被覆盖

建立几个相近条件的旧目标，再引入普通新目标，验证默认在后；加入具有真实截止的候选，验证自动调整有理由。

Owner 在页面切换人工排序并保存，再运行 Planner、激活新目标和重启。原人工相对顺序保持，Planner 的不同意见只作为建议。把第一目标设为合法等待，验证系统可执行后面具备资格的目标，而不是不断尝试第一项。

#### E2E-06｜依赖有效，容量冲突有解或明确阻碍

创建前置 A 和依赖 A 的 B。A 未完成时对 B 的旧触发和 Worker 恢复均不能启动新动作；A 正式完成后 B 被可靠复核并可在合法时机执行。

再准备五个受阻活动目标、一个未激活必要前置。验证 Planner 提出合法改组并遵守 Owner 保护；无权限调整时显示具体阻碍，不超额激活。补测并发环检查，以及“来源于已完成 C”不被误当作必须等待 C 的执行依赖。

#### E2E-07｜没有合理新目标／人工停止时，系统可以安静

隔离子场景一：没有可接受的新方向或只有两个有效候选。Planner 如实保留空位并记录复核条件；相同快照反复 WakeUp 不会无限补充、重试或硬编目标。

子场景二：Owner 在途关闭自动规划，并明确暂停某目标。规划结果迟到、重启、周期 Review 均不能自行激活或改名恢复；原既有目标执行是否继续符合开关语义。手动“立即规划”默认只给建议，明确恢复自动后再按最新状态推进。

#### E2E-08｜迁移、故障恢复与资源回归

使用包含终态历史、旧人格愿望、多个 Actor、待执行 Intention 的测试快照，执行 dry-run、正式分批迁移和中断重跑。另设超额活动实例，确认不静默删除，并通过受控治理收敛。

故障注入覆盖读取后配置变化、模型失败、提交冲突、提交成功响应丢失、关系事实晚到、Worker 重启。验证无重复目标和旧愿望复活，事件不会漏处理。记录普通聊天和 Planner 多轮工具场景的实际调用数、输入量和资源变化，不能只展示第一轮短 Prompt。

### GP12.4 交付报告与完成门禁

交付 `docs/fluctlight-goal-planner-implementation-report.md`，或仓库规范下语义相同的文档，至少包括：

| 报告部分 | 必须内容 |
|---|---|
| 实施基线 | 实际 HEAD、工作区边界、前置完成链回归结果；不把用户反馈当全量测试 |
| 逐任务映射 | GP00–GP12 的实现位置、生产入口、迁移／API／UI 变化和剩余问题 |
| 数据与语义 | 五目标计数口径、自动开关、人工顺序、依赖、来源、Actor 配置来源及版本规则 |
| Agent／Tool | 实际注册、原生 loop 运行证据、各 Tool 独立测试、提交失败消费证据 |
| 测试结果 | A01–G06 与八条 E2E 对应的真实测试名称、命令、环境、PASS／FAIL／SKIP／未运行 |
| 故障与并发 | 容量竞争、并发环、关闭竞争、重复请求、响应丢失和晚到事实的断言 |
| 存量与清理 | 来源回填数量、超额实例处置、保留关联、旧自主生成／人格注入入口清理清单 |
| 运行开销 | 同类场景改造前后调用数、token／字符量、工具续轮峰值及限流／退避默认值 |
| 实际样例 | 一个“全部完成后补充”的完整过程、一个“有空位但不生成”的过程及依据 |
| 部署与限制 | 开关、备份、迁移、回滚／前向修复、真实 Provider 未验证内容及重跑方式 |

最终验收必须同时满足：原目标完成链不退化；初始愿望不复活；Actor 可编辑并影响运行；所有激活入口遵守实例最多五个；Planner 可独立查询与真实提交；历史与新需求可区分；人工控制、排序和依赖实际生效；触发可恢复且不自激；新目标能够沿原执行链完成。

如真实 Provider 或部分环境无法运行，提交已经完成的实现与可复现实验，明确缺口，不把 SKIP 算通过，不为了交付编造日志、事件、证据或截图。不能将“代码和模型已建好，但生产调用方、界面或迁移未接通”表述为本轮完成。

## 3. 给 Codex 的收口要求

本轮不再扩大到新的人格演化引擎、奖励／惩罚机制、通用图执行引擎、全量事件溯源、长期记忆重构、现实支付或整套工作流替换。

先保证最短真实路径：已有目标正式完成 → 持久规划请求 → GoalPlanner 读最新目标／人格／Actor／结果 → 受控生成与激活 → 原推进链执行 → 原证据链完成。随后验证这条路径在手动控制、容量、依赖、故障、迁移和上下文约束下仍然成立。

不要为使测试通过而把合理不生成改成固定填满五个，也不要以“允许不生成”为理由让输入充分的所有场景都 no-op。决策必须有事实依据，系统必须能解释和追溯。
