# Fluctlight 目标闭环实施任务书

## 0. 执行要求与完成定义

你是本地 Codex，请在当前 `local-ai-companion` 仓库中实施本任务。目标是补齐 Fluctlight 运行时 Goal 的正确性、持续推进和治理闭环，**不是修改 Trellis 开发任务系统，也不是整体重构**。按仓库现有规范创建或更新实施任务，完成源码、迁移、测试与验收报告；不要只输出设计建议或检查结论。

输入基线是用户提供的 **2026-10-07、`master`、`ee1e468`** 检查报告。该提交仅供定位，不要求切换、回退或覆盖当前分支。先检查实际 HEAD、工作区与已落地功能；报告中的缺陷必须结合当前代码核实，已经修好的部分补回归，不再重复实现。

用户要的最终行为是：

> 摇光保有长期目标，按当前阶段形成适当的短期推进目标，寻找实际机会并执行；根据真实结果判断推进、受阻、无变化或完成；周期复盘并调整策略。事件已经实际达成时能够识别和结算，不会一直等待下一次反思；原目标结束后，根据尚未解决的动机决定是否产生后续目标，而不是无条件生成任务。

两条闭环都必须成立：

- **执行闭环：** Goal → 当前 Stage → 短期 Commitment → Intention → Action → 实际 Outcome／对话事件／领域事实 → Evaluation → 进度、阶段转换、完成或下一步。
- **治理闭环：** 周期 Review → 该周期有没有推进、没有推进的原因、策略是否有效 → 继续、等待、调整、暂停或结束 → 下个周期读取最新权威状态。

简单目标允许直接关联 Intention，不强制套入 Stage、Commitment；复杂或长期目标必须具备阶段与短期推进能力。每日小目标是可选时间范围，**不是每天必须完成的配额**。

### 0.1 不可突破的边界

保留现有 Goal／Intention 权威模型、版本校验、幂等、修订历史、日程、生活活动、人格权限和自治权限。新增的是缺失的领域能力与接线，不替换整个 runtime、BFF、Temporal、状态系统或记忆系统。

沿用现有 Eino、Agent／Task、插件化 Tool 机制。需要调用工具并消费结果的独立任务使用现有原生 Agent loop；只做结构化语义判断的任务可使用现有 Task，不为此另造循环。Tool 必须能脱离 Agent 独立执行和测试。

同一事实只能有一条权威写入路径。购物专用链、通用 Outcome、Reflection 和 Owner 操作最终应收敛到统一领域提交规则；不保留两套互相覆盖的完成逻辑。允许版本化数据迁移，不保留长期运行的旧行为兼容分支。

目标推进不能覆写 Core Persona，不能靠提高亲密度、焦虑、重要性或行动频率伪造进展。继续尊重人格作用域、共享目标作用域、Actor 身份、日程位置、睡眠状态、用户拒绝和既有执行授权。

本任务中的购物指现有**虚拟生活获取链**，不是新增现实支付权限。不能通过目标权限绕过已有工具授权、购买确认或浏览器日程写入边界。

### 0.2 四个最重要的语义约束

**执行成功不等于目标完成。** 消息发出、工具调用成功、异步任务提交、模型宣称完成，分别不等于对方认可、物品获得、异步结果已生成、成功标准满足。

**没有调用工具也可能有有效证据。** 用户真实对话、已经落库的双方互动、领域事实，可能证明某项标准；它们不一定事先绑定 Goal 或 Intention。必须支持候选关联和复核，不能要求模型伪造 ActionOutcome 来适配旧接口。

**小目标完成不自动换算长期目标进度。** 完成一次试探只能证明试探发生；是否改善关系、获取新信息或满足阶段条件，需要独立评估。

**保留原目标含义。** “明确表达心意”与“建立双方确认的恋爱关系”是不同目标。不能把前者偷偷升级成后者，再声称表白后目标无法完成。

## G01｜Goal 生命周期与关联行动统一约束

**目的：** 目标暂停或结束后，不再启动新的关联行动；已在执行的行动有明确处理语义。

实现统一的执行资格检查，至少涵盖 Goal 状态、Intention 状态、所属 Actor／人格作用域、授权、期限、当前版本及本次 Attempt。新建意图、资格提升、到期投递、Worker 恢复、工具副作用入口、生活活动启动均须使用同一套规则。

暂停、恢复、取消、放弃等生命周期命令统一通过领域服务执行，包含修订、关联意图处理和待触发工作的失效／恢复。恢复时重新校验日程、到期时间和权限，不直接复用已经失效的旧触发。

明确“行动已开始”的可审计边界。生命周期变更与执行许可领取必须通过现有事务、版本或等价串行化机制协调，不能只在很早之前读取一次 Goal 状态。异步任务实际启动前仍须验证许可没有失效。不可把一次检查描述为跨数据库与外部系统的原子执行。

已启动的动作按能力契约处理：可安全取消的请求取消；不可撤销或外部结果未明的进入等待／核对；已产生的真实结果照常记录。暂停／取消不能删除真实副作用，也不能把晚到结果变成新的自动推进指令。

默认治理策略：只有 `active` Goal 自动推进阶段与下一步。其他状态仍接收事实和审计记录，但不自动恢复、不新增关联行动。`cancelled`／`abandoned` 不因迟到成功回调自动改为完成；暂停期间已满足标准的结果可记为待结算，交由恢复或明确结束命令处理。

**完成标准：** 暂停、取消、执行启动并发测试通过；旧消息、旧 workflow、恢复 Worker 均不能绕过门禁。Owner、Tool、Reflection 改状态的效果一致。

## G02｜Attempt 完整结算、工具前失败恢复与重试

**目的：** 每次执行都有可追溯结果；模型或基础设施故障不会留下永久 `due`、永久 `pending`。

在到期认知被执行器认领时就建立或复用本次 Attempt，不要等第一个工具结果出现后才创建尝试记录。区分 Intention 的逻辑生命周期与一次 Attempt 的状态，不能用 inbox 的失败状态替代意图结算。

覆盖模型请求失败、工具前校验失败、超时、进程退出、取消、无动作决定、工具同步完成、异步提交、异步终态等所有出口。每个已认领 Attempt 都必须有终态，或有明确等待对象、截止时间和恢复策略。正常等待、没有机会、睡眠门禁不一律按执行失败处理。

修复报告中的工具前失败路径：认知 inbox 标为失败时，同时完成本次 Attempt 的失败记录，并按分类将 Intention 交回可恢复状态、等待核对或终止。不能只安排一次普通 WakeUp 并假设意图会恢复。

同步与异步结果严格分开：同步 ACTION 按实际结果结算，不得因“本轮调用过 Tool”统一置为 `pending`；异步 ACTION 记录关联操作／回调／超时；纯 QUERY、只生成计划、`no_op` 不能被认定为目标行动成功。目标本身是获取信息时，可由真实查询结果证明对应的信息型标准，但仍须评估。

实现可配置重试退避、抖动、尝试上限与错误分类，并复用现有调度设施。`next_attempt_at` 必须参与触发资格；时间条件已过期时不得立即重新投递形成热循环。权限拒绝、明确用户拒绝、硬截止到期不能靠自动重试绕过。

保留本次逻辑操作标识和每次 Attempt 标识。重复触发、重复回调、恢复重放不得重复副作用。超时但副作用未知时先核对真实操作状态；不能直接重新购买、重新发送或重新入库。

**完成标准：** 用真实测试数据库和可控故障点证明工具前失败能恢复；重复事件只结算一次；同步动作不悬空；异步丢回调能进入可观察的超时／核对；停止重试的原因可查看。

## G03｜成功标准版本与完成证据一致性

**目的：** 修复“按旧标准完成，再覆盖新标准”的一致性缺陷。

为成功标准保留稳定标识及版本，优先复用已有版本机制。Evaluation 必须记录评估的目标版本、成功标准版本、证据集合和评估策略版本。

采用明确的两步语义：**变更成功标准与提交完成判定不能在同一候选更新中混合执行**。先提交标准修订，随后对新版本重新评估。混合请求返回明确的校验错误，而不是选择某个隐含执行顺序。

提交评估时校验期望版本。标准或相关状态已改变则拒绝陈旧提交，并重新排队评估，不允许旧评估覆盖新目标。新标准可复用既有真实证据，但必须重新确认适用性；不能沿用旧 `progress=1`。

对每项标准记录 `satisfied / not_satisfied / unknown` 等明确判定及对应证据。必要标准缺证据时不能完成；必选／可选、全部满足／替代满足等完成逻辑必须结构化并由服务端校验，不以自由文本和浮点进度判断。

上述成功标准版本、证据和陈旧提交规则同样适用于 Stage 与 Commitment，不只适用于顶层 Goal。只实现当前需要的简单结构化完成条件，不引入通用规则语言或表达式引擎。

已经完成的目标禁止普通编辑直接改变成功定义。需要修正时走显式修订／重开或创建后续目标，保留旧完成结论和当时依据。证据被纠正或失效后，活动目标重新评估；已结束目标产生需复核记录，不静默改写历史或自动衍生新目标。

**完成标准：** “买到画笔”完成时同时加入“完成一幅画”会被拒绝；新标准生效后必须补充相应证据。标准编辑与评估并发、重复评估、证据失效都有测试。

## G04｜Stage 与短期 Commitment 模型及持久化

**目的：** 长期目标能够分阶段推进，不再每轮只看到一句宏观愿望。

保留 Goal 作为长期／独立目标。增加明确的 `GoalStage` 与 `GoalCommitment` 逻辑模型，并复用现有领域编码与持久化习惯；不能把所有层级塞成没有类型边界的递归 Goal。Evaluation、Review 可以复用现有事件／修订存储，不以“必须新增固定数量表”为实施指标。

最低语义如下：

| 对象 | 至少承载的内容 |
|---|---|
| Goal | 原始动机、期望结果、成功标准及版本、生命周期、作用域、当前阶段、期限策略 |
| GoalStage | 所属目标、阶段目的、进入／完成／退出依据、当前策略、依赖、状态和版本 |
| GoalCommitment | 所属目标及可选阶段、短期预期结果、完成标准、时间窗口、机会条件、状态、阻碍 |
| Intention | 继续承载具体行动、执行条件、权限与尝试；可关联 Goal、Stage、Commitment |

关联必须验证同一实例、合法 Actor／人格作用域和父级一致性。不能将 A 的 Intention 关联到 B 的阶段，也不能让人格切换后本应共享的目标消失或私有人格目标泄露。

默认聚焦一个当前推进阶段；模型可按实际结果调整、合并或跳过尚未满足的计划阶段，不要求强行走完整套预设剧情。跳过阶段记录理由，不把“跳过”伪记为“完成”。真正需要并行阶段时再按现有能力表达，不引入通用 DAG 引擎。

Commitment 可按今天、未来几天、下次合适机会或指定时间段设定。跨日仍有意义的承诺继续存在；窗口结束后复核延期、替换或放弃，不能每天清空，也不能所有长期目标每天自动各生成一个子目标。

子目标完成不使用固定百分比推高父级进度。一个子目标可仅减少不确定性、验证策略或暴露阻碍；父目标是否推进仍由 G06 评估。

**完成标准：** 长期目标能形成并读回 Stage／Commitment；简单购物目标仍可走短链；重启、跨日、人格切换和父子关联校验通过。历史 Goal 和 Intention 不因新增层级失效。

## G05｜统一证据入口，补齐“对话已达成但没有完成”链路

**目的：** 通用目标既能消费真实工具结果，也能消费没有预绑定 Intention 的有效对话和领域事实。

建立统一证据引用／适配机制。至少覆盖：终态 ActionOutcome、已持久化且确实发生的 ConversationEvent、物品／生活活动等权威领域事实。证据以可重新读取的来源记录为准，不复制模型自述作为事实。

每条关联至少记录目标、可选阶段／承诺、来源类型与来源 ID、发生时间、入库时间、主体与对象、来源版本、候选／确认／拒绝状态及关联理由。对话证据不能伪装成工具结果，也不能补造一条不存在的执行尝试。

扩展旧 `ApplyGoalProgress` 的调用体系时，保留“真实、合法、适用、绑定正确”的校验。推荐把通用校验和提交下沉到统一领域入口，由旧 Outcome 路径与新增对话／领域事实适配器进入。不能简单移除 `completed` 和 Goal 关联检查，让任何文本都能更新进度。

证据分级必须体现来源的能力：用户直接表达可以证明其当前说法或意愿，不一定证明另一 Actor 的动作或库存；用户转述、引用、假设和未来计划不等于已发生事实。查询失败、不存在的物品 ID、模型草稿、未发送消息均不能证明完成。失败结果可证明阻碍或反证，不能直接证明成功。

对未绑定目标的事件，新增“候选关联 → 读取真实来源 → 语义评估 → 校验提交”路径。候选生成复用当前认知或聚焦的评估任务，只围绕相关作用域内的目标处理，不对所有历史目标逐条发起模型调用。漏掉的事件由增量 Review／对账补读。

需要支持以下直达结算：用户引导摇光在普通聊天中实际完成了目标事件，即使没有事先安排的 Intention，也能评估原 Goal 的成功标准；确已全部满足时直接完成，而不是强制重演计划中的 Stage 或先补一条虚假行动。

**完成标准：** “已实际表达心意，但未预先绑定 Intention”能够完成“表达心意”目标；普通闲聊、引用的表白、未发送草稿不能完成；不同 Actor、会话或实例的无关证据被拒绝。事件重复与乱序到达不会重复计数。

## G06｜结果驱动的 Goal Evaluation 与统一结算

**目的：** 结果发生后有可靠、可观察的评估，而不是所有进度等待夜间 Reflection。

在真实 Outcome、相关对话、领域事实及标准修订提交后，接入持久化评估请求。复用现有事件、任务或 workflow 设施；事件与评估任务之间必须有可恢复的持久联系。可使用既有事务消息／outbox，或可证明不会漏读的游标与对账机制，不用进程内 fire-and-forget 作为唯一保障。

评估请求允许合并相邻事件、按目标去重和限流，但要保留来源范围与处理水位。不能仅依赖 `occurred_at > last_review_at`，否则迟到事件会被漏掉。模型失败保留待评估状态与重试，不得把“没有评估成功”记录为“没有进展”。

统一结构化输出至少包含：

| 字段组 | 语义 |
|---|---|
| 版本与范围 | Goal／标准版本、事件范围、证据引用、评估策略版本 |
| 逐条标准判断 | 满足／不满足／未知、正反证据、简短理由 |
| 本次影响 | `progressed / no_change / blocked / regressed / needs_evidence / completed`，可映射到项目等价枚举 |
| 后续建议 | 当前阻碍、等待条件、下一步建议、是否需要重新规划 |
| 执行状态 | 待评估、评估中、成功、失败、下次重试及错误原因 |

区分评估任务状态、目标生命周期与本次影响，不能把三者塞进一个 `status` 字段。

确定性标准由代码按权威领域结果验证；开放语义标准由模型给出候选判断，服务端校验来源、主体、版本、作用域和提交条件。结构校验不能被描述为已经解决所有语义误判；不确定时返回 `unknown / needs_evidence`，保留真实模型验收。

逐条标准的满足情况是主要进展事实。数字 `progress` 只做有明确依据的投影，不能按消息数、尝试数、天数或已完成 Commitment 数自动累加。不适合百分比的关系目标显示阶段、标准与证据，不强造百分比。

Stage、Commitment 与 Goal 分别判断是否达成。父 Goal 的必要标准已被直接证明时，不得因为还有旧计划未执行而卡住完成；应在完成时撤销／替代尚未开始且已无必要的计划，正在执行的动作按 G01 处理。

提交标准判定、进展、修订、阶段转换事件与待处理下一步时，使用现有事务与幂等机制。重复证据即使被多个批次引用，也不能重复增长进展或触发多个后继阶段。版本冲突重评，不覆盖新状态。

购物专用结算、通用结果和 Reflection 必须收敛到这一提交入口。生活活动适配器保留“实际获取物品才能证明获得”等领域校验，但不能继续独立写一个与通用评估冲突的 Goal 完成状态。

**完成标准：** 结果已产生、尚未到周期反思时，目标也能完成或明确显示待评估原因。多标准、失败、迟到结果、标准变更、重复回调和进程重启均能收敛。

## G07｜当前阶段、短期推进、机会响应与后续目标

**目的：** Goal 不仅能被正确结束，还能持续产生合适的下一步。

实现或补齐目标推进任务，读取当前 Goal、Stage、Commitment、已评估结果、阻碍、现实背景及执行资格，输出下一步候选。只在目标刚激活、阶段完成、承诺结束、有效结果到达、阻碍解除、出现相关机会或 Review 判断需调整时运行。

对可推进的活动目标，不允许长期既没有行动、也没有等待条件、还没有复核时间。投影中至少存在一种可解释状态：可执行下一步、已安排意图、正在执行、等待明确机会／外部结果、受阻及解除条件、暂停／结束，或待规划及其失败原因。不能用空 `next_step` 掩盖停滞。

长期目标生成当前阶段与适当的短期承诺，不预先铺满未来几十天的剧情。下一步要描述可观察结果，不能只写“继续努力”“适时推进关系”。但也不能把每次普通聊天强制改成目标规划流程。

普通认知与 WakeUp 读取精简的目标上下文；在有相关事件时可以自然推进现有目标。机会识别基于当前目标、阶段、人格和对话语义，不能用固定关键词规则硬编码“用户说想要女朋友就必须表白”。可以试探、明确表达、询问或有依据地暂缓；用户表达一般恋爱愿望并不证明其已经选择摇光。

发生机会时，执行仍经 Intention／Tool 的既有权限与日程边界；在普通回复中发生的真实推进事件则经 G05 入证。不强制所有自然互动先走一遍日程安排。

阶段完成后复核父 Goal，再决定进入下一阶段、调整路径或结束。只做有限次数的同批次转换，后续工作通过持久事件继续，避免“完成 → 新阶段 → 新目标”在一次模型调用中无界递归。

目标终结产生一次可追溯的 Resolution，记录结果、标准版本、依据、残留动机及后续处置。只有仍有未解决且符合人格的上层动机时才产生后续目标候选，并按现有自治授权激活。不得无条件补一个新目标，也不得用不同措辞重复创建已完成目标。

两个语义示例必须正确：

| 原目标与结果 | 应有结算 |
|---|---|
| “向对方表达心意”，已实际明确表达，但对方未接受 | 表达目标可完成；关系未确认；可记录拒绝／等待，不继续重复表白 |
| “建立双方确认的恋爱关系”，只有摇光表白 | 行为完成；父 Goal 尚未完成，等待明确且适用的对方回应 |
| 双方在该语境中明确确认关系 | 评估成功标准后完成关系目标；通过现有关系状态权威入口更新，并保留证据 |
| 获得短靴，物品已真实入库 | 获得目标完成；不强行生成“穿靴子”或“再买一双”的后续目标 |

关系事实只能修改对应 Actor 关系的有效动态状态，不能写成用户现实生活状态，也不能覆盖初始化人格原文。跨领域更新复用现有事务／可靠事件机制，失败可重试且不能重复产生后续目标。

**完成标准：** 有下一步、有结果后的调整、有阶段转换、有明确结束，并能停止。目标推进不会绕过用户拒绝、睡眠、异地事实、人格或权限。

## G08｜Reflection／Daily Review、停滞治理与期限语义

**目的：** 回答“今天有没有推进，为什么，接下来怎么办”，而不是只生成一段反思文字。

Reflection 与 Daily Review 使用统一的 Goal Review 能力。Review 先读取未评估／新到证据并触发必要的 G06 补偿，再分析当前周期；不能仅根据旧进度和摘要判断，也不能另造一套完成写入路径。

持久化 Review 的目标、周期与时区、事实处理水位、总体影响、真实证据、阻碍、策略效果、可能错失的机会、下一步、下次复核时间及修订关联。重复执行同一周期不重复累计停滞次数或新增 Commitment。

将未推进原因明确区分为：没有机会、时机未到、等待外部结果、已有行动但无有效进展、存在真实阻碍、可能错失可行机会、评估失败未完成。不能把用户未上线、明确拒绝、睡眠或系统故障等价成“摇光不努力”。

错失机会判断必须引用原事件、当时阶段及可行替代动作；模型只给语义判断候选。不因一句“想谈恋爱”就断言对方喜欢摇光，也不把所有未暧昧回复自动标为失败。按人格克制地暂缓可以合理，但长期没有有效理由的回避必须进入策略复核。

原先设想的“惩罚”按策略治理落地：连续有可行机会却未行动，要求更明确的下一步；连续尝试但无效，调整策略而非提高调用频率；真实受阻，建立等待／解除条件；无机会则合理顺延。计数与阈值可配置、可查看、可重置，不直接污染情绪或自动增加亲密度。

Review 不硬性要求每天推进所有目标。复用现有日常／周期调度；对没有新信息的目标可以确定性记录继续等待，不为每个目标每几分钟单独调用一次模型。保留事件驱动评估与定期补偿的分工。

Goal deadline 增加或明确 `soft / hard` 策略。历史未指定期限语义的目标默认软期限，迁移中不直接取消：软期限到达产生超期复核，记录延长、调整、暂停或放弃及原因；硬期限到达后禁止启动新的相关行动，并处理未开始的意图，正在执行的行动遵守 G01。超期本身不是完成证据。

迟到证据按真实发生时间和来源可信度判断是否在窗口内达成，不能仅以评估时间判为逾期；硬期限修改需要授权与审计，不能由重试器自动延长。

时间契约统一：时刻持久化为 UTC；跨服务交换统一使用带时区的 RFC 3339，默认 UTC `Z`，不得混入无时区时间。日历日期字段可单独使用 `YYYY-MM-DD`，并明确其所属 IANA 时区。每日 Review 按目标所属 Actor 的本地日界线计算起止，再转换为 UTC；用户时区、服务器时区不能覆盖 Actor 时区，跨日与夏令时不能简单按固定 24 小时拼接。

**完成标准：** 能看到某天真实推进、等待、阻碍和策略调整；重跑不重复惩罚；软硬期限、跨时区和迟到事件行为确定；复盘不会强迫角色违背人格或对方拒绝。

## G09｜通用执行投影、Prompt／Slot 与插件化接入

**目的：** 下一轮实际读到“做过什么、结果如何、为什么停住、接下来怎么办”。

修复 `readGoalExecutionStateWith` 仅依赖生活活动记录的问题。统一读取通用 Attempt、ActionOutcome、对话／领域证据、Evaluation 和 Review；生活活动是其中一种来源，不再是唯一结果权威。修正 `running`／`in_progress` 等真实状态与展示阶段的映射不一致。

精简运行投影至少提供：Goal 的有效目的与状态、当前 Stage、相关 Commitment、未满足的关键标准、最近尝试和结果、评估是否待处理、最近影响、阻碍／等待条件、下一步、下一复核或执行时机，以及必要的来源 ID。没有行动尝试但存在有效对话证据时，不能显示为“从未发生任何结果”。

所有字段从同一权威状态派生，Projection 不自增、不存第二套独立生命周期。详细历史、全部证据与完整阶段计划通过查询 Tool 或 Owner 页面按需读取，不把整棵目标树和全部复盘塞进常驻上下文。

修改普通认知、WakeUp、Reflection、Daily Review 与相关目标任务的 Prompt／Slot 装配。必须区分目标、计划、行动、结果与评价；有效动态状态优先于旧人格中的初始化愿望。例如已经完成表达目标后，运行时不再把“仍未表白、等待表白”当作当前事实。

沿用现有上下文预算、摘要去重、作用域过滤和按需检索；不得新增每轮强制规划／评估调用，也不能以减少 token 为由把关键当前状态截掉。记录新增字段与 Agent 调用带来的请求体和调用次数变化，特别检查工具续轮。

查询、创建／调整、暂停／恢复、结果评估等 Tool 能力优先扩展已有注册入口。查询不得产生隐藏写入；写入声明副作用、权限、幂等与错误契约。模型读取 Tool 真实结果后继续决策，不能从回复正文猜测伪造的 `tool_calls` 或宣布尚未成功的修改。

**完成标准：** 普通对话、WakeUp 和 Reflection 对同一目标读到一致状态；工具与 Agent 能独立测试；新增能力不会重启一套旧式自研循环，也不会使上下文重新膨胀。

## G10｜Owner 生命周期管理与历史追溯

**目的：** Owner 能管理目标，并解释“为什么没有完成”。

新增或补齐目标级 API 与界面。至少支持按状态查询当前／历史目标、查看详情、受控新建与编辑、暂停、恢复、取消，以及明确发起重新评估。放弃／期限调整等操作按现有权限模型表达。不能直接编辑数据库绕过版本、证据和治理规则。

详情展示：目的与动机、逐条成功标准及版本、Stage／Commitment、关联意图与日程、最近尝试、来源证据、评估与复核状态、阻碍、下一步、期限、重试情况、完成依据及修订历史。一次失败应能追到对应运行与诊断，一次完成应能追到具体标准和事实来源。

完成、取消、放弃的目标有独立可分页历史入口，不能仅复用 `candidate / active / paused` 的 `agencyProfile`。历史、运行与目标诊断按实际时间倒序并有稳定次级排序，避免旧错误排在新错误之上。

所有操作通过 G01／G03／G06 的统一领域命令，校验实例、Owner、Actor／人格作用域、版本与幂等；无权限页面可以只读，但后端必须独立校验。标准编辑不得隐式保留不成立的完成状态。

保留浏览器日程写入拒绝任意 `intentionId / actionPlan` 的既有边界。需要关联时增加受控查询／命令或只读跳转，不能简单删除原限制。

不新增“无证据强制完成”入口。需要人工补充观察时，以有身份、有来源类型、有审计的人工证据进入评估，不能伪造 Tool Outcome。Owner 人工暂停与模型主动调整的来源必须可区分。

**完成标准：** Owner 可管理一个目标的完整生命周期，结束后仍可查回；所有按钮实际调用正式 API，相关领域状态与后续执行一致，而不是仅在前端改显示。

## G11｜数据迁移、存量修复与旧路径清理

**目的：** 新机制接入真实存量，而不是只在新建目标上生效。

从 G04 的第一个模型变更开始设计版本化迁移，覆盖字段、索引、关联、评估／复核记录与必要唯一约束。按当前仓库迁移规范实施，不猜测表名或手工修改开发者生产数据。

存量 Goal 保留原描述、标准、状态、证据、Intention 关联和历史。可以补稳定标准 ID、版本与新投影；不能凭空生成历史阶段完成证据。原来已完成但证据无法验证的目标保留历史并标记待审查，不批量伪造“通过”，也不无提示重开。

旧长期目标缺 Stage／Commitment 时进入受控规划队列，结合原定义形成候选；迁移 SQL 不调用模型，不给所有目标灌入同一套阶段模板。简单目标不强制补层级。

对永久 `due / pending`、陈旧 Attempt、待复核标准、未处理结果和断开的关联提供可重复执行的检查与修复入口。修复前重新检查真实执行结果和 Goal 状态，不能批量重试未知副作用或复活已取消目标。修复记录来源、前后状态和原因。

所有回填与补评支持分批、进度水位、重入和停止，避免一次部署为全部历史目标触发大量模型调用。迁移结果以数量和抽样关联核验，不只看 SQL 执行成功。

迁移所有生产调用方到统一领域提交规则，删除或明确停止调用旧的独立完成分支、过时 Prompt、重复投影、无效枚举映射和失效测试。数据库迁移兼容不等于保留两套长期运行逻辑。

只对明确隔离的测试环境自动执行破坏性操作。为真实部署提供备份、迁移和回滚／前向修复说明，未获授权不得更改生产数据或清理用户已有容器、卷和数据库。

**完成标准：** 存量数据能加载、查询、恢复和推进；没有伪造证据；回填可中断重跑；生产写入入口唯一；旧 Goal／Intention 关联与历史可追溯。

## G12｜分层测试、真实数据库与端到端验收

**目的：** 验证真实调用链，而不是依赖对象存在、HTTP 200、父测试 PASS 或模型自述。

### G12.1 验收层级

| 层级 | 必须证明的内容 | 不能替代的内容 |
|---|---|---|
| 领域单测 | 状态机、证据适用性、标准版本、期限、幂等、父子结算 | 数据库事务、事件恢复与模型语义 |
| 隔离 PostgreSQL 集成 | 真迁移、持久化、事务并发、重复消费、重启后状态 | 真实 Provider 决策 |
| 正式 Agent／Tool 链路＋脚本 Provider | 原生 loop 确实请求 Tool、执行、回填、继续；Tool 可独立调用 | 真实模型是否自然识别机会和正确理解回应 |
| Worker／故障恢复联合测试 | 到期触发、工作领取、失败、恢复、重试、回调、暂停竞争 | 真实模型质量与真实媒体质量 |
| 真实 Provider 场景验收 | 自然行为、语义证据、人格与目标一致性、上下文读取 | 长期稳定性，不能用一次对话成功保证所有情况 |

如果可以安全使用项目测试设施，自动准备隔离 PostgreSQL 并执行数据库场景。`GO_CORE_TEST_DATABASE_URL` 未设置不是默认跳过理由；应先查看已有测试环境启动方式。确实无法运行时记录阻塞原因与完整重跑命令，不访问或清空生产库凑验收。

新增和受影响的独立 Agent／Task／Tool 都要有能走通逻辑的测试。需要工具的 Agent 至少覆盖：生成真实工具调用 → 执行 → 回填真实结果 → 模型继续 → 提交合法状态；Tool 覆盖独立成功、失败、权限、幂等与参数校验，不依赖 Agent 暗中预处理。

### G12.2 必测用例矩阵

下列编号应映射到真实测试名称或可复现验收脚本，不能只写进文档。

#### A. 执行正确性与故障恢复

| ID | 场景 | 核心断言 |
|---|---|---|
| A01 | Goal 暂停后旧意图到期 | 不启动新副作用；有明确抑制原因 |
| A02 | Goal 取消与 Worker 启动竞争 | 执行许可边界一致；无越权新动作 |
| A03 | 暂停后恢复，原窗口已过 | 重新校验并调整或结束，不盲目启动旧计划 |
| A04 | 首个 Tool 前 Provider 失败 | Attempt 可结算；Intention 可按策略恢复，不永久 due |
| A05 | 仅同步 ACTION | 实际结果可结算，不永久 pending |
| A06 | 仅 QUERY、仅计划或 no_op | 不误记业务行动成功；信息型标准另按真实查询评估 |
| A07 | 异步成功、失败、丢回调、迟到回调 | 关联正确，有超时／核对，迟到不复活终止目标 |
| A08 | 同一事件、工作与回调重复投递 | 不重复副作用、入库、进展或下一阶段 |

### G12.3 三条关键业务端到端脚本

**脚本一：事件已经发生，目标必须能完成。**

初始目标明确设为“在适当时机，向 actor_user 清楚表达自己的心意”，成功标准仅要求实际明确表达，不能改成对方接受。不给它事先绑定某个表白 Intention。用户通过普通对话引导，摇光实际发送了清晰表达；系统从正式对话记录关联目标并完成评估，Goal 进入完成，证据可查。后续 WakeUp 不再说“还没表白，等待机会”。另测只起草未发送、用户引用他人的表白，均不完成。

这条是本次用户报告的核心回归，不能被“模拟一个成功 Outcome 直接调用 ApplyGoalProgress”替代。

**脚本二：双方关系目标，不能把表达当成接受。**

初始目标是“建立双方明确确认的恋爱关系”，成功标准显式要求双方确认。用户说“想要女朋友”时，只允许作为相关机会或开放信号，不能直接完成；摇光表达后对方沉默，也不完成。在对该表达的明确回应中，用户确认接受，才评估相应标准，并通过现有关系状态入口更新双方状态。用户回应含糊、引用台词、转述、否定或明确拒绝时，分别记录未知／反证，不硬判成功。完成后仅在有合理动机时生成不同的后续目标。

脚本 Provider 用于确定性接线；真实 Provider 验收检查语义与人格表现，不匹配固定句子，也不以一次成功声称长期可靠。

**脚本三：缺少物品 → 想购买 → 安排行程 → 获取 → 入库 → 可使用。**

摇光想要短靴，查询衣柜确认没有。形成购买意愿／目标，经已有工具与日程能力安排合适购物活动。实际获取工具／领域结算成功并有权威物品 ID 后，目标完成。未入库、Tool 失败或查不到物品 ID 时，不得提前完成，不得成为当前穿着或图像请求中的既有物品。

购买完成与换装分开；买到不等于已经穿上。重试不能重复入库，取消目标后旧日程不能继续购买。真实媒体服务不可用时，至少验证生成请求使用的物品／着装快照；报告明确未做真实媒体验收，不把请求构造测试写成图片质量通过。

## G13｜交付、证据报告与最终门禁

### 必须交付

交付实际实现代码、版本化迁移、受影响 Prompt／Tool 注册与 API／UI、单测和集成／E2E 脚本、必要配置及操作说明。报告可建议命名为 `docs/fluctlight-goal-closed-loop-implementation-report.md`；若仓库已有等价正式文档则更新并说明。

报告至少包含以下内容：

| 项目 | 要求 |
|---|---|
| 实际基线 | 实施前后提交、分支、与用户报告的差异、未覆盖的本地修改 |
| 任务映射 | G00–G13 的实现状态、代码位置、未完成项及原因 |
| 链路说明 | 触发、真实结果、证据、评估、提交、下一步、Review 与 Owner 的实际调用入口 |
| 数据变更 | 迁移、唯一约束、回填、兼容数据处理和回滚／前向修复方法 |
| 测试记录 | 完整命令、实际环境、PASS／FAIL／SKIP 数量，分别列到关键子场景 |
| 故障证据 | 工具前失败、评估丢失窗口、重复回调、暂停竞争、重启恢复的记录 |
| 场景证据 | 三条 E2E 的目标、证据、标准版本、评估、最终状态及可追溯 ID |
| 性能与上下文 | 新增模型调用条件、合并／退避效果、代表性 token／请求体变化 |
| 剩余风险 | 真实模型、Worker 联合、真实媒体等实际未执行部分及重跑方法 |

不得只统计测试父级 `PASS`；所有业务子测试 `SKIP` 的场景必须计为未验证。脚本 Provider、mock、领域单测不能写成真实模型通过。没有环境就标记 `BLOCKED`／未执行并继续完成可完成部分，不能修改测试条件让报告变绿。

### 最终验收检查

下面六项缺一不可；不满足时，在结论中明确仍缺哪条链：

1. 实际达成事件能够闭合原 Goal，包含没有预绑定 Intention 的普通对话事件；不会伪造证据。
2. 活动目标有下一步、等待条件或可见阻碍；结果之后会调整，不是永远重复同一愿望。
3. 行为、短期目标、阶段与长期目标分别评估，不靠次数或固定百分比制造进展。
4. 暂停／取消、工具前失败、标准版本变更、重复和迟到事件、重启恢复具有可靠边界。
5. Reflection 能解释该周期为何推进或未推进，并形成持久的合理下一步；Owner 能查看和治理全过程。
6. 所有生产入口使用统一权威状态与提交逻辑，旧数据可迁移，Agent／Tool 与上下文约束没有回归。

### 明确禁止的“交付方式”

不能只新增模型／表而不接生产链；不能只修改 Prompt 写“你要积极推进目标”；不能只新增每日 cron；不能拿购物专用链代表通用目标；不能通过每次发消息增加进度；不能让 Reflection 直接宣布完成却没有证据；不能为修复 due 悬空无限重试；不能让模型判断绕过权限、日程、用户拒绝和标准版本；不能把已有实施报告当作当前版本验收。

本任务的最终产物应是一套**能够推进、能够停止、能够恢复、能够解释、能够验证**的目标闭环，而不是更多仅供模型阅读的目标描述。
