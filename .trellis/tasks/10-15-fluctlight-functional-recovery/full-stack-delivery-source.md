## 1. 任务目标、依据与范围裁定

### 1.1 本轮必须交付什么

交付一个使用当前 v3 外观与交互、全部已确认业务功能可真实运行的版本。允许并要求补齐必要的数据库迁移、领域服务、查询投影、浏览器接口、客户端类型、后台任务、Tool、Agent 任务接入和运行结果回读。

“没有旧接口”“之前列为 C 类”“需要加表”“旧版本没做”都不是延期理由。接口返回成功、组件可以点击、构建通过、单元测试使用 Mock 通过，均不能单独代表功能完成。

本轮不是重新设计 UI，不是重复盘点，不是仅修当前报错，也不是将全部后台能力统一改造成另一个框架。

### 1.2 各依据的职责

| 依据 | 决定什么 | 禁止的用法 |
|---|---|---|
| 当前已确认前端 + UI-01/UI-02 | 唯一 UI 实施基线：布局、视觉、组件组合、操作路径 | 不能因为接口接入困难而恢复旧面板、旧导航或旧配色 |
| 最新明确的用户需求与本任务 | 本轮功能范围、身份、权限和操作语义 | 不能以历史 P1/P2/P3 或“本期未接入”自行缩减 |
| 完整蓝图、总稿、v3 和 Quasar 参考 | 查漏，包括页内 tab、详情、抽屉、编辑器及跨页旅程 | 不能照搬未经确认的新玩法，不能把样稿视为已实现的后端 |
| 当前代码、数据与有效契约 | 识别可复用能力、真实行为、兼容约束和故障原因 | 不能把缺陷、未实现状态或旧 UI 当作需求上限 |
| 旧审计、迁移表和接口缺口表 | 历史检查线索、旧功能防遗漏映射 | “已接入”不等于本轮已验证；建议路由不等于定稿 API |

如果本地无法找到用户当前认可的 UI 版本，只询问该基线的位置或版本，不自行挑选旧实现代替。其余可独立核验工作继续。

### 1.3 全量范围的有限边界

本轮范围是以下并集，按业务含义去重，不是按页面或旧接口数量统计：

- 当前已确认 UI 的全部业务页面、读取、写入、详情、筛选、分页、菜单和抽屉操作。
- 已确认需求中遗漏于当前 UI 的功能，尤其“关于你”、NPC、世界、日记、通知、创作应用、角色级策略等。
- 上述功能真正生效所需的数据生产、执行、状态结算、上下文消费、异步任务和诊断入口。
- 原有真实能力在新 UI 中的等价入口和完整行为，不能因本轮使用 Mock 而丢失。

旧审计的 53 个条目是保留检查线，不是完整需求的上限。当前 UI 已确认的新增操作必须增加稳定 Feature ID。

明确排除：桌宠、Live2D、角色时间线回档执行、永久性伤害放行、未单独确认的任意动态代码/插件安装平台、模型训练工程及与本次功能无关的基础设施整体重构。

语音消息、实时通话、群聊、共享世界、摄像头等增强功能，按最新明确确认范围逐项登记：已经确认可用的操作不能沿用旧 P2 标签延期；仅有未来说明、尚未确认的设想不因 Quasar 出现过就擅自纳入。不能把含糊项默认为排除，也不能把一整个功能域改名为“未来版本”逃避实现。真正无法裁定的范围冲突集中列明，并继续不受影响的工作。

业务备份与故障恢复不等于角色时间线回档；前者在确认的数据工具范围内实现，后者仍不实现。

### 1.4 冲突处理

先检索本地最新确认记录。UI 解决“怎样看和操作”，服务端负责执行身份与权限；Mock 的假成功不是业务契约。

例如日记正文是否允许用户编辑、人格切换的授权路径、建议日程与所有者直接修改，不得仅凭一个 Mock 按钮推翻已确认边界。旧总稿与旧接口建议不一致时，将两者视作历史需求冲突而不是已定稿的新权限。确需用户裁定时，一次集中描述冲突、影响与推荐处理，不因普通字段命名或内部实现选择反复等待。

必要核验结束后直接修改代码。文档是执行依据，不是本轮最终交付的替代物。

## 2. 不得破坏的实现约束

### 2.1 UI 只接业务，不退回旧版

- 允许修改 props、事件绑定、数据源、类型、请求逻辑、加载错误及冲突处理。
- 复用旧 BrowserClient、store 中有效的业务行为、服务与协议；不因旧组件已经接接口就整块嵌回。
- 原有 GoalPanel、GovernanceView、OperationalSettings 等名称仅用于寻找业务能力，不构成继续保留旧视觉的授权。
- 不通过 iframe、整页旧组件挂载或另建一套页面绕过当前 UI。
- 真实长文本、多页列表、缺图和异步状态按当前设计语言适配，不能为了截图一致删数据或写死值。
- 非必要的布局、主色、导航、密度和操作路径变化不在本轮擅自进行。必要例外记录影响与理由。
- 已确认需求确实缺少入口时，在当前设计系统内补足对应页面或交互并登记基线增量，不能以“UI 已冻结”为由拒绝补全，也不能借补全恢复旧面板。

### 2.2 组件与数据提供层

沿用已实现的基础组件、业务组件、composables 与页面接入分层，按需修正边界，不重新造通用组件平台。

Mock 与真实模式复用同一套页面/展示组件，使用明确、类型化的数据提供接口或现有等价结构。协议映射集中在客户端/适配层；新旧后端字段差异不能散落为每个组件里的特殊判断。

生产构建默认真实模式，API 失败不回退 Mock。测试 fixtures 与 Mock 状态不在启动时写入真实库，测试页面不得暴露生产写操作。不要仅通过隐藏“Mock”徽标伪装真实接入。

展示层可以持有草稿、动画进度、选中态、滚动位置；服务端是消息、关系、目标、世界、物品和有效状态的权威来源。

### 2.3 聊天与动效保护

先核验本地实际协议，保护已有流式、历史序号、turn 身份、幂等、部分提交、显式取消和最终校准。历史材料中的 POST + NDJSON 是查证线索，不允许未经核验改成另一套传输模型。

等待圆点由真实请求阶段驱动；打字效果只展开已收到的可展示文字。历史消息不重播、最终校准可覆盖、动画结束不代表任务完成、关闭动画不代表取消后端任务。

用户阅读历史时不强制滚到底；加载旧消息保持位置；切换会话不串字；组件销毁清理监听/计时器，不因此擅自取消后端工作。保留减少动效与窄容器适配。

### 2.4 运行架构保护与必要扩展

允许为本轮功能新增或补齐领域服务、Tool、查询投影、任务、提示词 slot、调度触发、上下文装配和结果写回；不把“不要整体重构”解释为“后台永远不能变”。

保留现有 Eino/ADK 的任务边界及各 Agent 的独立运行方式，Tool 可单独测试与调用；复用基础设施不等于把所有业务塞进一个新总控 Agent。确定性的 CRUD 和查询不应仅为“智能化”强制经过 LLM。

保留当前确认的 fact-only 双模型分工：Qwen 处理工具、事实和证据；Cydonia 读取人格、Goal、关系、当前状态与真实聊天上下文并独立决定社交表达，不能退化为 Qwen 草稿润色器。具体调用链以本地有效实现核验；新增信息按既有职责接入。

不得为了新功能把整个世界、全部 NPC、所有物品及完整历史常驻塞进每轮 Prompt。使用相关范围的短投影与按需查询，记录新增上下文负担。

### 2.5 事实、身份和权限

区分 Owner 身份、交流 Actor、Fluctlight、active profile、NPC 身份、定义资源和运行世界。前端“交流/管理”切换不等于服务器授权。

保留 Foundation、Working Persona、有效当前状态、临时状态、Developing Self 的边界。已生效变化不因人格切换或旧字段缺失回退初始化；unknown/cleared 不伪装为旧值。

建议、请求、计划、执行、结果、生成、发送分别处理。拒绝或无须行动可以是合法业务结果；不能为了测试通过强制角色接受请求。

浏览世界不移动角色；同处地点不自动代表已认识；私聊和通话不自动令用户在场。创建定义不自动改变所有使用者；产生图片不证明图片中行为或物品状态已经发生。

## 3. T00—T04：开工基础任务

### T00：完成两处小优化并锁定 UI 基线

执行 UI-01/UI-02。保留当前页面、导航、弹窗、抽屉、组件场景及桌面/窄屏截图，记录基线 commit 与后续合法例外。

建立固定内容的视觉回归场景。对照使用同一批可复现数据，冻结动画时间或采用减少动效模式；不凭一张首页截图判断全站一致。

验收：两个已填写优化有对应结果；UI 基线可定位与复现；后续接入能够对照这个版本，而不是旧原型或旧生产 UI。

### T01：建立唯一、不会缩水的功能台账

实际遍历当前前端：主页面、tab、菜单、详情、抽屉、编辑、导入导出、筛选分页、状态设置、异步任务入口。扫描 Mock provider 和事件处理，找出当前模拟了哪些后端与运行能力。

再对照蓝图、总稿、Quasar 已保存参考与旧审计补漏。现有模块名只作分组，每个业务动作必须可单独追踪。额外登记无直接按钮的生产/消费流程。

每项至少记录：

| 字段 | 内容 |
|---|---|
| Feature ID / 旧 ID / BP 关联 | 稳定且可追溯，新条目不挤入不相干旧 ID |
| 需求来源、当前范围状态 | 当前 UI、最新确认、蓝图条目、明确排除或待裁定 |
| 页面 / 组件 / 操作 / 触发点 | 包含隐藏入口和后台定时/事件触发 |
| 行为与完成依据 | 不是只写“保存”或“查询” |
| 身份与数据范围 | Owner、Actor、Fluctlight、profile、世界等 |
| 当前本地证据 | route/client/service/tool/model/migration，未查到时如实记录 |
| 数据生产者、消费者与生命周期 | 创建、变化、失效、重试、当前读取 |
| 依赖、所属工作包 | 可定位实施顺序与阻塞关系 |
| 测试编号、实际结果 | 单测、集成、浏览器、模型/媒体实测分开 |
| 实施状态与阻塞原因 | 不以“按钮存在”标为完成 |

范围状态与实施状态分开。实现状态至少区分：Mock 已验收、待实现、实现中、已接接口、集成测试通过、真实 E2E 通过、待用户验收、真实阻塞。

已确认范围内的条目不可自行改为排除、未来迭代或“可选优化”。旧 B/C 分类用于估算差异，不用于延期。

验收：每个当前业务入口和后台闭环有台账落点；明确的延期有最新用户依据；53 个旧条目逐项映射，但统计不局限于 53。

### T02：建立真实测试环境并处理公共故障

读取本地仓库约定、现有脚本和有效配置，启动前端、Core、数据库、必要 Worker 与媒体/模型连接。核验登录、CSRF、代理路径、流式缓冲、API origin、迁移版本、启动条件和资源访问。

检查 git 状态，保留用户未提交修改；不得使用破坏性重置。工作分支与测试库明确区分，测试数据带可清理标识。

已有数据库在副本上验证升级；不得通过 drop 表、清库、重建角色解决兼容问题。生产密钥不写文档、日志或 fixtures。

对“报错/没数据”追到实际原因：无记录、未配置、未初始化、迁移未生效、范围/ID 错误、字段解码错误、鉴权失败、任务未运行、消费者缺失、缓存过期，分别处理。

没有模型或媒体访问条件时，记录缺少的具体配置并继续其他工作。测试替身可用于隔离测试，但不冒充外部真实验证。不得静默调用昂贵服务或进行大规模压测。

验收：真实前后端可访问；基础认证、读写、日志关联可用；未满足依赖明确列明；不得把 API 404/500 包装成成功空列表。

### T03：统一契约与客户端适配

逐项形成 UI 数据需求到领域协议的映射，不照抄 Mock 对象作为数据表，也不照抄历史建议路由。

契约需要覆盖：稳定 ID、字段与可空语义、范围、版本/幂等、合法状态迁移、分页/排序/搜索范围、权限与结构化错误、同步结果和异步受理结果、来源/时间。

缺字段、合法空值、未配置和调用失败不由组件自由猜测；沿用有效项目契约，不新造一个抹平全部领域的通用状态枚举。异步受理不能直接映射为业务 completed。

时间遵循项目现有统一规范；缺乏明确规范时建立带明确时区/偏移的约定，并保留业务本地日期与 IANA 时区。不能在同一链路混用无时区字符串、UTC 和浏览器本地推断而不转换。

沿用 BrowserClient 或现有等价入口处理 session/CSRF、请求取消、错误映射。服务端验证对象范围，不信任浏览器提交的 Actor/角色 ID。

验收：客户端与后端契约有实际测试；字段转换集中；生产请求失败不回退 Mock；接口名和 DTO 不是脱离代码的第二份规范。

### T04：实施缺失模型、数据迁移与执行闭环

先复用有效领域模型。确需新增实体、关系、索引、版本或任务记录时编写迁移；不因减少改动而把所有新能力塞进没有约束的大 JSON，也不机械地每个页面建一张表。

World/地点目录、NPC、物品定义与持有、创作版本、日记、通知等新概念，给出简短建模决策及兼容方法后实现。旧文本地点保留来源，不能只按同名字符串无条件合并成世界实体；历史物品 ID、来源及穿着引用不能丢。

每个新字段或列表明确谁写、何时写、谁消费、如何失效和重试。只有 schema 和 GET 而没有生产者的功能不完成。

数据库操作使用合适的事务边界；外部模型/媒体调用复用现有持久任务或可靠执行机制，不放进长数据库事务里。处理成功副作用与消息重试、Worker 重启之间的重复执行和漏写，至少有可追踪的恢复办法，不强制另建事件总线。

验收：全新库可启动、旧库副本可升级；服务重启后数据与任务正确恢复；不借迁移写入虚构历史或示例事实。

## 4. WP-01—WP-18：完整业务工作包

以下是执行分组，不替换原有 BP / Feature ID。每包必须做到：当前 UI → 真实请求 → 领域处理 → 持久化/执行 → 回读 → 必要运行消费 → 回归证据。内部按依赖连续推进，不把每包变成等用户再次立项的阶段。

### WP-01：认证、角色库、创建与生命周期

**实施：**接回真实登录/退出、密码与会话处理；角色列表、头像、近期对话、真实未读与运行状态；分组创建、加入、移出及已确认的批量操作。创建支持当前已确认的空白/描述/JSON/模板流程，保留预览与正式激活的区别；初始世界、地点、资料、目标和自治策略按向导真实生效。

创建中断和重试不生成重复角色；新角色必须具有开始聊天和生活所需的有效初始数据。分组不改角色事实，退休不等于物理删除。旧链接兼容通过规范路由实现，不恢复旧页面。

**验收：**新建角色后刷新可见、聊天可进入、初始化任务可追踪；切换/退出不残留其他角色数据；分组与退休不误删生活记录。

### WP-02：“关于你”、Actor 背景与关系

**实施：**在当前已确认的自然入口提供“关于你”读取、编辑、保存、修订与冲突恢复。区分用户自填资料、其他 Actor 背景、摇光对用户的记忆/印象、双方关系；不把“关于你”做成软件说明或摇光角色资料。

先核验 owner background 与 Actor context 的已有作用范围和 CAS 规则。界面写明实际范围；若定义了角色特定覆盖，需要明确优先级与隔离，不把共享资料悄悄复制为互相冲突的多份真相。

接通相关认知、回复、目标规划等真实消费者，按任务最小化装配最新版本。关系继续使用已确认的有向、可 profile-scoped 语义；修订关系不回退事件和历史消息。

**验收：**保存、重新查询、重启后读取一致；两个用户 Actor/角色范围不串写；构造完整请求检查正确版本进入相应上下文，再进行真实对话验证。不能只因为模型偶然说出某个字段就证明接入成功。

### WP-03：聊天、会话历史与附件

**实施：**使用当前 ChatPanel、消息列表、输入区和动效，接真实发送、流式、历史分页、已读、取消、失败重试、部分提交与最终校准。新会话延续人生状态，不清空记忆/关系/目标。

接通已确认的消息搜索、来源、纠错、行动卡和附件操作。附件覆盖选择/上传/预览/撤销/引用签发/发送/授权读取/失败清理；服务端校验文件类型、大小与访问权限。图片或语音需要被模型消费时验证实际消费者，而非只显示附件缩略图。

用户上传媒体和生成媒体保留不同来源，不能统称为同一类“生成图”。语音消息/实时通话分别按锁定范围实现，不把静态录音控件当语音功能。

**验收：**真实多轮、断流、取消、幂等重试、历史分页、快速切换、附件失败与越权访问；动画不改业务完成状态；进入新会话后长期状态连续。

### WP-04：角色资料、人格与有效状态

**实施：**接回 Foundation/Persona 的读取、编辑提案、差异、接受/拒绝/回滚及当前生效版本；当前人格与切换记录单独展示。已确认的手动切换请求走 Core 受控能力，不靠直接更新 active_profile 字段绕过授权。

核验 Working Persona 编译/缓存失效、有效外观/习惯与临时内在状态。定义变更与正在使用的状态按既有规则分开；不把全局视觉工作流当某个角色的视觉定义。

**验收：**修改源定义后相应投影可追踪更新；持久切换保留有效生活状态；已剪短的头发、当前穿着不会因为切换人格或刷新回到初始化。

### WP-05：世界、地点、场景与当前在场

**实施：**实现已确认的世界/地点/场景目录、详情、连接关系和运行世界绑定。定义资源与运行实例分开，复用模板不自动共享生活状态。列表和图视图读取同一组真实 ID 与关系。

将现有 Event/Schedule/Activity 的位置语义与新目录兼容关联，保留原文本来源。当前在场必须按有效事件、活动或日程估计规则解析，并区分已确认与预计；不能让地图、此刻和聊天各算一套权威位置。

世界浏览、地点详情、附近列表和来源查询保持无业务写副作用。无法确定地点时显示未知，不造默认咖啡店填空。

**验收：**建立/应用世界后可真实浏览；场景、日程和此刻一致；重复 GET 不移动角色、不创建相遇；多运行世界使用同一模板时位置和事件隔离。

### WP-06：NPC 创建、生活规律与相遇互动

**实施：**提供当前确认的 NPC 创建、编辑、查询、引用管理和停用/删除语义，不只返回 npc_ids。选择兼容 Actor/Relationship 的明确身份模型，覆盖类型校验、参与者解析和权限影响；NPC 模板与运行身份区分，不强制创建完整 Fluctlight。

接独立生活规律、日程/当前活动、初始或常驻地点与实际事件覆盖，采用按需或现有调度机制推进；无需每个 NPC 常驻 LLM。档案描述不能直接冒充已发生经历。

建立实际到达/有效在场 → 相遇机会 → 按已确认规则决策 → 事件结果 → 关系/记忆更新的路径。共处地点不等于自动交友；创建 NPC 不自动生成历史关系。已确认的场景互动/动态评论必须使用真实 NPC 身份与来源。

**验收：**创建、刷新与修改可用；NPC 位置在相应条件下变化；受控测试事件可产生相遇结果；重复处理不会重复结识或写记忆；取消/失效在场不会伪造相遇。

### WP-07：Goal、意向、愿望与约定

**实施：**保留完整 Goal 生命周期、阶段、完成条件、证据、历史、排序、依赖、规划建议、审查与受保护目标。延续 Goal 与固定人格解耦、独立规划、完成后补充候选和旧目标延续策略，不能降级成普通 todo。

核验当前“约 5 个”等策略以配置/有效契约执行，不在前端截掉其余数据，也不强迫每次机械生成五个目标。

当前 UI 若明确提供独立愿望生命周期，就实现持久化语义与 Goal/Intention 的关联；若最新裁定只是既有 Intention 的视图，说明映射并保留相应操作。不能把同一 Goal 列表换个标题冒充独立能力。

约定区分提出、接受/拒绝、改期、取消、履行、失约，接入日程与实际结果。用户建议不直接成为角色已经接受的计划。

**验收：**规划触发真实执行、候选与来源可回看；目标推进/完成由证据支持；完成后的后续规划仍可运行；依赖冲突与重复触发正确处理。

### WP-08：日程、行动、生活事件与变化

**实施：**以当前日/周 UI 接逐项编辑、取消、接受、调整来源和历史；适配既有整日命令或补逐项服务，但保留 intention、action_plan、时间、版本及来源，不能仅保存界面上几个文本字段。

打通计划 → 执行触发 → Activity/任务 → 权威结果 → 当前状态/目标推进/后续日程。计划到点不自动等于成功，叙述“买到了”也不能代替工具结果。

临时事件影响日程与约定时保留影响链。世界事件模板的运行调度按锁定范围与 WP-12 联动：有明确触发、适用范围、频率/冷却、幂等和影响处理，不能只有开关配置。

正常离线或服务恢复采用当前时间与真实可恢复记录，不批量补造未执行成功的事件。禁止永久性伤害继续在服务端各入口生效。

**验收：**跨日/跨时区、版本冲突、重试、中断恢复和计划取消；运行结果在此刻/日程/目标/世界中一致；事件拒绝不会留下已生效副作用。

### WP-09：物品定义、持有、穿着、搭配与使用

**实施：**补齐已确认的定义库与持有项关联、全量分页/筛选、添加/修订/删除、可用性、借还、搭配、穿脱、普通物品开始/结束使用及历史。沿用稳定 item ID，迁移不能破坏旧穿着和来源。

拥有、可用、当前穿着、当前使用、入库任务是不同维度。定义一件物品不等于拥有；人工补录不伪装成购买；列表未加载完整不代表不存在。

购买按项目虚拟生活规则执行：意向/目标 → 合法取得行动 → 真实执行结果 → 入库。不得接真实消费/支付服务来“证明购买”而未经另行授权。入库中/失败等状态由实际取得任务产生，不新增一个永远不更新的字段。

**验收：**未拥有且无合法借用的物品不能穿用；实际取得后多页回读一致；重复任务不重复入库；换装不改来源/所有权；生成图不自动改衣柜。

### WP-10：日记、共同经历与来源

**实施：**建立日记生产触发、输入来源、生成状态、持久化、日期/时区、列表、详情、收藏与重试。复用适合的每日处理/任务基础，不把对话摘要直接改名日记，也不另建重复运行链。

角色主观正文与事实来源、用户注记分开；沿用“用户不能直接改写角色日记”的已确认边界，除非查到更新的明确裁定。共同经历来自真实共同参与，包括远程交流；只有确有同场来源才标同场。

对无有效素材、无变化或无需产出给出合法结果，不强迫生成虚构一天。异常与没有内容区分。

**验收：**通过真实源事件/对话触发生成并读回；失败可恢复；跨日期边界归属正确；独自活动不被写成用户共同在场；创作预览不进入日记。

### WP-11：记忆浏览、纠错、反思与成长

**实施：**接完整分页/搜索、详情、来源与修订/忘却，不能把 detail 中有限摘要当全量账本。消息纠错关联实际来源，未找到可靠关联时只作为反馈，不造引用链。

复用 Reflection V2 的 window/proposal/evaluation/application 等真实结构；查询、候选状态、采纳结果和影响领域各自展示，不新造简化正文模型覆盖已有能力。

Developing Self、临时状态、人格提案继续分开；正常反思不因有管理页而全部转为人工审批。源事实修订后按已定义的有效性传播机制处理，不承诺自动撤销所有下游历史。

**验收：**跨页追溯到真实源 ID；修订后当前召回不再继续当作原有效事实；历史保留必要说明；反思触发和各领域应用有证据，零候选是可解释结果而非假失败。

### WP-12：创作资源、助手、预览与应用

**实施：**覆盖确认的角色/人格、世界/地点、NPC、物品/搭配、事件及视觉资源类型；草稿、版本发布、复制、搜索、引用与删除约束真实持久化。

助手使用真实模型与资源草稿上下文，复用 ChatPanel 不复用生活私聊会话副作用。实现预览任务、文本/媒体产物、重新生成、丢弃、存为资源素材；必须隔离角色记忆、日记、关系、衣柜和正式媒体库。

应用到实例先算差异、影响及冲突，再以明确版本执行。定义变化不自动广播覆盖已运行实例；当前有效状态的保留/覆盖按已确认规则处理，失败不留下未说明的部分应用。

事件模板包含条件、影响、频率与范围；预览不触发正式世界事件。保存、导入、复制、应用及实际执行均不能绕过永久性伤害禁用。

**验收：**从草稿到真实应用的完整链路可操作；助手不是本地假回答；旧实例与新定义差异可见；冲突恢复可用；预览后正式生活状态未被写入。

### WP-13：视觉身份、媒体生成与媒体库

**实施：**接角色视觉定义、初始化任务、attempt、候选/参考图/角色卡、有效版本、头像选择及历史；区别全局工作流和角色具体身份。修改角色定义不修改其他角色或全局 ComfyUI 配置。

统一媒体库、单项详情、来源、生成、失败重试、授权读取和已确认的管理操作。异步受理后有实际 Worker/执行器消费，并能恢复结果查询，不能只返回 task ID。

保留“摇光决定大概内容 → KEV 按启用状态补分类/视图 → LLM 规范提示词 → 工作流”的有效分工；无人物场景不注入人物属性，人物不默认自拍。使用当前有效外观、合法穿着和范围正确的视觉版本。

**验收：**真实执行至少覆盖已配置生成链路的代表场景；失败能定位与恢复；资产回读和来源一致；既有成功结果不因重试重复生成；风景/物品图不变成角色自拍。

### WP-14：动态发布、评论与互动

**实施：**接全局/角色筛选、详情、分页、回应、评论、隐藏/恢复、媒体与来源。用户发布使用实际交流 Actor；禁止 Owner 通过传 author ID 冒充摇光发布。

角色自主发布沿用角色决策与发布能力；“建议她发布”是请求而非强制发布。确认范围内的 NPC 互动接其真实身份/事件，不硬编码评论。提交与通知关联有幂等和可追踪结果。

**验收：**用户发布、角色自主发布、建议被拒绝分别正确；无权限代发被拒绝；隐藏内容行为符合规则；评论/通知不会重复，刷新后内容一致。

### WP-15：角色自治、主动触达、通知与待处理

**实施：**区分全局策略、角色级覆盖与最终有效策略，保存后在真实决策/执行/发送入口消费。预算、并发、冷却与确认要求使用可追踪的实际计量/规则，不建立只会保存的设置页；单位与作用范围清晰，不能混淆模型开销与虚拟生活花费。

静音通知、暂停主动联系、暂停自治分别处理；恢复行为按当前明确产品语义实施，不照搬历史文档中未经核验的冻结/补跑规则。变更与正在执行任务的关系需要定义并测试，不悄悄丢任务。

通知从真实事件产生，持久化、未读计数、已读与深链接可用。待处理只聚合真实待决来源，处理回原受控命令；通知已读不等于事项处理完成。单一来源故障只影响该来源，不能显示“全部处理完”。

**验收：**策略保存后真实阻止/允许对应行为；两角色策略隔离；静音仍可保留消息/通知记录；重复事件不重复通知；原事项处理后聚合正确消失。

### WP-16：系统设置、模型绑定与能力目录

**实施：**接所有确认的 Endpoint、模型角色、Reply/Vision、fact-only、KEV、媒体工作流、连接测试、运行策略、Owner 设置与只读能力目录。查看与编辑读取同一份有效配置。

明确测试的是已保存还是当前草稿；密钥保持写入专用，空白、保留和显式清除有区分。未配置与调用失败分开；不因旧配置兼容恢复废弃 tab。

能力请求审查与 registry 查询复用当前模型，不扩大为动态代码安装。角色级设置不嵌入一个没有范围说明的全局面板。

**验收：**保存重启后仍有效，真实调用使用选定配置；不同配置角色不串用；密钥不回显；设置失败不以本地草稿显示已保存。

### WP-17：诊断、任务恢复与操作审计

**实施：**接生命周期、Agent/model runs、KEV、媒体请求、事件、任务、工作流历史/控制、筛选分页、导出与清理。任务详情使用真实标识与步骤关联，不新建脱离原执行器的假任务表。

每个新增异步工作包提供 producer、状态、结果/错误、source/correlation 和回读入口。重试仅重做合法未完成部分，取消/重启/重置保留既有边界和确认，不能承诺撤销已经完成的外部效果。

拦截统计有真实数据来源；没有数据不是默认 0。清理诊断不删除生活事实、记忆或角色内容。

**验收：**从业务失败定位到实际步骤，再恢复并回到原页面；稳定链接刷新可用；同一成功副作用不重复；导出完整性与清理范围可验证。

### WP-18：配置包、业务备份、兼容与发布

**实施：**已确认的资源导入/导出包含格式版本、结构校验、引用检查与处理结果，导入先形成定义，不自动应用运行实例。模型/媒体密钥不随公开资源包泄露。

确认范围内的业务备份覆盖必要数据库、媒体及配置依赖，说明一致性策略、版本兼容、恢复维护条件和审计。恢复只在明确隔离环境实际测试，不能为了验收覆盖用户正在使用的库或资产目录。

实现旧数据升级与必要 URL 兼容，清理被替代的生产 Mock/旧 UI 入口。保留代码级安全回退方式，不通过运行时悄悄恢复旧页面进行兜底。代码发布回退、数据库恢复与角色时间线回档分别说明。

**验收：**新装与升级均可运行；样本业务备份在隔离库恢复后引用、数量和关键状态一致；资源导入不改变生活；正式构建不走 Mock；时间线回档仍无执行按钮。

## 5. 跨模块端到端用例

这些是最低检查线，不取代功能台账里的每个动作。通过用例须记录实际命令/浏览器步骤、测试数据范围、结果、相关 ID 与日期；截图和自动化 trace 存本地，不写密钥或不必要的个人信息。

| 用例 | 操作与完成依据 |
|---|---|
| E01 新建并开始生活 | 隔离测试环境从创建向导产生角色，初始化完成，打开聊天/此刻，刷新与服务重启后仍能读取相同角色与配置。 |
| E02 关于你真实消费 | 修改明确测试字段，保存并核验版本；完整模型请求或可脱敏上下文记录中出现正确 Actor 的最新值，再验证真实对话；另一 Actor 不受影响。 |
| E03 双模型与真实流式 | 完整用户回合穿过实际 Qwen/回复能力/Cydonia/Tool 结果链路；检查职责、增量、完成和持久消息。内部循环不算多个用户回合。 |
| E04 取消与失败重试 | 在测试任务中制造可控中断，保留已提交内容；重试不重复消息和成功副作用；离开页面不等于服务端取消。 |
| E05 附件与权限 | 上传、预览、发送、模型按能力读取、刷新回看；失败不产生假消息；越权资产不可读，撤销不误删已被消息引用的资产。 |
| E06 新会话与分页 | 新会话不重置关系/目标/记忆；多页历史不重复不漏；切换与刷新保持正确范围、已读和滚动行为。 |
| E07 NPC 与真实相遇 | 创建/应用 NPC 与地点，核验未自动相识；通过实际受控日程/事件到达，产生符合规则的互动结果与可追踪关系/记忆；重复触发不重复结识。 |
| E08 世界查看无副作用 | 浏览/刷新地图、地点、附近和 NPC，记录前后领域版本/事件；查询不产生移动/购买/结识写入。 |
| E09 意向到物品使用 | 产生合法取得意向并经实际执行入库，换装/使用后在衣柜、此刻、聊天摘要中一致；未取得前不可用；不是直接 SQL 写结果。 |
| E10 目标完成与后续规划 | 达到实际完成条件后记录证据，规划器继续处理后续目标/候选，旧目标优先与依赖策略保留；候选为零时有可解释原因。 |
| E11 日程变化与跨时区 | 受控临时事件影响计划/约定，保留变更来源；跨日、时区切换及夏令时相关用例按项目支持范围验证，无无时区误读。 |
| E12 日记与共同经历 | 真实对话/事件触发生产并持久化；用户未在场的事件不写成同场；失败重试不重复生成多个有效当天版本。 |
| E13 纠错与反思 | 从消息到来源修订，重新查询/召回使用有效版本；触发真实 Reflection 后可见窗口、候选与处置，不要求每次都有成长。 |
| E14 创作隔离与应用 | 真正编辑/生成预览/发布/应用，处理并发冲突；预览不写生活，应用后对应定义/实例版本一致，不重置未选择覆盖的当前状态。 |
| E15 视觉与媒体 | 实际生成后任务终态、资产和来源可回读；检验人物与无人物提示词路径；重试不重复已有成功产物，图片不改变物品事实。 |
| E16 动态与身份 | 用户发布、角色发布及建议拒绝分开；不允许伪造作者；互动产生真实通知且正确去重。 |
| E17 自治/通知/待处理 | 分别设置静音、暂停主动、自治策略并触发受控测试；验证实际执行边界，已读不等于处理完成，单源失败不显示全空。 |
| E18 设置与任务恢复 | 保存配置后用实际调用验证生效；从业务错误跳诊断恢复任务、读回结果；密钥不回显，已成功步骤不重复执行。 |
| E19 隔离与冲突 | 双角色快速切换、延迟响应、退出再登录、双页面版本冲突；旧响应不覆盖新对象，409 保留草稿，服务端阻止越权写入。 |
| E20 升级、备份与资源包 | 空库初始化、旧数据副本升级、资源包导入与隔离恢复；核对引用完整和敏感字段，不操作真实用户库作为测试。 |
| E21 v3 视觉与组件回归 | 固定内容的桌面/窄屏、长文本/空态/失败/抽屉/流式场景与 UI 基线对比；没有旧 UI 回退，没有每页独立重写动效和加载。 |
| E22 正式模式无 Mock | 真实构建中审查数据源，断开 API 只出现真实错误；不会自动填演示角色/物品/动态，保存刷新不依赖浏览器本地假数据。 |

### 5.1 分层测试与证据边界

- 单元/组件测试：可用 Mock，验证布局、状态、算法与错误处理，不称为业务 E2E。
- 集成测试：真实 Core 与测试数据库，实际迁移/事务/查询/权限；外部模型替身需标明边界。
- 浏览器 E2E：当前正式组件 + 实际 API + 数据库，验证操作、回读、刷新、跨页和版本冲突，不使用浏览器拦截请求返回成功来证明已接入。
- 真实模型/媒体验收：使用已配置测试对象与有界预算，确认生产者、消费者和结果持久化；测试替身的成功不计为真实外部链路通过。

可通过可注入时钟或测试触发器驱动跨日/定时流程，但必须调用同一生产领域服务与执行路径，测试入口不暴露于正式用户。不得靠直接写数据库制造最终结果，再把 GET 成功当完整闭环。

数据准备允许受控测试 fixture；准备初始对象与伪造待验收行为结果严格区分。概率性角色决定可以拒绝、延期或不生成候选；验证规则和结果一致性，不强制迎合测试剧本。

外部依赖确实缺少时，将对应用例标为“真实链路阻塞/未验证”，完成不依赖该条件的工作并给出最短复现/配置要求。不得宣称全部通过，也不因此把其他未实现功能无限放置。

## 6. 执行节奏：一个范围、连续推进、最后统一验收

### 6.1 内部顺序

1. T00 完成两处优化与视觉基线；T01—T02 同步建立完整台账及真实环境。
2. T03—T04 完成共用契约与必要基础，优先接回现有真实能力、关于你和核心聊天，形成新 UI 上首条可运行链。
3. 按依赖连续完成 WP-01—WP-18；世界/NPC/创作、生活/目标/物品、记忆/反思/日记、自治/通知等各自纵向打通，不能只先写完所有 GET。
4. 每个工作包完成后当场跑对应测试，同时保持公共回归；继续下一包，不等待用户重新提出下一轮。
5. 全部范围具备实现后，跑 E01—E22 与台账用例，检查升级、视觉、生产 Mock 隔离及交付条件。
6. 交付统一候选版本，由用户整体验收。内部集成通过不冒充用户已验收。

### 6.2 Bug 不得替代功能建设

维护同一份功能台账、缺陷列表和决策记录，不每完成一轮就用新文件遗忘旧缺口。

数据损坏、权限/身份串用、重复副作用、启动失败、保存失败等阻断问题优先修；修完恢复原工作包进度。非阻断的表现微调进入统一优化列表，不借此重新设计或无限打磨单页。

新增缺陷和真实缺口必须链接到 Feature ID。不能把“当前错误修完”“主要页面可打开”作为任务结束条件。

### 6.3 长任务续接与协作

单次会话/上下文耗尽时，更新执行日志：当前基线、已完成 Feature ID、最近 commit、运行中的测试/进程、阻塞、下一项具体动作。续接读取同一台账，不重新发明分期或停止在盘点报告。

可并行处理互不冲突的领域，但共用契约、迁移编号、Mock/real 数据接口和公共 UI 由明确负责人统一。不能为了使用子 agent 重写项目工作流，也不需要强制引入多 agent 管理平台。

无权限/凭据缺失、不可逆数据变更或不可自行裁定的产品语义，才集中请求用户决定；不要每个模块完工都询问“是否继续”。

## 7. 最终完成标准与交付物

### 7.1 完成门槛

- 当前已确认 UI 不回退，两个已填写优化完成并可对照。
- 范围内每项功能都进入台账，没有用“C 类/P2/后端不存在”自行延期。
- 真实模式不存在靠 Mock、静态假数据、默认值或假成功支撑的业务功能。
- 每个数据展示有真实来源；每个后台产物有生产者；每个可配置行为有实际消费者；每个异步任务能执行并读回结果。
- 已确认的操作权限、版本、幂等、来源、时间及多角色隔离经过验证。
- 当前库升级与新环境启动可复现，生产秘密与用户数据得到保护。
- 范围内用例真实通过，或对外部阻塞逐项明确写出未验证。仍有未实现条目或关键用例阻塞时，只能交付进度/候选，不能写“全量完成”。
- 用户统一验收在后；agent 不以内部结果自行标为用户验收通过。

### 7.2 交付物

优先沿用仓库已有等价位置，避免重复一堆同义文档；下面是内容要求，不强制文件名。

| 交付内容 | 必须包括 |
|---|---|
| 实现代码与迁移 | 前端接入、后端/运行补全、类型、测试、必要数据升级与兼容 |
| 基线与视觉对照 | 已确认 UI commit、两项优化、固定场景截图/差异和合法例外 |
| 唯一功能台账 | 全部范围、旧 ID 映射、新增能力、实现与证据状态、真实阻塞 |
| 契约与建模决策 | 关键身份/范围/生命周期、已有模型复用与新增关系、生产/消费链路 |
| 测试报告 | 实际命令、环境、数据范围、用例结果、真实与替身边界、失败复现 |
| 运行与验收说明 | 启动、迁移、配置、依赖检查、统一验收入口、隔离测试数据准备和清理 |
| 继续执行记录 | 仅在未全量完成时保留明确待办、下一步、阻塞，不用“后续优化”掩盖未实现 |

### 7.3 最终报告格式

1. 本次实际采用的 UI / 前后端代码版本。
2. 范围内 Feature 总数、已真实 E2E 通过数、未实现数、阻塞数；不同粒度和重复映射不混加成百分比。
3. 新增了哪些原本缺失的领域与运行能力，分别有哪些完整结果证据。
4. 关键旅程及真实模型/媒体测试结果。
5. 与当前 v3 基线的差异及原因。
6. 已知缺陷、待用户裁定与外部阻塞，注明是否阻止全量完成。
7. 用户统一验收的操作入口与建议顺序。

不得以“路由都注册了”“接口都返回 200”“全部使用真实 Client”“53/53 已映射”或“构建和 Mock 测试通过”替代这些证据。

## 8. 给执行者的结束指令

完成必要核验后开始实际实施，并按总台账连续推进。不要仅交计划，不要只接已有 API，不要恢复旧 UI，不要把缺少的后端能力留成默认占位，不要以修完当前 Bug 结束任务。

最终目标是：**同一套已确认的 v3 页面，承载完整、真实且持续运行的摇光业务；全部确认能力完成后统一交付用户验收，再进入后续优化。**
