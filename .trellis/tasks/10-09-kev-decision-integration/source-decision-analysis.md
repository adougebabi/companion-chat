# 摇光 Kev 主动生效接入：本地 Codex 实施任务

## 0. 任务目标与执行方式

在当前摇光仓库中完成 Kev 判定能力的实际接入。本轮不是调研、不是只接 API、不是只记录 shadow 结果：四类场景全部接入，交付的本地测试配置全部启用，Kev 的有效判断直接影响运行。

四类场景：

1. 是否运行 WakeUp、反思、目标完成检测、新目标规划。
2. 本次 Agent 运行预先披露哪些 Tool／Capability。
3. 当前声明的人格切换条件是否成立。
4. 本次注入哪些记忆、事件和目标详情，控制上下文体积。

必须同时做到：

- 全局开关关闭时完全跳过 Kev，走接入前的原流程；每个决策点也可以单独关闭。
- Kev 超时、不可用、返回不合法或明确弃权时，该决策点回到原流程。
- 记录每一次实际判定的原始输出，以及它最终是否生效、影响了什么。
- 保留现有 Agent、Eino 原生 loop、Tool 插件化以及领域校验；不借机重构整个系统。
- 不先实施 shadow 再等待批准；本轮默认直接生效。可以保留已有 shadow 能力，但不得让它成为本轮交付的前置条件或默认模式。

先检查真实代码并建立改造映射，然后继续完成实现、配置、测试和报告。不能把本任务只转换成待办后结束。文件名、类名、函数名以仓库实际结构为准，下文名称是逻辑职责，不要求照抄目录。

## 1. 已知基础与范围边界

### 1.1 已知基础

- 当前候选后端为用户已经在本地运行和测试过的 `Jakevin/kev-4b-ternary-mlx`。
- 已验证请求接口为 `POST /v1/systemone`，采用 `state + questions -> answers`，本轮默认仅使用 `choice`。
- 本地测试接口示例为 `http://127.0.0.1:8010/v1/systemone`。它不是可直接写死到所有部署环境的生产地址。
- 用户的主机同时承担主 LLM 和 ComfyUI 负载；不要为了接入另起 Laya、第二个大模型或一套 Python 推理服务。
- 现有模型使用其自带 runtime；业务系统只通过 HTTP 调用。不要改为普通 Chat Completions，不要用 mlx-lm 加载替代。
- 用户提供的完整结果中，82 个具体问法用例的 choice 为 78 正确、3 错误、1 弃权；这是合成场景的探索结果，不是生产准确率承诺。

### 1.2 本轮不做

不引入新的总控 Agent、不替换 Eino loop、不改造整个日程／事务／工作流系统、不重写 GoalPlanner、不改写人格设定、不更换主 LLM、不微调模型、不引入外部云模型兜底、不自动下载或升级 Kev 权重。

本轮保留原流程是明确需求。这里的“原流程”必须是单一原实现，不是复制出一套逐渐分叉的 legacy 系统。

目标容量、物品所有权、数据库真实状态、权限、时间比较等确定性规则继续由程序处理。Kev 的判断不能覆盖这些规则。

### 1.3 原行为基线

先记录当前提交和已有测试结果，定位下列入口：

| 范围 | 必须定位的真实代码 |
| --- | --- |
| 调度 | WakeUp、反思的触发器、资格检查、并发去重、冷却和执行入口 |
| 目标 | 完成检测入口、完成证据来源、目标规划／补充入口、容量和依赖检查 |
| Agent | 统一运行封装、Eino 版本、可用中间件／状态扩展、流式与 Tool 执行时机 |
| Tools | Tool 注册表、Capability 元数据、每个 Agent 的权限集合、工具发现／补载入口 |
| 人格 | 当前激活人格、候选切换规则、切换判定器、实际提交切换的唯一入口 |
| 上下文 | Prompt／Slot 拼装、Working Persona、Actor 背景、动态状态、目标、记忆和摘要装配 |
| 配置和诊断 | 动态设置、管理员权限、诊断持久化、BFF、前端诊断界面 |

输出简短的入口映射，随后实施。若此前讨论过的能力在代码中不存在，不得将它标成“已接入”；先检查是否有等效入口，仍没有则在本轮报告明确列为缺失，不能用空方法或假返回通过验收。只补本次接入真正需要的最小连接能力，不扩展成另一轮业务系统重建。

## 2. 共用判定层与原流程分支

### 2.1 逻辑组件

复用现有框架，增加以下职责：

- `KevClient`：HTTP 调用、请求取消、协议解析、响应上限。
- `DecisionSpec`：决策点 ID、版本、有限问题、最小状态构造、允许选项。
- `DecisionService`：开关、预算、Kev 调用、答案校验、策略解析、决策记录。
- 各业务入口的应用适配：把有效结论应用到当前流程；无法采用时调用原实现。

不要求创建通用插件市场、复杂工作流 DSL、独立调度平台。先服务以下七个明确决策点即可：

| 决策点 | 判断对象 | yes | no | use_original |
| --- | --- | --- | --- | --- |
| `runtime.wakeup` | 当前自动唤醒候选 | 运行原 WakeUp 执行体 | 延后本次候选 | 原触发路径 |
| `runtime.reflection` | 当前自动反思候选 | 运行原反思执行体 | 延后本次候选 | 原触发路径 |
| `goal.completion_check` | 某目标的新证据／关联事件 | 运行该目标的原完成检查 | 本次暂不检查 | 原检查路径 |
| `goal.replenish_plan` | 一次现有目标规划候选 | 运行原 GoalPlanner | 本次暂不规划 | 原规划路径 |
| `tools.select` | 每个允许的候选能力 | 预先披露 | 不预先披露 | 保留该候选的原选择结果 |
| `persona.switch` | 一条已声明切换规则及目标人格 | 通过原切换入口提交 | 保持当前人格 | 原人格判定路径 |
| `context.select` | 每条可选上下文候选 | 纳入本次请求 | 不纳入本次请求 | 保留该候选的原装配结果 |

`use_original` 是明确的内部结果，不是 `false`，也不是“什么都不做”。没有可靠判断时绝不能隐式变成“不运行”“不切换”“删除记忆”。

### 2.2 只做一次语义判定，复用原执行体

启用且 Kev 返回可采用的 yes／no 时，不要再运行原语义判定器进行第二次投票。否则 Kev 实际不起作用，成本反而增加。

程序硬校验、权限校验、合法状态转换仍正常执行。应把原代码中“判断”和“执行”做必要的局部拆分，共用原执行函数，而不是复制业务操作。

关闭、弃权或异常时，调用原判定／装配／触发函数。原函数应延迟调用，不能为了准备 fallback 先运行一次旧 LLM。

禁止把用户本次取消整个请求当成 Kev 故障：业务 context 已取消时直接结束，不再启动原流程或新任务。只有 Kev 子调用自己的超时／错误才触发原路径回退。

## 3. 开关、配置和生效语义

### 3.1 必需设置

在现有配置机制中支持：

- 全局 `kev.enabled`。
- 七个决策点各自的 `enabled`。
- `endpoint`、可选的受保护凭据、请求超时、并发上限。
- `choice` 策略及可选的额外置信门槛。
- 诊断记录保留时长、自动任务的最大延后约束。

交付的用户本地配置：全局启用、七个决策点启用、策略为本轮实测的 `choice_argmax`。不得只在示例里启用，而实际代码默认全部走原路径。不要修改未授权的远程／生产配置。

配置应接入现有管理界面，至少可以保存全局开关、七个分项开关、endpoint，并查看当前生效状态。修改开关不应要求重新构建前端或重新部署后端。

### 3.2 关闭意味着真正旁路

全局或分项关闭时：

- 不调用该点 Kev HTTP 接口，不进行预热、自动健康探测或后台影子判定。
- 不为该点额外执行候选召回和提示词构建；业务原流程本来需要的数据读取不受影响。
- 不注入 Kev 指令、结果、特殊 Tool 描述或额外会话消息。
- 使用原有 Tool 集合、原上下文装配、原人格判定及原调度规则。
- 可以写一条轻量的 `disabled / original` 路由记录，但不得伪造模型输出，不能每个 scheduler 空轮询都刷大量记录。

同一模型请求中已发出的内容无法撤回。开关关闭后，下一次尚未发送的模型请求应恢复原装配，并保留已经发生的合法对话、Tool 结果和事实。不能为了恢复原流程重复发送消息或回滚已成功购买的物品。

Kev 正在调用期间关闭开关：在应用结果前重新检查开关。旧结果留痕，但不再生效；当前业务请求未取消时走原路径。以 `config_version` 和可见的 `discarded_after_disable` 原因记录。

### 3.3 初始运行参数

以下仅为本轮工程起始值，不是性能保证，使用现有配置风格落地：

| 项目 | 起始建议 |
| --- | --- |
| HTTP 单请求超时 | 1500 ms，允许配置 |
| 一次选择阶段总预算 | 3000 ms，包含排队和全部分批请求 |
| 同实例 Kev 并发 | 1；优先复用现有并发控制 |
| 单批问题数量 | 最多 8；先验证当前 runtime 批量契约 |
| 自动重试 | 默认 0，失败立即回原路径 |
| 自动任务最大连续延后 | 默认 3 次，下一次合格机会走一次原路径；可按点配置 |
| 决策记录保留 | 默认 7 天，可配置，界面显示保留策略 |

优先使用已有超时、熔断、限流机制。不为了这一功能引入新的分布式中间件。多实例部署时注意单实例并发限制不等于服务总并发上限。

调用预算用尽时，对未完成的候选采用原结果，不要继续无限排队。网络请求不能放在业务数据库事务或 Actor 锁中执行。

## 4. Kev 协议与 choice 策略

### 4.1 协议示例

沿用已测通的协议，下面只是格式示例；正式问题来自有版本的 DecisionSpec。

```json
{
  "state": "用户：给我拍一张现在的全身照。",
  "questions": {
    "q_0001": {
      "type": "choice",
      "instructions": "Does the user request an image?",
      "criteria": {
        "yes": "The answer to the question is yes",
        "no": "The answer to the question is no",
        "unclear": "The available information does not determine the answer"
      }
    }
  }
}
```

响应示例：

```json
{
  "answers": {
    "q_0001": {
      "type": "choice",
      "choice": "yes",
      "confidence": 0.6111,
      "probabilities": {
        "yes": 0.7408,
        "no": 0.1212,
        "unclear": 0.1380
      }
    }
  }
}
```

传入的 state、问题和候选说明必须是业务数据，不包含 API key、连接串或无关隐私。采用当前 runtime 和现有脚本验证过的 state 表示；不要在接入时同时未经验证地更换模型版本、输入序列化方式和问题语义。

### 4.2 默认不新增 0.8 门槛

默认复用本轮 choice 测试行为：合法的 `choice=yes/no` 直接采用；`choice=unclear` 回原流程。

`confidence` 不等于 yes 概率，不能拿它冒充 `probabilities.yes`。同时记录选中项的概率、完整分布和前两名差距。

可额外支持 `choice_guarded`，由管理员显式配置选中项概率下限和前两名差距下限；不满足时回原流程。这个策略默认不启用，不能悄悄让大部分本次接入退化成旧流程。

修改策略、问题文本、criteria 或状态构造方式必须递增对应版本。初期不按单个测试样本挑选不同阈值，不自动学习或在线修改规则。

### 4.3 响应校验

检查 HTTP 状态、JSON 结构、question ID 映射、type、允许选项、有限且在 [0,1] 的概率、分布合计及 choice 与最大概率的基本一致性。允许合理的四舍五入误差，不允许 NaN、负值、不认识的人格／能力 ID 或错配答案。

未知的额外元数据可以保存在 raw 中；缺失必需字段和关键契约错误不能被宽松转换成 yes。

整份 HTTP 响应无效则整批回退。部分 question 缺失或无效时，独立候选逐项回退；其他有效结果可以继续使用。存在依赖的 Tool／上下文组合，应用前必须做整体依赖闭合与事实完整性检查。

不要强迫 Kev 输出自然语言理由。现有 scorer 只给出了选项／概率时，reason 由程序标为 `model_selected_yes` 等策略说明，不伪造模型解释。

## 5. 调度四个判定点：实际阻止或放行候选任务

### 5.1 接入位置

沿用当前触发器产生运行候选，先执行原资格检查，然后调用对应 Kev 决策点。不要每几秒遍历全部 Agent 让 Kev 决定跑谁。

明确不合格的任务，例如自治未开启、角色正在执行同一任务、权限不允许、还在原冷却期，不调用 Kev。

程序能够直接确认必须处理的事件，仍按原强制语义处理，例如人工“立即执行”、明确不可延误的已到期承诺、与某目标直接关联的权威完成事件。沿用现有强制语义；确需补充兜底时集中声明并测试，不在多处散落特例。

Kev 重点控制自动触发中的可延后候选。它返回 no 必须真的延后这一轮，而不能记录 no 后继续照常执行。

### 5.2 最小输入

| 点 | 必需的精简输入 |
| --- | --- |
| WakeUp | 触发原因、当前生活状态、未处理事件摘要、到期／自主思考机会标记、距上次运行时间 |
| 反思 | 自上次反思后的新增事件、程序统计的失败／重复行为、目标变化和上次反思时间 |
| 完成检测 | 目标 ID／版本、完成条件、新证据 ID 与摘要、原检查时间 |
| 目标规划 | 活动目标精简目录、剩余容量、最近完成／取消结果、规划相关背景变化 |

数量、时刻和状态比较先由代码得到，不要求 Kev 从长段文本中重新数目标或计算时差。

问题需分别表达“是否值得执行该流程”，而不是让 Kev 代替执行结果：`goal.completion_check=yes` 只是启动检查，不代表完成；`goal.replenish_plan=yes` 只是调用 GoalPlanner，不代表立即插入一个新目标。

### 5.3 防止延后变成永久丢失

Kev 返回 no 时不推进原 `last_run_at`、已处理事件游标、已反思标记或完成检测水位。新增独立的 `last_decision_at / deferred_until / deferral_count` 等必要信息，复用现有机制优先。

相同事件可以合并／冷却，不能被当成“已经处理成功”。新证据、状态变化和兜底到期后仍能触发。

保留没有外部消息时原有的周期性自主思考机会，避免系统永远没有主动行为。达到配置的最大延后边界时，下一次合格机会使用一次原路径，记录 `max_deferral_original`；仍然先通过睡眠、权限等原硬约束。

“运行 WakeUp”不等于“角色醒来”。Kev yes 不能直接改变睡眠、地点、着装或情绪；变化继续来自合法的行动／事件。

### 5.4 目标流程顺序

目标完成检测提交成功之后，才以最新目标版本决定是否补充规划。两者不能同时读取旧快照后各自写入。

目标容量沿用现有配置，用户目前倾向最多 5 个。保留旧目标优先级、排序、依赖约束；Kev 不创建新目标、不修改排序、不清空旧目标。允许 GoalPlanner 返回“本次无合适目标”，避免强行补满及持续重复规划。

活动目标归零且自治允许时，必须保留有界时间内重新规划的机会，不因一次 Kev no 永久停摆。批量规划落库时再次核对容量和版本。

## 6. Tool 预注入：多选、可补载、真实可执行

### 6.1 候选与权限

候选先由代码限定为当前 Agent／Actor 原本允许使用的能力，再交给 Kev 做相关性选择。不能把整个系统所有 Tool 暴露给判定器，也不能通过 Kev yes 获得新权限。

每个候选能力一个 yes／no／unclear 问题，允许同一次选中多个能力。不得用单选“聊天／生图／日程”替代多工具任务。

优先复用已有 Capability 分组和 Tool 元数据。不存在分组时，先按真实 Tool 注册元数据接入，不为分组重写插件体系。

### 6.2 原集合、必需集合和选中集合

保持原始允许集合和每次运行的独立可见集合。当前 Agent 的必需出口、必要查询和能力发现入口不能被筛掉；具体 Tool 名称由仓库实际能力确定，不把示例名称硬编码为必然存在。

- yes：预先披露该能力及其确定性依赖。
- no：本轮初始不披露，但保留允许范围内的发现／补载能力。
- unclear／错误：该候选沿用原披露策略。

Tool 被预加载不等于被执行；选择生图能力不能自行触发生图，选择购买能力不能自动完成购买。

### 6.3 Eino 实际装配

选择结果必须同时对齐模型请求中的 Tool schema 与执行层可调用对象。

可行方式是保留完整的授权执行注册表，按本次运行过滤模型可见的 ToolInfo；能力发现后，在下一轮模型调用之前加入对应 ToolInfo，并确认执行器能找到真实 Tool。

禁止仅将 Tool 名称写入普通提示词。禁止对共享单例的工具列表做原地修改，导致 Actor A 的筛选影响 Actor B。

按仓库 `go.mod` 对应的 Eino 能力接入。当前官方文档推荐在支持它的版本里通过 `BeforeModelRewriteState` 修改 `ToolInfos`，而不是在 `WrapModel` 中私自绑定另一套工具；不能把最新文档中的 API 强行写到旧版本。优先复用已有扩展点，不为此整体升级框架。[S2]

### 6.4 运行中补载

复用现有发现 Tool；不存在则增加一个最小的、可独立调用的能力查询／加载入口。Agent 能表达所需能力，代码从授权注册表解析并返回真实结果。

对本轮原本隐藏但被明确请求加载的能力，不能再次被同一次 Kev no 否决。否则会形成“漏选后无法补救”的死循环。

同一轮只增加必要能力，不频繁撤销正在使用的能力。新增工具需要的当前状态和数据访问条件也要补齐。无权限、能力不存在和加载失败须返回真实错误，不能伪造成功。

## 7. 人格切换：直接采用 Kev 判定，但保留合法提交边界

### 7.1 切换对象

只评估已经声明的切换规则和候选目标人格。不是问“谁更适合回答”“谁更甜”“B 是否表现更好”。

明确的时间或标志规则继续由程序判断。需要语义理解的条件交给 Kev；需要 A 的拟议反应才能判断的规则，仍在原来的提案阶段处理。

输入只包含当前人格 ID／版本、候选规则、必要事件、相关状态和必要的未执行提案，不注入所有人格完整设定与整段历史。不得让 Kev 生成不存在的人格 ID。

### 7.2 生效逻辑

- yes：经原切换 Tool／Capability 或领域提交入口切换，然后由新人格重新生成。
- no：保持当前人格，原语义切换逻辑不能在后面再次偷偷切换。
- unclear／异常／关闭：运行原判定路径。

多条规则同时 yes 时，使用原有优先级和冲突规则；没有明确胜出规则时回原判定，不随机挑选，也不按未经校准的不同问题概率直接比较谁更高。

一次相关运行最多完成一次持久切换。保留原冷却与事件消费机制，不发生 A→B→A 的反复重新判定。

### 7.3 先决定，再执行副作用

重点检查原代码的真实时序：如果采用 A 提案→切换判定→必要时 B 重生成，A 的 `reply`、购买、换装、日程变更等必须在判定前尚未提交。

可以保留获取判定证据所需的无副作用查询，但不能先把 A 的回复流式发送给用户，再宣布由 B 接管重写。必要时只缓冲有可能触发切换的对外片段，不把所有 Agent 改成双重生成。

同一批 ToolCall 中包含多个副作用时，切换检查应在放行该批副作用前完成，不能并行执行一半后再切换。

切换成功后，旧提案未执行的调用必须被真实取消／丢弃，不能伪造 Tool 成功结果，也不能留下破坏 Eino 消息协议的孤立调用。利用当前框架的取消／中断／工具执行入口完成，不另写一套 Agent loop。

提交前核对人格版本。判定期间人格已由另一合法事件变更时，不应用旧结果，记录 stale，按当前状态交回原路径。记录判断结果和实际切换结果，不能把 Kev yes 当作切换成功。

## 8. 上下文选择与压缩边界

### 8.1 必需信息与可选候选分离

在现有 Slot／上下文装配层增加可选择边界，不把整条最终 prompt 交给 Kev 自由删除段落。

每种 Agent 明确必需字段：当前人格简画像、身份与 Actor 归属、关键有效背景及约束、必要时间和生活状态、当前输入、进行中的 ToolCall 与真实结果等。按该任务实际需要保留，不意味着所有动态状态都全量常驻。

面向认知／WakeUp 的活动目标保留精简目录：ID、名称、优先级、状态、依赖／阻塞。用户当前目标数上限较小，不应让某个目标完全从感知范围消失。

可选候选包括相关历史记忆、事件摘要、人格细节、已完成目标经验、活动目标的详细进展。上下文筛选不修改目标的持久优先级和依赖。

### 8.2 选择过程

先通过现有主体、时间、目标关联、检索逻辑形成有限候选；再提交候选摘要给 Kev。选择结果只能引用本次候选真实 ID，从存储取回内容，不能接受模型新编出的记忆。

- yes：注入该候选。
- no：只从本次请求的可选内容中排除。
- unclear／异常：保留该候选的原装配行为。

禁止因此删除长期记忆、历史事件、已完成目标或源摘要。原始数据仍能被 Tool 检索。

强约束、当前事实、未处理承诺和正在执行流程所必需的证据不能由相关性筛选掩盖。初始化事实与当前有效状态冲突时，沿用现有权威状态覆盖规则，而不是按模型评分挑一个。

### 8.3 与 Tool 选择协同

采用有界的准备顺序：

1. 读取本次运行的权威最小快照和活动目标目录。
2. 结合当前事件和任务选择预披露能力。
3. 由代码加入所选能力必需的状态字段／依赖信息。
4. 对可选记忆、事件和目标详情进行筛选。
5. 进入原 Agent loop；后续发现能力／查询事实时按真实结果继续。

候选准备可以共享数据读取，但不同决策点仍分别记录。不要让“先选 Tool 必须先知道全部上下文”和“选上下文必须先知道全部 Tool”相互递归。

### 8.4 压缩与预算

Kev 本轮只做选择，不负责生成摘要。原有增量摘要、总结覆盖范围标记、历史压缩及硬预算保留，不新增一个 Kev 摘要模型。

不把决策日志、每次选中理由或完整候选列表追加到下一轮 runtime context。必要的执行事实按原事件机制更新，判断过程留在诊断系统。

一次请求预算包含协议、画像、动态状态、Tool schema、记忆／目标、工具结果与输出预留空间。候选筛选后的集合仍由程序检查预算；fallback 保留原内容时也必须走原预算处理，不无限塞入。

关闭 Kev 后，从权威状态及原历史重新执行原装配，而不是继续使用上一次经过 Kev 裁剪的持久列表。若框架内部状态跨 iteration 保存筛选结果，必须维护可恢复的原始集合／来源，不能把临时筛选当作源数据。

## 9. 每次判定留痕：模型说了什么，程序做了什么

### 9.1 必须持久化，不是只打印 stdout

优先复用现有诊断存储及 Trace；承载不了再增加轻量决策记录存储。每个实际 question 都可单独追溯，多问题共享一次 HTTP 调用时保留共同 request ID，不把 HTTP 次数当成判定点次数。

至少记录：

| 字段组 | 内容 |
| --- | --- |
| 关联 | decision ID、request ID、trace/run/event ID、actor_self、相关 actor_user、Agent、决策点、目标／候选／规则 ID |
| 版本 | DecisionSpec 版本、问题版本、策略版本、配置版本、候选集与相关状态版本、配置模型标识、服务实际返回模型标识 |
| 输入 | 实际提交的 state、questions、criteria，脱敏后的请求；候选 ID 与原选择集合 |
| 输出 | 完整原始响应或持久化引用、每题原始 answer、choice、confidence、完整 probabilities、选中项概率、前两名差距 |
| 调用 | 开始／结束时间、耗时、HTTP 状态、调用状态、错误类型、重试次数、服务返回 usage／latency（缺失保留 null） |
| 应用 | 策略结果、实际生效来源、是否回原流程、原因、前后选择集合、实际任务／切换／工具调用关联 ID |

原始输出可以先脱敏再落库，但不能只保存一个 `true`，也不能用截断后的摘要冒充原始 JSON。对允许的响应大小设上限；超出按契约错误回退并记录大小／受限原文，不能悄悄接受未留存的结果。

### 9.2 分离三层状态

不要用一个 `success` 混淆所有结果：

- `call_status`：not_called／ok／timeout／unavailable／invalid_response／cancelled。
- `policy_outcome`：yes／no／use_original。
- `application_status`：applied／original_used／stale／cancelled／not_applied。

另外记录 `fallback_reason` 和 `rule_reason`。例如 Kev 返回 yes，但提交前发现目标已满，应该显示“模型 yes，程序硬约束阻止”，不能显示“Kev no”。

没有实际运行原判定时，不编造“原流程原本会如何决定”；可以记录原候选集合或入口，但原模型结论应为未执行。

### 9.3 可靠性和隐私

实际模型输出持久化成功后再应用结果，或者写入已有的可靠持久化队列／本地追加日志。不要为了审计长期持有业务事务。

若主诊断库暂不可写，优先复用可靠暂存机制；没有则使用受容量限制、配置了持久卷的本地追加日志。两种存储均不可用时不采用未留痕的 Kev 结果，回原流程并发出明确诊断告警。不能用无界内存队列宣称“每次都记录了”。

调用开始可以写 pending 记录，完成后更新。取消、崩溃遗留 pending 标为结果未知／中断，不在启动时自动重放业务副作用。

诊断访问沿用现有管理员／Actor 权限隔离，凭据永不明文展示。输入快照限于真正提交给 Kev 的必要片段，不另外导出整段私密历史。保留期到期按显式策略清理。

## 10. 诊断界面与管理入口

在现有诊断中心增加 Kev 决策视图，不另建一套前端项目。

列表支持按时间、Actor、Agent、决策点、选项、fallback／错误过滤，按 `started_at DESC, id DESC` 稳定倒序；不能按异步落库顺序导致旧记录置顶。

详情展示：判定输入、问题与选项、raw response、完整概率、实际采用策略、执行／回退原因、相关 run 和真实行动记录。

同时展示“模型结论”和“实际动作”，例如：

- 模型 no → 本次反思延后。
- 模型 unclear → 原反思流程已执行。
- 模型 yes → 切换提交因版本过期未采用。
- 全局关闭 → 未调用 Kev，原 Tool 集合直接装配。

支持按筛选条件导出 JSON，保留 request/question/decision 的关联，便于继续离线复核。统一使用带时区的时间：内部存 UTC，API 输出 RFC3339，界面按用户／Actor 配置展示且显示时区，不混用无时区本地字符串。

系统只统计调用量、采用率、拒绝率、弃权／回退率和延迟，不能把 `application_status=applied` 称为“判断正确率”。正确率需要人工标注或独立预期数据。

## 11. 地址、版本和启动条件

`127.0.0.1:8010` 只在调用进程与 Kev 服务处于同一网络环境时成立。Go core／worker 若在 NAS、Docker 或另一台机器，必须配置从那个进程实际可达的 Mac 地址或受保护代理地址，并从该运行环境执行连通性验证。不能把 Mac 上 Python 测通当作 NAS 已可访问。

保持内网可达与访问控制，不为了连通把未鉴权服务开放到公网。请求凭据只从现有 secret 配置读取；是否需要认证以当前服务／代理实际部署为准，不臆造协议要求。

固定已测通的本地权重和 runtime。记录 revision／manifest hash；没有可得 hash 时明确 unknown，而不是以 `kev-latest` 假定模型版本已知。当前模型仓库有多个发布版本，本轮不能擅自升级后继续引用旧结果。[S1]

全局关闭时系统必须在没有 Kev 服务、没有模型文件的环境正常启动。启用但 endpoint 暂不可用时，清晰显示降级并走原流程，不让整个应用启动失败。

手动“测试连接”属于管理员明确操作，可以独立执行；不得偷偷当作关闭状态下的周期性探测。测试连接只调用无副作用的协议检查，不启动业务 Agent。

## 12. 必须完成的测试

### T1. 原流程旁路等价性

全局关闭、逐项关闭、服务不可用分别验证。使用固定状态与可控模型／Tool stub 比较接入前后的模型请求、Tool schema、提示词和领域调用轨迹。排除 trace ID、真实时间等非业务差异；不以随机 LLM 的自由文本逐字相等作为标准。

断言关闭状态 Kev HTTP 次数为 0；不多调用原 LLM；原有 Agent 和 Tool 正常可运行；无额外 Kev 信息进入提示词。

### T2. 协议与选择策略

使用本地假 HTTP server，测试合法 yes／no／unclear、缺少题目、额外元数据、未知选项、NaN／越界／错配概率、空响应、HTTP 500、慢响应、部分问题失败、业务取消。

默认 choice_argmax 下，低概率但合法的 yes／no 仍按所选项采用，与旧 benchmark 行为一致。guarded 开启后按配置回原流程。原始模型结果不能被策略覆盖掉。

### T3. 七个点均真实生效

每个点至少一组 yes、no、unclear／错误和 disabled 测试，验证的是原执行器／装配器是否真的走到正确分支，不是仅验证 parser。

### T4. 调度和目标一致性

no 不消耗原事件水位、不改 last_run_at；延后上限生效；强制事项和人工执行不被错误压制；睡眠不会因 WakeUp yes 自动变成醒来；同任务不重复运行；完成提交后才补充规划；并发下容量与依赖约束仍成立。

### T5. Eino Tool loop 与插件独立性

至少覆盖“预选漏掉工具→Agent 发现／补载→下一轮 schema 真正增加→Tool 实际调用→返回真实结果→Agent 继续”。

覆盖同时选中多个能力、依赖补齐、未授权工具无法调用、Actor 之间不串可见工具、补载能力不被旧 no 再次隐藏。

所有新增或受影响的 Tool 必须脱离 Agent 可独立调用；每个受影响的 Agent 至少一条走通其真实 loop 的测试。不能只测模型第一次输出。

### T6. 上下文与恢复

检查 required 信息、活动目标目录、未完成承诺、ToolCall／ToolResult 配对及预算不被破坏；no 只影响本次装配，不删除存储；候选 ID 无效按点回退；关闭后恢复原装配，不沿用旧裁剪列表。

### T7. 人格副作用边界

覆盖 A 提案时 B 接管、Kev no 保持 A、弃权回原判定、切换失败、并发人格版本变化、批量 ToolCall、流式回复尚未对外发出等情况。

证明被丢弃的 A 提案没有先产生消息／购买／日程变更；切换只有一个提交入口；不存在 Kev no 后原 Main 再次私自切换，也不存在一轮多次接管。

### T8. 开关和留痕

Kev 请求中途关闭、结果返回后但提交前关闭、诊断库失败、暂存失败、任务取消、服务熔断／预算耗尽，均有明确记录或显式告警。

批量一次 HTTP 的每个 question 均有可查询结果；导出能还原输入、raw answer、策略与应用。日志时间稳定倒序，Actor 权限隔离有效。

### T9. 模型回放与真实接口测试

若本地存在用户提供的 `kev_fluctlight_results(1).json`、原 benchmark 脚本，复用它们做协议回放和已知错误回归；不要假定聊天附件自动存在于项目目录。缺失时使用本任务协议样例建立固定 fixtures，并在报告标明未使用完整回放文件。

旧报告里已知错误不能改 expected 或移除后宣称全通过。区分“适配器正确复现原答案”与“答案符合业务预期”。

真实 Kev E2E 显式使用本地 endpoint，四类场景都测试 active 分支。业务写入限制在隔离测试 Actor／测试数据，不向真实用户发送消息、不支付、不发布动态；使用相同领域代码与隔离存储，外部副作用使用可验证的测试适配。

如果执行环境访问不到 Kev，应提交可运行测试命令并明确“真实接口 E2E 未执行”，不能把 mock 测试说成真实推理通过。这不构成只交付设计的理由，继续完成其余代码和测试。

### T10. 项目回归

执行仓库实际的后端测试、相关集成测试、前端类型／构建检查。记录命令、退出码、通过／失败数量。对原有失败、环境阻塞和本次引入失败分别说明，不能把所有失败统一归为环境问题。

## 13. 实施顺序与交付物

按以下顺序完成，但作为同一轮改造交付，不在每一步结束后等待额外确认：

1. 基线盘点、真实入口映射、原流程回归基准。
2. Kev HTTP adapter、DecisionSpec、开关、choice 策略和持久记录。
3. 七个决策点的真实应用适配，保留原路径。
4. Tool 补载、上下文来源恢复、人格提交前检查、延后兜底。
5. 现有设置界面的开关与诊断详情／导出。
6. 固定 fixtures、真实可用接口测试、后端／前端回归。
7. 本地全启用配置和最终报告。

交付至少包括：

- 代码、配置、必要数据库 migration、前端设置与诊断视图。
- 原入口到新决策点的映射表，以及哪些代码被共用而非复制。
- 一键关闭全局、只关闭某点、修改 endpoint、查看／导出决策的实际操作说明。
- `kev-integration-report.md`，附测试命令和证据。
- 已知问题、未验证行为、框架版本限制和真实 Kev 可达性说明。

最终报告逐项区分：

| 状态 | 含义 |
| --- | --- |
| 工程接入完成 | 配置、调用、应用、旁路、日志和测试连接点实际实现 |
| 真实模型行为验证 | 指定模型／版本在真实调用中做了什么，不等同于准确率保证 |
| 业务效果待观察 | 开启后主动性、Tool 漏选、上下文遗漏和人格行为的真实使用效果 |

不能用“模型测试得分较高”代替工程验收，也不能用“代码已经编译”代替四类场景真正接入。
