# 单人格共享场景与人格生图策略

## Goal

让用户与单个 AI 人格在一个可持续的共同场景中互动。人格的回复不再只有语言，还可以包含可见动作、场景变化和由人格触发的图片生成，使聊天表现为两者共同经历的一段时刻。

本任务只覆盖“用户 + 单个人格”的同场景交互。多个人格共享同一空间、跨人格世界和多人协同暂不纳入。

## Background And Confirmed Facts

- 当前项目已有单人格的生活状态、日程、生活事件、活动、主动消息和持久化媒体任务链路。
- 当前聊天上下文已经可以注入人格当前状态；现有媒体意图契约可以把经过验证的图片请求排入 durable job。
- 当前还没有独立的通用动作模型，也没有用户与人格共享的当前场景模型。
- 人格详情需要新增“人格生图频率”设置，设置属于人格，而不是每次由用户临时控制。
- 新建人格默认采用“人格自行决定”；其他四档主要用于开发调试、行为对比和问题复现。
- 用户希望保留人格行为的不确定性。MVP 不预先增加生图次数、冷却时间、重要性判断、自动化拦截或额外安全策略；系统只负责验证格式、保存状态和执行人格已经决定的动作/生成请求。

## Product Decisions

- 括号动作是用户可见的自然叙述形式；MVP 不要求对动作文本进行独立解析，模型通过系统提示词理解其含义。
- 一次人格回合可以同时包含语言、动作、场景变化和媒体意图。
- 用户明确要求生图时，应直接覆盖人格的默认生图频率偏好。
- 图片是动作/场景事件的结果，应附着在原交互上；生成中、成功和失败状态都需要保留原有对话与动作。
- 交互目标是接近人与人之间的自然互动，不设计成选项式分支或固定文本驱动的叙事系统。
- 用户与人格使用同一套表达：普通自然语言描述内容，括号中的自然语言描述动作；例如“我把伞递给你（把雨伞递给你，并且自己往隔壁挪了挪）”。
- 括号动作是自然叙述而不是命令语言。模型结合整段对话理解其含义；服务端不因出现括号或某个固定词而直接触发副作用。
- 括号动作不是每次回复的必需格式；人格只在认为自然且有意义时加入动作。
- MVP 通过系统提示词向模型说明上述表达约定，不增加隐藏的第二次语义整理调用；服务端保存消息原文并继续使用现有模型能力契约处理明确的媒体作业。
- 重大场景切换使用一个模型原生的场景事件 function；人格先通过自然语言和用户交流，确认后由模型自行决定是否调用 function，服务端只执行 function 参数，不匹配用户文字。
- 场景事件 function 统一支持 `start`、`switch`、`end` 三种操作；它是唯一的持久化共同场景切换入口。

## Requirements

### R1. 单人格共同场景

- 人格与用户拥有一个可被连续对话复用的当前场景，至少能够表达地点、时间/时段、正在进行的活动、参与者、氛围/心情和可见物件。
- 当前场景进入人格聊天上下文，并能影响人格的语言、动作和媒体概念。
- 当前场景是持续投影，而不是每条消息临时创建的画面；场景能够从日常聊天中的明确计划或事件开始，并在后续回合中保持连续性，直到事件结束或被新的场景替代。
- 人格可以自主产生当前场景内的轻量动作；跨地点或跨活动的重大场景变化必须先向用户提议，得到用户确认后才能成为新的当前场景。
- 跨地点或跨活动的重大场景变化必须通过场景事件 function 持久化，function 调用产生可解释的事件记录并更新当前场景上下文。
- 场景提议只能通过自然语言对话确认，不提供确认、拒绝、替换等快捷按钮，也不把交互设计成固定选项式分支。

### R2. 括号动作表达

- 人格回合支持可见动作，例如表情、手势、移动和物件交互；模型按照系统提示词以自然的括号动作表达，前端原样保留并以一致的视觉方式呈现。
- 用户和人格的消息都可以包含普通自然语言与括号动作，前端以一致的视觉方式呈现两者。
- 正常聊天不显示独立的当前场景面板；用户通过普通语言、括号动作和图片感知场景，完整场景状态只作为人格上下文和调试数据存在。
- 括号内容本身不触发任何服务端副作用；是否改变场景或触发媒体由模型在本次自然回复中自行判断，媒体仍需使用现有明确的模型能力契约。
- 括号动作不需要 function；场景事件 function 只负责正式的场景开始、切换和结束，避免把每个短暂动作都变成状态机事件。
- 系统不得通过关键词、固定短语、正则表达式或其他固定文本匹配来触发动作、场景切换、用户确认或媒体生成；服务端不从用户原文猜命令。

### R3. 人格生图频率

- 人格详情提供以下五个互斥选项：`始终询问`、`始终生成`、`重要时刻自动生成`、`只有我要求才生成`、`人格自行决定`。
- 选项持久化到人格配置，并在人格上下文或能力策略中可被模型读取。
- “人格自行决定”是默认和主要产品模式；其他四档属于调试/实验模式，但仍需保持可切换和可验证。
- 人格生图频率在人格详情中以一个普通下拉框呈现，五个选项都可选择；人格列表和其他默认界面不额外展示该设置，用户进入详情后查看当前值。
- `始终询问`要求人格在生成前先向用户发出询问；`只有我要求才生成`禁止人格主动发起生成；`始终生成`允许人格在产生视觉动作时直接发起生成；另外两个选项分别交给事件显著性和人格判断。
- 这些选项在 MVP 中不附带次数、冷却、预算或额外安全限制。

### R4. 图片生成联动

- 人格可以在动作或场景事件中声明拍照或其他图片生成意图；MVP 只处理图片。
- 聊天优先使用模型原生 `media_event` function 创建图片任务；旧 `<media-intent>` marker 继续作为兼容路径，同一回合不能重复创建任务。
- 生成请求必须带有当前场景和动作事实，不能让媒体 worker 在重试时重新猜测动作含义。
- 媒体请求中的当前场景事实优先来自最近一次已持久化的场景事件，再结合当前对话中的短暂动作。
- 前端展示稳定的生成中状态；生成成功后将媒体附着到触发它的消息/事件；失败时保留文字和动作，并展示可理解的失败状态。

### R5. 交互表现

- 聊天界面能区分人格说的话和人格正在做的动作；当前场景不通过独立面板展示。
- 用户能够只通过自然语言推进、接受、拒绝或改变场景，例如发起外出、改变地点、要求拍照或要求停止拍照；这些意图由模型语义判断，不由固定文字匹配判断。
- 当用户对场景提议的回复含义模糊时，模型继续结合上下文自然处理，可以追问、调整提议或暂时保持当前场景；不使用固定词表决定是否切换。
- 用户可以在普通消息中自然描述自己的动作，模型结合上下文回应，不要求额外的用户专用动作 API。
- 所有括号动作都保留在对话记录中；只有模型明确调用 `scene_event` function 才会写入持续场景事实。
- MVP 不做多个 AI 人格同时进入同一场景，不建立跨人格共享事实或跨人格事件参与者模型。

## Acceptance Criteria

- [ ] 创建或编辑人格时可以通过下拉框保存并读取五档“人格生图频率”设置，新建人格默认值为“人格自行决定”；列表等默认界面不额外展示该设置。
- [ ] 系统提示词明确说明普通文字与括号动作的表达约定；人格可以自然选择是否在回复中加入括号动作。
- [ ] 用户和人格消息中的括号动作会原样保留并渲染，且不会被服务端当作副作用命令执行。
- [ ] 当前场景在连续回合之间保持一致，并能进入下一次人格上下文。
- [ ] 系统向模型提供场景事件 function；模型调用后会持久化场景事件并更新下一次上下文中的当前场景。
- [ ] 普通括号动作不会自动创建场景事件；只有模型明确调用场景事件 function 才会写入持久化场景事实。
- [ ] 场景提议只能通过自然语言回复推进，不出现确认按钮或固定选项式 UI。
- [ ] 用户的接受、拒绝、犹豫和改议不依赖固定词表或正则匹配，而由人格模型结合上下文自然回应。
- [ ] 用户对场景提议的模糊回复不会被系统直接归类为接受或拒绝，而由人格继续自然处理。
- [ ] 用户和人格的括号动作都会保留在对话记录中；服务端不从括号文本单独提取场景事实，只有 `scene_event` function 调用会更新持续场景。
- [ ] 正常聊天不出现独立场景状态面板，场景信息通过消息、动作和媒体自然呈现。
- [ ] 人格不需要在每次回复中生成括号动作；普通对话可以只有自然语言，动作出现时才按统一格式渲染。
- [ ] 用户明确要求生成图片时可以触发媒体任务；“只有我要求才生成”时人格的普通视觉描述不会自动排队媒体任务。
- [ ] 聊天提供 `media_event` function；明确照片请求可以通过该 function 创建与 marker 相同的 `chat_image` durable job。
- [ ] 其他生图策略至少有可验证的行为差异：询问、直接生成、重要时刻生成和人格自行决定不再全部表现为同一种流程。
- [ ] 媒体任务的生成中、成功、失败状态都不会删除或覆盖触发它的文字/动作交互。
- [ ] 现有聊天 SSE 事件名和现有人格私有记忆边界保持兼容。

## Out Of Scope

- 多个人格共享一个空间或相互读取对方的世界/记忆。
- 完整的 3D/实时空间、可自由编辑的物理世界和高频动作模拟。
- 生图次数、冷却、预算、重要性评分和额外自动化安全拦截。
- 通过固定文字、关键词或正则表达式实现的意图识别与触发器。
- 视频生成、连续帧动画和实时视觉直播。

## Open Question

- 无；技术设计需要把已确认的 `scene_event` function 接入现有聊天和事件持久化链路。
