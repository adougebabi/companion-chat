# 人格生活模型与事件时间线

## Goal

把当前“固定三种自动生活变体”的实现，升级为完整的、人格驱动的生活模拟系统：

- 人格初始化时，由 LLM 根据身份、性格、兴趣、关系和生活阶段生成结构化生活模型；
- 生活模型定义固定时间事件、每日可偏移事件、随机正向事件和随机负向事件；
- 每天基于生活模型编排完整时间线，运行时按照时间、地点、前序事件、关系、预算、冷却和风险规则推进；
- 事件必须有开始时间、结束时间、状态、因果和可恢复路径；
- 没有明确安排时，人格进入自己初始化的默认房间/场景，而不是进入无上下文的通用空闲状态；
- “和用户聊天”是跨场景交互，不是普通生活事件的竞争者，可以在上课、逛街、吃饭、休息甚至睡眠场景下发生，但实际回复策略必须符合当前场景；
- 保留人格身份、生活世界、事件事实、状态投影、动态、媒体和主动消息之间的边界，避免 LLM 直接改写不可变人格或制造不可逆风险。

## Requirements

### R1. 人格初始化生成生活模型

- 在人格激活流程中，将明确用户输入与可推演信息分离。
- 使用 LLM 生成结构化生活模型，不允许 LLM 改写姓名、身份、年龄阶段、基础人格、用户关系边界或用户明确提供的配角事实。
- LLM 输出必须经过 JSON 解析、结构校验、地点引用校验、时间冲突校验、风险校验和字段/体积限制。
- LLM 调用失败或输出不合格时，必须使用确定性的完整 fallback 生活模型，不能阻断人格创建。
- 人格激活阶段采用同步 LLM 生活模型生成；人格创建前先构造安全基线，LLM 超时/失败/校验失败时直接使用完整 fallback，不采用创建后异步覆盖作为默认路径。
- 生活模型必须记录来源、schema 版本、prompt 版本、模型信息、是否使用 fallback 及有限的校验警告。

### R2. 结构化生活世界与默认房间

- 每个人格必须拥有默认归属地、默认房间和可引用的地点/房间字典。
- 日程和事件可以引用稳定的 `locationId/roomId`，同时保留面向用户和媒体提示词的渲染场景文本。
- 当不存在有效固定事件、弹性事件或活跃例外事件时，状态必须回落到默认房间/场景。
- 地点、房间和场景的生成必须服务于人格身份，不能每次事件重新随机改名。

### R3. 四类事件模型

生活模型必须支持以下四类事件，并区分模板、当天计划和实际发生的事件：

1. 固定时间事件：课程、固定工作、已确认约会等。
2. 每日可偏移事件：吃饭、睡觉、休息、自习、整理等具有时间窗口和可移动范围的行为。
3. 随机正向事件：逛街、约会、兴趣活动、偶遇、完成小目标等低风险、可逆事件。
4. 随机负向事件：轻微挫折、临时不便、短暂低落等 mild、可逆且必须有恢复路径的事件。

- “固定时间事件”“每日可偏移事件”是生活模型和当天时间线的结构性安排，不得被固定三选一逻辑替代。
- 随机正向/负向事件必须从人格生成的候选模板中选择；`no_event` 必须是合法选择。
- 事件模板必须包含时间语义、持续时长/结束条件、适用场景、前置条件、优先级、冷却、频率预算、风险级别和效果。
- 负向事件默认不得永久或不可逆地改变身份、关系、健康、财务、学业/职业或外观基础；自动生成只允许 mild、可恢复事件。

### R4. 当天时间线编排

- 每个人格每天生成一条可审计的时间线，包含固定事件、可偏移事件、空闲窗口和符合条件的候选事件。
- 明确用户确认的日程优先级最高；固定事件不得与其冲突；可偏移事件可以平移或跳过。
- 时间线必须支持事件开始、进行中、完成、跳过、替换、取消、延后、恢复等状态。
- 运行时必须根据下一次时间边界、用户消息、日程变化、事件结束和恢复条件推进，而不是每次 tick 随机创建一条独立事件。
- 同一时间段的事件必须有显式优先级和覆盖模式：无覆盖、叠加、替换、阻塞。
- 事件结束后必须回退到当时仍然有效的下层状态（固定日程、当天计划、日常作息或默认房间）。
- 服务离线恢复时不得补发过时的中间事件；过期计划应标记为跳过、过期或离线总结。

### R5. 事件因果与连续性

- 事件实例必须可以关联当天计划槽位、父事件、被替换事件、恢复事件和后续结果。
- 事件选择必须考虑人格特征、兴趣、已有 supporting characters、地点、近期事件、开放中的生活线索、重复度和用户最近交互。
- 人格初始化可以生成少量稳定的 supporting characters 候选；运行时事件可以首次引入或发展这些人物，但不得每天随机捏造新名字。
- 每个 supporting character 必须有稳定 ID、关系类型、生成来源、首次出现事件和可审计的关系变化；同一人物应优先被后续事件复用。
- 新人物数量、首次出现频率和关系发展速度必须受生活模型策略与运行时冷却限制。
- 系统必须记录候选被采纳、压制、跳过或过期的原因，支持 Debug Inspector 解释“为什么发生/为什么没发生”。
- 随机事件不能反复生成同一事件家族、同一场景、同一人物组合和同一文案；需要持久化的新颖度/重复度记录。

### R6. 跨场景聊天

- 聊天是独立的互动通道，不受“人格当前必须空闲”限制。
- 在任何生活场景下都允许用户发起聊天，包括上课、吃饭、逛街、通勤、休息和睡眠。
- 人格是否立即回复、简短回复、延迟回复、醒来后回复，必须由当前场景的 `interactionAvailability` 与中断策略决定，而不是由生活事件类型硬编码禁止。
- 睡眠场景必须支持至少一种完整、可解释的策略：被用户消息短暂吵醒并回复后继续睡；或保持睡眠并在合理醒来时间后回复。该策略应体现人格作息、睡眠阶段、消息重要性和用户关系，而不是无条件立即回复。
- 当睡眠决策为“不立即回复”时，不向用户显示额外的睡眠占位、系统提示、虚假已读或预计回复时间；用户消息正常持久化，系统内部为该消息/对话计算自然的 `deliverAt`，到时以普通助手消息形式投递。
- 一旦睡眠决策已经确定为“不立即回复”，该决策在本次待投递批次内不可被后续消息打断或改写；后续消息只追加到同一待处理对话批次，等既定 `deliverAt` 到达后统一理解并投递一条普通助手消息。
- 延迟投递期间，生活状态可以继续推进，但不能因此唤醒人格或把本批次改为即时回复；若投递任务失败，只允许按同一批次重试，不得生成重复事实回复。
- 聊天不能无授权地改写当前生活事件；若聊天造成了用户确认的计划或明确生活影响，必须通过显式日程/事件入口进入时间线。
- 聊天回复应能携带当前地点、正在做的事、可用注意力、是否被打断、预计回复延迟等上下文，但不能泄露内部调度规则。
- 普通场景中的聊天默认是当前生活事件上的 overlay interaction，不直接替换生活事件；聊天会消耗注意力/时间，持续影响达到阈值时才允许推迟或压缩可偏移事件。
- 聊天不得覆盖固定时间事件、用户明确确认的日程或高优先级恢复/安全状态；若确实需要打断，必须由事件优先级和中断策略明确裁决。
- 睡眠场景的即时回复采用“亲密度加权 + 随机保留不回复”的决策：亲密度提高被唤醒/即时回复概率，但任何亲密度下都必须保留继续睡眠、不立即回复的合法结果。
- 睡眠回复决策必须记录可审计的内部原因类别（亲密度区间、消息重要性、睡眠状态、随机结果、预计醒来时间），普通聊天文案不得暴露概率、评分或内部规则。

### R7. 事件到状态和用户可见投影

- 事件事实必须先持久化，再按策略选择是否产生动态、媒体作业、主动消息和记忆。
- 不是每个日常事件都应发布动态或主动私聊。
- 动态、媒体、主动消息必须与事件事实可追踪关联，但事件真实发生不等于必须向用户投递。
- 主动消息需独立记录“是否应该投递、实际是否投递、跳过原因”，避免把事件发生和打扰用户耦合。
- 前端普通视图显示当前状态、地点/场景和用户可见动态；Debug Inspector 显示完整时间线、事件、候选、决策、作业及其原因。

### R8. 兼容性、安全与持久化

- 追加数据库 migration，不修改既有 migration；已有数据库升级后必须保留现有人格、事件、日程、动态、媒体和消息。
- 继续兼容 `companion_life_events`、`companion_schedule_items`、`companion_daily_plans`、`companion_jobs` 现有数据与 API。
- LLM 只能生成候选模型和计划建议；最终事件实例必须通过服务端 validator。
- 禁止自动生成死亡、严重伤害、医疗诊断、违法、重大财务损失、不可逆关系/身份改变、现实接触义务、情感勒索等事件。
- 事件、计划、决策和异步作业必须幂等；服务重启、租约过期和重复 tick 不得重复生成同一事实事件。

## Acceptance Criteria

- [ ] 人格初始化可以生成并持久化一份结构化生活模型；模型失败时使用完整 fallback，且人格仍可正常创建和聊天。
- [ ] 人格激活时同步生成生活模型；无论 LLM 成功还是 fallback，首个状态、默认房间、supporting characters 和首日计划都来自同一份最终生活模型。
- [ ] 生活模型包含默认地点、默认房间、固定时间事件、每日可偏移事件、随机正向候选和随机负向候选。
- [ ] 当天时间线可以被审计，明确区分固定安排、弹性安排、候选事件、已执行事件、跳过事件和被压制事件。
- [ ] 事件具有明确的开始/结束时间或结束条件；结束后状态正确回落到有效的下一层时间线状态。
- [ ] 事件冲突由优先级和覆盖模式确定解决，不再由“最近写入的事件”偶然覆盖。
- [ ] 相同人格、相同日期和相同触发上下文在重试/重启/重复 tick 下不会产生重复事实事件。
- [ ] 随机事件来自人格生活模型，而不是固定的三种硬编码模板；`no_event` 可以被选择。
- [ ] 正向事件具备人格适配、冷却、频率限制、地点连续性和重复度控制。
- [ ] 人格初始化可以生成少量稳定 supporting characters；事件首次引入或发展人物时有稳定 ID、来源、首次出现事件和关系变化审计，并优先复用已有角色。
- [ ] 负向事件仅允许 mild、可逆、有恢复路径的事件，并有每日/每周预算和全局安全守卫。
- [ ] 用户可以在任意生活场景发起聊天；普通场景可即时或短暂被打断，睡眠场景会根据策略被唤醒或延迟回复，并在 UI 中呈现自然状态。
- [ ] 睡眠场景下，亲密度越高即时回复概率越高，但每个亲密度区间都仍有不回复/醒来后回复样本；随机决策可复现、可测试且不会因重复轮询重复触发。
- [ ] 睡眠决定不立即回复时，用户侧不会出现睡眠占位、系统提示或预计时间提示；消息在内部进入延迟投递状态，并在计算出的 `deliverAt` 到达后以普通助手消息投递。
- [ ] 睡眠延迟批次在 `deliverAt` 前收到多条用户消息时，会合并理解并只投递一条回复；后续消息不能打断、唤醒或改写已经确定的延迟决策。
- [ ] 聊天不会因为当前事件类型被禁止；聊天影响生活时必须通过显式计划/事件契约进入时间线。
- [ ] 聊天作为 overlay interaction 叠加在当前生活事件上；短聊天不改变固定/可偏移事件，长聊天只能按明确阈值推迟或压缩可偏移事件，不能覆盖固定承诺。
- [ ] 事件事实、状态投影、动态、媒体、主动消息和投递结果之间存在可查询关联。
- [ ] Debug Inspector 能展示今日时间线、当前事件、候选/压制决策、事件因果、作业状态和跳过原因。
- [ ] 现有人格、日程、动态、消息、媒体、主动消息、恢复和屏蔽相关测试保持通过，并新增时间线、事件安全、幂等、跨场景聊天和睡眠回复测试。
- [ ] 追加 migration 与文档/规格同步完成，且完成全量质量检查。
- [ ] 用户明确修改会影响生活的身份、职业、居住地、兴趣、作息或关系设定时，可以生成新的生活模型 revision；历史事件、历史消息和已发生事实不被回写，当前固定日程不被静默删除，未来时间线渐进切换到新模型。

## Confirmed facts

- 当前 `companion_life_events` 是事件事实记录，`companion_persona_states.source_event_id` 指向状态来源，`companion_activities.event_id` 关联动态，`companion_messages.proactive_event_id` 关联主动消息。
- 当前 `createEvent()` 在同一事务内写事件、更新状态、可选创建动态、媒体作业和主动消息作业。
- 当前 `maybeCreateLifeVariation()` 使用固定 `social/shopping/mild_setback` 三类逻辑与确定性 seed，不是人格生成的完整事件库。
- 当前 `companion_daily_plans` 与 `daily_plan` job 已存在，但当天计划仍然是有限的日程项，不是完整的事件时间线。
- 当前状态读取优先级是活跃生活事件 > 有效日程 > routine；前端后台主要依靠 15 秒 polling，聊天 POST 内部使用 token/done/error SSE。
- 当前没有结构化世界/地点/房间领域模型，只有 `scene` 字符串。
- 当前 `reconcilePersona()` 每五分钟可能通过 `createEvent()` 记录状态推进，新的编排器必须避免重复复制事实事件。
- 项目采用版本化 SQLite migration，已有数据库必须通过新 migration 升级。

## Non-goals

- 不把生活事件改造成通用外部消息队列或跨服务 Event Bus 作为第一步；先在现有 SQLite durable job 与事件事实模型上完成完整领域能力。
- 不让 LLM 直接控制数据库、直接实例化未经验证的事件或直接改写人格身份。
- 不把每个生活细节都发布成动态，不把事件日志原样暴露给普通用户。
- 不允许自动生成不可逆、高风险或会制造用户现实义务的事件。

## Resolved decisions

- 睡眠时收到消息：按 AI 与用户的亲密度、消息重要性、当前睡眠状态和随机结果决定是否立即回复；亲密度只提高即时回复概率，不能把概率提升为 100%。
- 所有亲密度区间都必须保留“继续睡眠、不立即回复、自然醒后回复”的结果。
- 睡眠决策必须成为持久化、幂等、可测试的互动决策，不能在前端轮询或每次重复读取时重新随机。
- 睡眠下不立即回复时，不展示额外的系统状态或预计回复信息；系统只在内部决定消息的 `deliverAt`，到时投递自然的普通助手消息。
- 一旦进入睡眠延迟批次，后续用户消息只能合并到该批次，不能重新触发即时回复；该批次成功投递后才开启下一次独立的睡眠互动决策。
- 普通场景聊天默认是 overlay，不创建替代生活事件；只有达到注意力/时长阈值时才调整可偏移时间线，固定事件和用户明确日程不被聊天覆盖。
- 允许人格初始化生成少量稳定 supporting characters；运行时只在事件证据和冷却允许时引入/发展关系，不按每次随机事件临时创造人物。
- 人格激活阶段同步调用 LLM 生成生活模型；先生成 deterministic-safe baseline，LLM 失败或校验不通过时使用完整 fallback，不能让异步回写改变刚创建人格的首日一致性。
- 只有明确影响生活模型的设定修改才触发重新规划；语气、外观文案或互动边界等不影响生活结构的修改不自动重建整套生活模型。
- 生活模型 revision 必须保留旧版本和变更原因；新模型只影响未来候选与未来时间线，不能重写历史事件或已发送消息。
