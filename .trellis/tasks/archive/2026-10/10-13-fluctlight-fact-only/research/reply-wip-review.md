# FO-C WIP correctness review

2026-10-13; static review only. No product edits, real model, database integration run, or full regression suite.

## Confirmed findings

1. **P1: Source-less cognition runs can publish more than one reply in the same run.** `apps/core-go/internal/core/private_reply_run.go:83` falls back from `SourceFactID` to the individual native Tool operation ID. `adk_conversation_runtime.go:163` deliberately changes that ID for every model sequence/tool index. `RunConversationCognitionAgent` supports runs without an inbox fact (`cognition_agent.go:9`, input only requires RunID/current input), and supplies that stable RunID as the operation root (`cognition_agent.go:133`). With empty SourceFactID, two reply calls therefore obtain distinct draft/publication identities, independently generate, and can both publish. The publication's one-reply-per-turn check only runs when it resolves a real turn (`tool_publication.go:136`), so it does not fence these independent source-less runs. Minimal fix: derive draft/publication identity from source fact when present, otherwise from the stable private run's operation root/RunID; use the same key in preparation and publication. Preserve per-native-call IDs for receipts/diagnostics. Add a focused controlled case with one stable RunID, no SourceFactID, two native reply positions, asserting one draft and one message.

2. **P2: Durable prepared/published replay unnecessarily depends on the current model binding being available.** `fact_only_reply_capability.go:49` returns `AssignmentError` before the durable cache lookup at `:121-130`. A previously committed reply can have no receipt for a later native call's distinct operation ID, so generic receipt replay will miss even though the source-level draft is published. If the model role is removed/unavailable or its budget invalid before recovery, `withPrivateReplyRun` populates AssignmentError and this call cannot consume the published result. Likewise an already prepared text cannot be committed without model availability despite requiring no generation. Minimal fix: keep resource authorization before replay, but validate AssignmentError only immediately before a new physical generation, after authorized cached prepared/published lookup. This also needs a focused test for published draft + no receipt for the new native operation + unavailable model, asserting no model call and successful replay.

## Verified paths and limits

- Context registry is used for generic capability-owned preauthorization, runtime creation, ADK definition validation/lookup/native contract, and native model-facing result projection. Catalog/discover implementations consult the scoped registry; Kev original definitions come from the scoped catalog. Remaining shared-registry utility lookups add unchanged utility schemas and do not replace conversation.reply.
- Generation occurs in capability preparation before `executeToolMutation` opens its transaction. Publication and draft-published update run inside the existing transaction, which also persists the Tool receipt.
- Exact-operation receipt replay occurs before Prepare and does not regenerate. Authorized prepared/published cache hits themselves do not regenerate; finding 2 concerns their earlier binding gate.
- The child resets physical parent tool policy, Kev selection/persona state, ADK context, refresh plan, repair marker and queue bypass; the formal child rebinds its own definition, text output, scenario, diagnostics and frozen assignment. The child's formal input has no definitions, and Kev returns without adding discovery tools.
- Parent physical queue permits are scoped to Generate/Stream calls and released before Tool execution; child capacity wraps the shared generated queue with its own capacity key cleared. No nested parent-generated permit deadlock found in the reviewed path. Child reply currently uses non-streaming formal input, so the separate streaming queue's absence of task-capacity support is not an active text-reply bug.
- Normal committed Tool output includes the generated text and retains it in the model-facing schema. Duplicate-suppressed proactive output continues existing semantics and is excluded by existing committed-reply projection checks.
- No new confirmed late-send/authorization bypass was established. Existing transaction ownership checks, lifecycle-before-life lock ordering, WakeUp current-execution gate and context cancellation remain in place.

Known unfinished items explicitly excluded from new findings: media handoff, legacy fallback/retry implementation, Draft LifeRevision/FactsRevision wiring, and bounded failure cleanup. The failed/expired draft takeover also retains old stored config/binding/profile while generating from a new run snapshot; this overlaps the unfinished retry contract and should be checked when recovery is implemented rather than counted as an additional new finding here.
