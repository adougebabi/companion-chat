# 简化人格初始化为自然语言描述

## Goal

让用户在创建陪伴者时直接输入一段自然语言描述，由服务端调用现有 LLM 能力提取创建人格所需的信息；用户不需要理解或逐项填写当前访谈中的大量字段。系统只保留能够映射到人格和生活蓝图的结构化信息，其余内容丢弃或不进入持久化状态。

## Background

- 当前实际使用的创建入口是 `src/companion-main.js` 的 `openPersonaWizard()`，会通过 `/api/companion/interviews` 展示逐题访谈，问题清单位于 `server.js:938-963`。
- 当前访谈预览由 `previewInterviewAnswers()` 确定性生成，尚无“自然语言 -> 结构化人格”的 LLM 抽取阶段。
- `buildInitialBlueprint()` 已提供结构化 `characterCard`、`foundation`、`interests`、`supportingCast` 和字段 provenance；`generateInitialLifeBlueprint()` 已提供严格 JSON、超时和完整 fallback 的 LLM 调用模式。
- 人格最终持久化由 `createPersona()` 负责，生活模型创建应继续沿用现有 `activateInterviewWithLifeModel()` 路径，避免产生半成品人格或重复计划。

## Requirements

1. 创建人格向导的主要输入改为一个多行自然语言描述框，并以清晰、简短的文案说明“描述你希望她是谁、什么性格、生活背景以及你们如何相处”；不再要求用户理解并逐项回答完整字段清单。
2. 服务端提供一个分析/预览阶段：接收有长度上限的自然语言描述，通过现有服务端 LLM provider 抽取允许的人格字段，严格解析和规范化 JSON，未知字段和无法映射的信息不进入结构化结果。
3. 抽取结果必须复用现有人格蓝图/访谈字段契约，至少支持创建所需的 `name`、`role`、`foundation`，并尽可能填充性格、语言风格、兴趣、外观、支持角色、用户关系与互动边界等已有字段。
4. 用户明确写入的事实优先于模型推断；预览中要区分用户提供和 AI 推断的内容，并允许用户在确认前修改核心摘要字段。
5. 分析失败、模型超时、非 JSON 或校验失败时，不得创建半成品人格；返回可理解的错误并允许用户保留原文重试，不提供逐题访谈 fallback。最终创建仍只发生在用户确认后，并继续使用现有激活/生活模型生成链路。
6. 保持现有逐题访谈 API 的兼容性，避免影响已经存在的客户端或历史数据；新自然语言流程可复用 interview session 保存分析结果和确认状态。
7. 不把原始自然语言全文写入稳定人格字段、聊天上下文或其他长期持久化字段，除非它已被映射为允许的结构化字段。

## Acceptance Criteria

- [ ] 新建人格向导默认展示一个多行自然语言输入，而不是连续展示大量字段选项。
- [ ] 输入一段包含姓名、身份、性格和关系偏好的中文描述后，服务端返回可预览的结构化人格摘要，并保留字段来源标记。
- [ ] 预览允许修改核心摘要并在确认后只创建一个完整人格；生活蓝图和 daily plan 仍通过现有激活流程生成。
- [ ] LLM 返回 Markdown 包裹 JSON、未知键、缺少必填字段、超长输入、空响应、超时或非 2xx 时，接口返回稳定的 `{ error }` 语义，不写入 persona。
- [ ] 用户明确事实不会被模型输出覆盖；无法从原文提取的信息不会伪装成用户提供。
- [ ] 现有逐题 interview API 和已有测试继续通过；新增测试覆盖正常抽取、过滤/校验、失败重试和 provenance。

## Decision

- 新建人格只允许自然语言描述 + LLM 分析流程；不保留逐题填写 fallback。现有逐题 interview API 为兼容历史客户端继续保留，但不再作为当前向导入口。
- 当描述缺少 `name`、`role` 或其他创建所需信息时，允许模型生成受约束的默认值。默认值必须标记为 AI 推断，并在确认前可被用户修改。
