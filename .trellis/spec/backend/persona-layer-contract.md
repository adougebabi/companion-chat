# Persona Layer Contract

## Scenario: Core Persona, Developing Self, And Current State Without Drift

### 1. Scope / Trigger

- Trigger: a new Fluctlight is initialized, a Reflection proposal is applied, or cognition/realization needs Persona context.
- This contract applies to the clean-start Go Core, Go BFF, browser client, and the existing Persona detail/governance surfaces.
- Old instances and legacy `provenance.self_model` / `personality_candidates` data are not migrated or replayed by the new flow.

### 2. Signatures

```text
create_fluctlight({core_persona, developing_self, initial_goals, initial_intentions})
  -> Fluctlight
reflect({developing_self_candidates, memory_candidates, relationship_candidates,
         drive_candidates, preference_candidates, trigger_candidates})
  -> ReflectionOutcome
BuildContextProjection(...) -> ContextProjection
GET  /api/fluctlights/{id}/detail
GET  /api/fluctlights/{id}/developing-self
POST /api/fluctlights/{id}/developing-self/{claimId}/rollback
POST /api/fluctlights/{id}/developing-self/{claimId}/forget
```

### 3. Contracts

- Core Persona is the owner-governed, automatic-read-only snapshot in `fluctlights.core_persona`. It contains the existing `identity`, `personality`, `behavioral_policy`, and `life_profile` page-shaped groups. Those legacy-shaped groups are synchronized projections for the same new instance, not separate automatic evolution targets.
- Developing Self is a claim projection stored one row per claim in `fluctlight_developing_self_claims`, with `category`, `claim`, `value`, `confidence`, `evidence_refs`, `provenance`, `status`, `revision`, and optional expiry/supersession. Revisions are append-only in `fluctlight_developing_self_revisions`.
- Current State remains the `fluctlight_inner_states` snapshot and resolved current context. It includes `pad`, `mood`, `momentum`, `regulation`, `drives`, `conflicts`, `revision`, and `last_updated_at`.
- Runtime priority is `Core Persona > Developing Self > Current State`. Developing Self is soft context; it may inform content and momentary expression but cannot mutate Core Persona or long-term behavioral policy.
- Initialization analysis returns `core_persona`, `developing_self.claims`, `initial_goals`, and `initial_intentions`. Current State is server-initialized and is not generated by the initialization model. Blank-slate creates safe Core defaults, empty Developing Self, and neutral Current State.
- Reflection returns `developing_self_candidates` and never returns or applies `personality_candidates` or `self_model_candidates`. A candidate can create/update a Developing Self claim or an existing typed slot, but cannot update `fluctlights.personality`, `fluctlights.core_persona`, or `provenance.self_model`.
- Every Developing Self mutation records an outcome (`accepted`, `rejected`, `conflict`, `rollback`, or `forgotten`) with a stable reason code, evidence references, confidence, provenance, source window, and revision/CAS information.
- Evidence references are validated against the Fluctlight-owned Reflection window. Fact IDs and `sequence:N` aliases resolving to the same fact count once. Repeated claims without new evidence are deterministic no-ops.
- ContextProjection exposes canonical `core_persona`, `developing_self`, and `current_state` fields plus the existing identity/personality/policy compatibility view. Frozen actions retain the projection captured at assessment; realization never re-reads mutable Persona state.
- Provider-facing serialization lifts the semantic Core Persona groups (`identity`, `personality`, `behavioral_policy`, `life_profile`) into the fixed system `# 人格设定` section. It omits schema/version, internal IDs, revisions, persistence timestamps, foreign keys, and automatic-evolution controls; Developing Self, Current State, memories, goals, intentions, recent messages, and `life_context.current_time/timezone` remain dynamic context sections.
- Existing Persona fields keep their current Web presentation. New layer objects are displayed as bounded, read-only JSON; Developing Self governance uses explicit rollback/forget actions rather than arbitrary JSON replacement.

### 4. Validation & Error Matrix

| Condition | Result |
| --- | --- |
| Initialization omits a required Core group or Developing Self claim metadata | Reject with `initialization_persona_invalid`; create no Fluctlight |
| Blank-slate request supplies non-empty layered foundation | Reject with `blank_slate_foundation_forbidden` |
| Reflection candidate targets Core Persona or an unknown Developing Self category | Reject/record bounded diagnostic; never mutate Core |
| Candidate has missing/foreign/duplicate evidence or confidence outside `0..1` | Reject or record `insufficient_evidence`; watermark does not apply the candidate |
| Reflection window or claim revision is stale | Return conflict; do not overwrite newer state |
| Owner rollback/forget uses stale claim revision | Return conflict; claim and ledger remain unchanged |
| Provider emits legacy personality/self-model candidate keys | Structured result is invalid; no legacy automatic write path runs |
| Current State is missing from a read model | Return bounded empty/current snapshot; never synthesize a personality change |
| JSON value is object/array/null in Web detail | Render through bounded `JSON.stringify`; never rely on implicit object coercion |

### 5. Good / Base / Bad Cases

- Good: a Reflection observes “我似乎喜欢安静” with two distinct inbox facts; Core stores one Developing Self claim with confidence/provenance and leaves `core_persona.personality` unchanged.
- Good: a current mood of “开心” makes the next response warmer for that turn while Core Persona still enforces mature, independent, non-pleasing behavior.
- Base: a new blank-slate Fluctlight has an empty claims list and neutral inner state until cognition produces evidence.
- Bad: three aliases of one inbox fact satisfy an evidence count, or a single positive user reaction changes `personality.agreeableness`.
- Bad: realization re-reads a newer Persona after a frozen decision and combines an old response plan with a new voice.

### 6. Tests Required

- Migration tests for `core_persona`, Developing Self claim/revision tables, indexes, constraints, and the new migration head.
- Initialization tests for layered provider schema, owner-defined seed provenance, blank-slate defaults, strict legacy-key rejection, and atomic claim creation.
- Reflection tests for candidate schema, category allowlist, evidence ownership/deduplication, repeated-claim no-op, Core conflict rejection, stale watermark/CAS, and transaction rollback.
- Context tests for authority/priority fields, complete Current State readback, separate layer revisions, and frozen projection reuse during realization retry.
- API/BFF tests for detail/layer routes, owner authorization, stable errors, CAS conflicts, rollback/forget, and redaction.
- Web tests for existing field rendering, bounded JSON display, new layer sections, read-only Current State, and Developing Self governance controls on narrow and desktop layouts.

### 7. Wrong vs Correct

#### Wrong

```go
// A reflection observation is treated as a permanent personality mutation.
personality["agreeableness"] = candidate["value"]
UPDATE public.fluctlights SET personality = ...
```

#### Correct

```go
// Reflection writes only an evidence-backed Developing Self claim.
applyDevelopingSelfCandidateTx(ctx, tx, fluctlightID, candidate, refs, allowed, sourceWindow)
// Core Persona remains owner-governed and Current State remains transient.
```
